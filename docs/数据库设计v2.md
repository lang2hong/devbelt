# DB Client — 数据库设计 v2（历史实现记录）

> **已被 [V3 实施规格](./v3/实施规格.md) 替代。** 本文描述当前 V2 运行时代码的历史模型，不能作为新功能、迁移或 API 的开发依据。

> 状态：S3 已完成并接入运行时（app.ts 切到 runMigrations，旧 schema/事件/流量落库/限流 DB 路径已删，单测全绿）
> 日期：2026-08-25（2026-08-26 更新）
> 前置决策：[ADR-0001 Team per-seat 席位计费](./adr/0001-team-per-seat-billing.md)
> 决策结论：Greenfield 重构；不迁移任何旧数据、不兼容旧客户端协议、不保留历史债务。`register`/`login`/`refresh` 响应统一返回 `accessToken`/`refreshToken`/`user`/`subscription`，已移除旧版 `token`/`userId`/`role` 顶层字段。

## 1. 全局约定

| 项 | 约定 |
|---|---|
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT` |
| 时间字段 | `create_time` / `update_time`，`DATETIME`（UTC），默认 `CURRENT_TIMESTAMP` |
| 软删除 | `delete_time DATETIME NULL`（NULL=未删，非 NULL=删除时刻） |
| 字符集 | `utf8mb4` + `utf8mb4_0900_ai_ci`，引擎 `InnoDB` |
| 金额 | `DECIMAL(10,2)`（元） |
| 命名 | snake_case、单数表名、外键 `xxx_id` |
| 迁移 | `schema_migrations` 版本化（替代 `addColumnIfMissing` 补丁式） |

设计原则：

1. **组织是计费与共享资源主体**：`users.plan_code` 反范式冗余移除；订阅、席位、组织共享额度和共享资源统一挂在 `organizations` 上。个人同步与私人资源仍挂 `users`，其有效私有额度取活跃席位对应套餐中的最高值，不跨组织叠加。
2. **外键策略**：核心关系建 `FOREIGN KEY`；组织审计不建外键，避免删除成员后丢失责任记录。
3. **从零初始化**：迁移只建 schema 与播种套餐；旧用户、密文、日志、支付回调和运行配置全部丢弃。

## 2. 领域划分与关系

```
身份/组织  users · organizations · memberships
认证/设备  refresh_tokens · devices
计费      plans · subscriptions · orders · seats · webhook_events
协作      organization_resources · organization_resource_permissions · organization_audit_log
同步      sync_sections · sync_section_versions · connection_meta
迁移      schema_migrations
```

核心关系（组织为枢纽）：

```
users ──membership──> organizations <──subscription── plans
                         │
                         ├── seats（逐席位数量，占用关系由 memberships 表达）
                         ├── organization_resources ── permissions ──> memberships
                         ├── orders（不可变计费流水）
                         └── (owner_user_id → users)
```

- 每个用户注册即建一个 `type='personal'` 的隐式个人组织，并写入一条 `role='admin'` 的 membership；商业 Owner 的唯一权威是 `organizations.owner_user_id`。
- free/pro = 单席位 personal org；team = 多席位 team org。订阅、席位、组织共享额度和共享资源从 org 出发取数；个人连接、设备、历史、同步密文仍属于 user。

### 2.1 商业配额归属

| 套餐字段 | 计量主体 | 对应数据 |
|---|---|---|
| `per_seat_max_devices` | 有效席位成员 | `devices`（按 user） |
| `per_user_max_private_connections` | 有效席位成员 | `connection_meta`（按 user，私有） |
| `per_user_max_open_connections` | 有效席位成员 | 客户端显式打开的连接数 |
| `per_user_private_sync_quota_bytes` | 有效席位成员 | `sync_sections`（按 user） |
| `org_max_shared_connections` | 组织 | `organization_resources` 中的 connection_template |
| `org_shared_sync_quota_bytes` | 组织 | `organization_resources.encrypted_data` |
| `org_max_members` | 组织 | 活跃 `memberships` |

同一用户属于多个组织时，个人资源额度取所有有效席位套餐中的**最高值**，不相加；personal org 的套餐是最低保底。组织共享额度只属于产生该共享资源的组织。

## 4. Greenfield 初始化

v2 不接收任何 v1 数据。旧数据库、旧表、旧密文、旧会话、旧设备、旧订单与旧日志均不参与初始化；运行观测、限流与系统日志交给应用配置和外部日志系统，而不是进入核心产品库。

初始化顺序：

1. 建立空数据库，执行 `migrations/index.ts`：001 建 16 张核心业务表，002 播种 Free / Pro / Team 套餐，003 补建 `admin_audit_log`（第 17 张业务表）。
2. 用部署环境变量执行 `pnpm --filter @db-client/server run bootstrap:admin` 创建唯一的初始系统管理员、其 personal org、free 订阅和一个有效席位。
3. 管理员在新系统中配置 Team 定价、创建组织和席位；用户重新注册、重新登录、重新录入个人连接与同步密码。

部署流程只应在 Greenfield 空库中执行管理员 bootstrap，且必须显式设置 `BOOTSTRAP_ADMIN_CONFIRM=CREATE`。不通过 migration 写入管理员凭据，避免把部署秘密混入 schema 历史。当前代码会验证邮箱不存在及 Free 套餐已播种；它尚未以数据库状态强制证明“空库”，该保护属于 S3 前的待加固项。

## 5. 剩余开放问题

1. **订单快照**：是否在 `orders` 增加不可变 `plan_snapshot`，避免套餐编辑改变历史订单语义。
2. **席位计费对齐**：加/减席位与月/年周期如何按比例折算。
3. **定价数字**：当前 Team seed 为 ¥20/月、¥200/年、包含 5 席位，额外席位同价；上线前需商业确认。
4. **静态加密密钥管理**：服务端数据密钥的 KMS 托管、轮换和泄露处置流程。
5. **共享类型扩展**：首期仅连接模板、查询、文件夹；项目、仪表盘等新增资源类型的授权语义。
6. **金额单位**：元（DECIMAL）是否满足多币种，后续是否需分（整数）避免精度问题。
