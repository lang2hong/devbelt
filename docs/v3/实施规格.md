# DB Client - V3 实施规格

> 状态：Phase 1（§2–§6 已冻结的基础域契约）已实施并通过验收（§6.4 含 route smoke）；个人 E2E 同步 V1 契约已冻结、待实施准入复核（§8.1），在通过复核并完成单独 L2/L3 实施规划前不得落码；其余 §8 暂缓专项尚未准入实现。本文件是 V3 唯一实施权威，替代此前分散的数据、权限、交接和阶段设计文档。组织资源版本存储·历史保留与受限协作、账号删除生命周期、支付运营、Platform Admin、资源静态加密与密钥隔离尚未冻结；未经对应专项设计和准入复审，不得实施这些能力。
> 兼容性：Greenfield。不得迁移 V2 数据、双写、保留 V2 API fallback、兼容 V2 DTO 或客户端语义。
> 实施原则：先交付第 7 节已冻结的基础域；暂缓模块仅在完成专项设计与准入复审后纳入交付范围。任何后续模块不得绕过前置数据、权限或安全契约，也不得以 V2 fallback、双写或兼容 DTO 作为过渡。

## 1. 范围与权威

V3 重构承载个人/组织数据归属、授权、套餐、同步与服务端交互语义的 `packages/server`、`packages/vscode-ext` 和 `packages/admin-ui`。`packages/db-core` 保持数据库驱动、连接和查询的通用职责，不引入用户、组织、套餐、同步、支付或 ACL。

本文件中已冻结的表、字段、状态、权限代码、路由、错误码和阶段边界各只定义一次。ADR 仅记录决策背景；历史 V1/V2 文档不得作为实现依据。实现中发现已冻结规格遗漏时，先更新本文件和测试，再修改代码；未冻结专项不得由实现自行补充安全、保留或商业语义。

## 2. 不可突破的边界

1. 服务端元数据存储仅支持 MySQL 8：使用 `BIGINT UNSIGNED AUTO_INCREMENT`、`DATETIME(3)` UTC、MySQL JSON、复合外键和 `SELECT ... FOR UPDATE`。数据库主键在 HTTP/TypeScript DTO 中一律为十进制 `string`。
2. 用户拥有个人空间，组织拥有协作空间。个人套餐、订阅、订单、设备、会话、E2E 同步、私有连接元数据只以 `user_id` 归属；组织套餐、订阅、成员、资源和席位只以 `organization_id` 归属。
3. 组织成员、权限或 seat 永远不能提升个人设备、连接、同步、历史或数据库引擎权益。个人数据不能被组织角色、组织 API 或组织管理员读取、修改、计量或管理。
4. 组织资源是服务端授权的结构化内容；禁止保存数据库密码、SSH 密码、SSH 私钥、私钥口令、个人连接 ID、个人 E2E 主密码、本地凭据映射或 SQLite 本地路径。个人 E2E 同步及其密文格式、密钥生命周期、版本和回滚在专项协议冻结前不实施。
5. 所有组织请求必须从 URL 取得 `organizationId`，并在服务端验证用户、组织、membership、权限、订阅和配额。Workspace 仅是客户端 UI 选择，不是授权输入。
6. 组织角色不能授予个人数据访问、支付确认、服务端内容解密或任何跨组织权限。Platform Admin 是暂缓专项模块，启用时只能通过独立 `/api/admin` 路由获得，应用 API 与 Admin UI 不读取组织资源内容。此限制是应用层访问控制，不构成对数据库、备份、部署环境或密钥管理等基础设施特权主体的保密承诺；在完成可验证的密钥隔离设计前，不得将“Platform Admin 不可读取组织正文”作为合规保证。

```ts
type DatabaseType = 'mysql' | 'postgresql' | 'sqlite';
type OrganizationRole = 'admin' | 'member';
```

## 3. 角色与权限

Phase 1 只有组织 `admin` 与 `member` 两个预置角色，不能创建、删除或改名其他角色。业务口语中的“组织 Owner”仅指组织 `admin`，文档、DTO、数据库与代码一律使用 `admin`，不存在 `owner_user_id`、Owner 身份、所有权转移或 Owner seat。membership 只保存一个 `role`；创建组织的用户成为首位 active `admin`。Platform Admin 及其 bootstrap、审计和最后一名管理员约束属于商业与运营专项，Phase 1 不提供该身份或 `users.system_role`。

### 3.1 管理可见性与操作矩阵

| 主体 | 可读取与管理 | 明确禁止 |
|---|---|---|
| 组织 `admin` | 本组织成员、邀请、资源正文与元数据及目录。 | 其他组织、平台运营、个人同步、私有连接元数据、任何凭据/密钥及用户本地凭据映射。 |
| 组织 `member` | 本组织摘要、最小成员目录、固定角色权限摘要、目录和全员共享资源的只读访问。 | 所有组织管理、平台运营和个人数据访问，除非其本人通过个人 API 访问自己的个人数据。 |

Platform Admin、支付渠道配置、审计、ACL、版本和监控均属于暂缓专项模块；在对应模块获批前，Phase 1 不创建其身份、表、路由或 UI。

## 4. 数据模型

所有实体表默认有 `id BIGINT UNSIGNED PK`、`create_time DATETIME(3)`、`update_time DATETIME(3)`。数据库列使用 `snake_case`，HTTP JSON 使用 `camelCase`。核心业务关系建外键；审计表不建外键以保留证据。订单快照和审计细节使用 JSON，但不得含 token、凭据或 E2E 明文。

### 4.2 Phase 1 MySQL DDL 约束与 seed

除下列明确的 `NULL` 外，Phase 1 业务字段均为 `NOT NULL`。所有 ID 都是 `BIGINT UNSIGNED AUTO_INCREMENT`；所有时间均为 `DATETIME(3)`；所有实体表都含 `create_time`、`update_time`。migration 与每个 MySQL pool connection 初始化必须执行 `SET time_zone = '+00:00'`，应用仅以 UTC 读写 `DATETIME(3)`，不得依赖数据库服务器或部署主机时区。migration 必须按以下依赖顺序建表：`users` -> plan 表 -> subscription 表 -> devices/refresh tokens/email verification tokens -> organizations -> memberships/invitations -> folders -> resources -> rate_limit_entries（限流计数表无外键，最后建即可）。

| 表 | 额外可执行约束、索引和外键 |
|---|---|
| `users` | `email VARCHAR(255)` 规范化为小写且 `UNIQUE`；`password_hash VARCHAR(255)`；`status VARCHAR(16) DEFAULT 'active' CHECK(status IN ('active','disabled'))`。账号删除状态与物理删除均属于账号生命周期专项。 |
| `personal_plans` | `code VARCHAR(32) UNIQUE`、`name VARCHAR(64)`、`allowed_database_types JSON`、`max_devices SMALLINT UNSIGNED`、`status VARCHAR(16) DEFAULT 'active' CHECK(status IN ('active','archived'))`。 |
| `personal_subscriptions` | `user_id UNIQUE`、`plan_id`、`status VARCHAR(16) DEFAULT 'active' CHECK(status IN ('active','expired','canceled'))`、`entitlement_snapshot JSON`、`period_start_time`、`period_end_time NULL`；FK -> users/plans。Phase 1 的 Free 订阅永久有效，`period_start_time=create_time`、`period_end_time=NULL`；非 Free 周期约束属于商业专项。 |
| `devices` / `refresh_tokens` | devices: `UNIQUE(user_id,device_key)`、status `active/revoked`、FK -> users。refresh tokens: `token_hash CHAR(64) UNIQUE`、`family_id CHAR(36)`、`device_id NULL`、`replaced_by_token_id NULL`、`expires_time`、`revoked_time NULL`、`last_used_time NULL`、`KEY(user_id,revoked_time,expires_time)`、`KEY(family_id,revoked_time)`、FK user -> users、FK device -> devices `ON DELETE SET NULL`、FK replaced-by -> refresh tokens。 |
| `email_verification_tokens` | `user_id BIGINT UNSIGNED`、`email VARCHAR(255)`、`token_hash CHAR(64) UNIQUE`、`expires_time`、`consumed_time NULL`、`KEY(user_id,consumed_time,expires_time)`，FK -> users。个人 E2E sync 与 `personal_connection_meta` 表在对应专项冻结前不得创建。 |
| `organization_plans` | `code VARCHAR(32) UNIQUE`、`name VARCHAR(64)`、`included_seats SMALLINT UNSIGNED CHECK(included_seats >= 1)`、`max_shared_resources SMALLINT UNSIGNED`、`shared_storage_quota_bytes BIGINT UNSIGNED`、`allowed_template_database_types JSON`、`status VARCHAR(16) DEFAULT 'active' CHECK(status IN ('active','archived'))`。 |
| `organizations` / subscriptions | organizations: `name VARCHAR(100)`、`status VARCHAR(16) DEFAULT 'active' CHECK(status IN ('active','closed'))`、`closed_time DATETIME(3) NULL`。subscriptions: `organization_id BIGINT UNSIGNED UNIQUE`、`plan_id BIGINT UNSIGNED`、`seat_limit SMALLINT UNSIGNED`、`status VARCHAR(16) CHECK(status IN ('active','expired','canceled'))`、`entitlement_snapshot JSON`、`period_start_time`、`period_end_time NULL`；FK -> organizations/plans，另建 `UNIQUE(id,organization_id)` 供复合 FK。Phase 1 的 `organization_free` 永久有效，`period_start_time=create_time`、`period_end_time=NULL`；非 Free 周期约束属于商业专项。 |
| memberships | `organization_id/user_id BIGINT UNSIGNED`、`role VARCHAR(16) CHECK(admin,member)`、`status VARCHAR(16) CHECK(invited,active,removed)`、`invited_by_user_id BIGINT UNSIGNED NULL`、`joined_time/removed_time DATETIME(3) NULL`、`UNIQUE(organization_id,user_id)`、`UNIQUE(id,organization_id)`、FK -> organizations/users。 |
| invitations | `organization_id/membership_id BIGINT UNSIGNED`、`token_hash CHAR(64) UNIQUE`、`email VARCHAR(255)`、`expires_time`、`accepted_time NULL`、`revoked_time NULL`；复合 FK `(membership_id,organization_id)` -> memberships `(id,organization_id)`。 |
| folders / resources | folders: `organization_id BIGINT UNSIGNED`、`parent_id BIGINT UNSIGNED NULL`、`name VARCHAR(200)`、`delete_time NULL`、`UNIQUE(id,organization_id)`，FK `(parent_id,organization_id)` -> folders `(id,organization_id)`。resources: `organization_id BIGINT UNSIGNED`、`folder_id BIGINT UNSIGNED NULL`、`resource_type VARCHAR(32) CHECK(connection_template,query)`、`name VARCHAR(200)`、`content JSON`、`version INT NOT NULL`、`created_by_membership_id BIGINT UNSIGNED`、`updated_by_membership_id BIGINT UNSIGNED NULL`、`delete_time NULL`、FK `(folder_id,organization_id)` -> folders `(id,organization_id)`、FK `(created_by_membership_id,organization_id)` / `(updated_by_membership_id,organization_id)` -> memberships `(id,organization_id)`，并建 `UNIQUE(id,organization_id)`。 |
| `rate_limit_entries`（限流计数，§4.5 共享存储落地补充） | `bucket_key VARCHAR(255)`、`window_start_time DATETIME(3)`、`count INT UNSIGNED NOT NULL DEFAULT 0`；`UNIQUE(bucket_key,window_start_time)`、`KEY(window_start_time)`。固定窗口：`window_start_time = floor(now / windowSeconds) * windowSeconds`（UTC 对齐）；计数经 `INSERT ... ON DUPLICATE KEY UPDATE count = count + 1` 原子递增。bucket_key 约定：`login:email:<normalized>` / `login:ip:<ip>` / `register:ip:<ip>` / `verify:email:<normalized>` / `verify:ip:<ip>` / `org:create:user:<userId>`，绝不包含密码、token 或组织资源正文。过期桶由受控清理任务删除，不依赖请求触发。 |

Phase 1 migration 必须显式 seed 以下最小值，不得从 V2 读取或继承：personal `free`（引擎 `mysql/sqlite`、`max_devices=0`，`0` 表示无限）；organization `organization_free`（`included_seats=3`、`max_shared_resources=50`、`shared_storage_quota_bytes=10485760`、引擎 `mysql`）。共享资源数量上限等于 `max_shared_resources`，所有未删除 `connection_template` 和 `query` 资源合并计数；配额按 canonical JSON 序列化后的 UTF-8 字节数总和计算，canonical JSON 使用递归字典序键排序、紧凑 JSON、UTF-8 编码。资源软删除立即释放数量和字节配额。

注册在单一事务内创建用户、永久有效的 Free 订阅和邮箱验证 token。创建组织在单一事务内锁定 `organization_free` plan，创建 active organization、永久有效的 Free 订阅（`seat_limit=included_seats`）和首位 active admin membership。

### 4.3 Phase 1 邀请、容量与资源事务

有效容量为 `COUNT(membership WHERE status='active') + COUNT(membership WHERE status='invited' AND 其邀请未过期、未撤销)`。创建、接受、撤销/过期邀请、移除、退出和角色分配都锁定组织订阅与相关 membership 行。Phase 1 不建 `organization_seats`：active membership 与未过期 invited membership 仅占用 `seat_limit`。

| 命令 | 前置条件 | 事务结果 |
|---|---|---|
| 创建邀请 | `member.invite`；组织/订阅 active；目标为既有 active、已验证邮箱；目标 membership 非 active；有效容量小于 `seat_limit`；未指定 role 时默认 `member`，指定 `admin` 还要求 `member.role.assign` | 撤销目标的旧有效邀请，membership 写 invited 和所选角色，写 token hash/过期时间。未注册或未验证统一返回 `400 INVITATION_TARGET_NOT_ELIGIBLE`。 |
| 接受邀请 | 认证用户的规范化、已验证邮箱匹配；token 有效；membership invited；组织/订阅 active | 标记 invitation accepted，membership 置 active，写 `joined_time`。 |
| 撤销 | `member.invite` | 标记 invitation revoked，membership 置 removed，释放容量。 |
| 过期 | 懒判定或清理任务 | 任何读取或容量计算都必须把 `expires_time <= now` 且未 accepted/revoked 的邀请视为无效并排除在容量之外；受控清理任务每 15 分钟把这些邀请标记 revoked、membership 置 removed，保证容量最终释放且不依赖成员再次操作。 |
| 移除成员 | `member.remove`；目标非自身；不造成最后一个 active admin 消失 | membership 置 removed，释放容量。 |
| 退出组织 | active member；退出者不是最后一个 active admin | membership 置 removed，释放容量。 |
| 分配角色 | `member.role.assign`；目标非自身；不造成最后一个 active admin 消失 | 更新目标 role。 |

资源更新条件为 `WHERE id=? AND organization_id=? AND version=? AND delete_time IS NULL`。受影响行数为零时，已授权调用者读取版本并返回 `409 RESOURCE_VERSION_CONFLICT` 与 `{code,currentVersion}`；不得 last-write-wins。创建和更新在同一事务内按 UTF-8 序列化 content 字节数、资源数量和当前订阅快照强制组织配额；超额返回 `409 ORGANIZATION_QUOTA_EXCEEDED`。目录移动在同一事务锁定被移动目录、新父目录和其祖先链，使用递归 CTE 或等价锁定查询拒绝 `parentId=folderId` 以及新父目录属于被移动目录后代的请求，返回 `409 FOLDER_MOVE_CYCLE`。目录不得隐式级联删除，含未删除子目录或资源时返回 `409 FOLDER_NOT_EMPTY`。

### 4.4 数据库引擎与内容 schema

个人连接支持 `mysql`、`postgresql`、`sqlite`，由个人订阅权益决定。个人 Free 仅 MySQL/SQLite；个人 Pro 和个人 E2E 同步属于后续专项。扩展在创建、编辑和连接入口做许可证门禁。

组织 `connection_template` 只允许组织订阅快照中的引擎：Phase 1 `organization_free` 仅 MySQL，其他引擎属于商业专项。`content` 必须是严格闭合 JSON：`{databaseType:'mysql',host:string(1..253),port:integer(1..65535),database:string(1..128),username?:string(1..128),ssl?:{mode:'disable'|'require'|'verify-ca'|'verify-full',rejectUnauthorized?:boolean}}`；服务端拒绝未知字段、空白 host/database、嵌套对象扩展和任何 password、secret、key、certificate、SSH 或本地路径字段。`query` 的 `content` 必须是严格闭合 JSON：`{sql:string(1..1048576),dialect?:'mysql'|'postgresql'|'sqlite'}`，`sql` 不得为空白且不接受连接标识、凭据、路径或未知字段。资源 `name` 是唯一显示名称来源，最大 200 UTF-8 字符；content 按第 4.2 节 canonical JSON 计量。SQLite 路径、文件内容和本地凭据永不进入组织资源。

### 4.5 Phase 1 认证安全契约

密码使用 Argon2id 保存，参数固定为 memory `65536 KiB`、iterations `3`、parallelism `1`、salt `16 bytes`、output `32 bytes`；每个 hash 必须自描述算法和参数。注册、登录与改密只接受 TLS 连接。密码至少 12 个 Unicode code points、最多 128 个 Unicode code points；服务端不记录或回显原始密码。

登录仅接受已验证邮箱且 `users.status=active` 的用户；未知邮箱、错误密码、未验证邮箱和被禁用用户均返回相同的 `401 UNAUTHORIZED`。登录和刷新响应包含 15 分钟有效的 Ed25519-signed access token 与 30 天有效的随机 refresh token。access token 必含 user ID、issued-at、expiry、key ID 和随机 token ID，仅经 HTTPS `Authorization: Bearer` 传输，不写入 URL、日志或持久化客户端设置。refresh token 至少含 256 bits 随机熵，仅经 TLS JSON request/response body 传输，不写入 URL 或日志；数据库仅保存 SHA-256 hash、user、可选 device、expiry、revocation、family 和 rotation 元数据。

每次 refresh 必须原子轮换并撤销被替换 token；已撤销或已替换 token 的再次使用必须撤销该 token family 的全部 refresh token 并返回 `401 UNAUTHORIZED`。logout、设备撤销、用户禁用和成功改密必须撤销受影响的 refresh token；改密要求有效 access token 和当前密码，并同时撤销该用户的全部 refresh token。access token 到期前可继续有效，但每个受保护请求仍检查用户状态。Phase 1 不提供忘记密码或邮件重置密码路由；该能力须在独立的恢复流程规格冻结后加入。

access token 使用部署环境注入的 Ed25519 私钥签名，配置提供当前签名 key ID 与全部可验证公钥（含待淘汰 key），服务端按 token 的 key ID 选择公钥；密钥绝不入库。缺少签名密钥时服务启动失败，不得回退到不签名或对称硬编码密钥。轮换时先加入新公钥并切换签名 key ID，待旧 access token 全部过期后再移除旧公钥。

对登录按规范化 email 与来源 IP 分别限流，每个维度 15 分钟最多 5 次失败；达到任一阈值返回 `429 TOO_MANY_REQUESTS`。注册按来源 IP 每小时最多 10 次；组织创建按用户（已认证，不按 IP）每小时最多 10 次；邮箱验证重发（匿名）按规范化 email 与来源 IP 每小时最多 3 次，响应不区分邮箱是否存在、是否已验证，以维持防枚举。限流计数必须保存在所有服务实例共享的存储中，使阈值对整个部署生效，不得按进程独立计数；限流状态不得保存密码、token 或组织资源正文。

### 4.6 Phase 1 设备与会话注册

`POST /api/auth/login` 与 `/refresh` 的请求都含以下 device 字段：

```ts
type DeviceFields = {
  deviceKey: string;
  devicePlatform: string;
  deviceName: string;
  clientVersion: string;
};
```

`deviceKey` 是客户端生成并持久化的随机标识，长度 16..128 字符，仅含 `[A-Za-z0-9_-]`；其余字段各最长 100 字符，仅作展示元数据。服务端按 `(user_id,deviceKey)` upsert device：不存在则创建 active device，存在且 active 则更新展示元数据，存在但 revoked 则重新置 active 并视为新会话。该用户 active device 数量将超过个人订阅快照 `max_devices`（`0` 表示无限）时返回 `403 PERSONAL_FEATURE_REQUIRED`，不得静默复用他人 device 或超额签发。

签发的 refresh token 必须绑定该 device；`DELETE /api/personal/devices/:deviceId` 只能撤销调用者本人的 device，并在同一事务把该 device 的全部 refresh token 撤销。`GET /api/personal/devices` 只返回 `{deviceId,devicePlatform,deviceName,clientVersion,status,lastUsedTime,createTime}`，不返回 token、hash 或其他用户的数据。

### 4.7 Phase 1 邮件投递契约

服务端只通过单一 `EmailSender` 抽象发送邮件，Phase 1 只有两类邮件：邮箱验证与组织邀请。生产环境使用部署环境注入的 SMTP 或服务商凭据；凭据只来自环境配置，不入库、不经 API 返回。测试与本地开发必须使用可断言的替身实现，禁止向真实地址发信。

token 先在业务事务内落库，再在事务提交后发送邮件。发送失败不回滚已提交的注册、邀请或 token，只记录不含 token 明文的失败日志，由用户重发邮箱验证或管理员重新创建邀请恢复。邮件正文只含收件人展示名、组织名、动作说明、一次性链接和过期时间，验证邮件另可含可复制的验证 token（与一次性链接中的 token 一致，无额外暴露）；不得包含密码、access/refresh token、组织资源正文、个人同步内容或其他成员邮箱。组织邀请邮件仅含一次性链接，不含可复制 token。

邮箱验证 token 有效期 24 小时，邀请 token 有效期 7 天；两者都至少含 256 bits 随机熵，数据库只保存其 SHA-256 hash，且只能消费一次。重发邮箱验证或重新邀请同一目标时，必须先作废该用户或该 membership 既有的未消费 token，保证同时最多一个有效 token。

## 5. Phase 1 授权、状态与 API

组织请求固定顺序：认证/session 未撤销 -> `users.status=active` -> organization active -> active membership -> permission code -> 配额 -> schema 校验 -> 单一业务事务。组织存在性属于敏感元数据：组织不存在、closed、suspended（如后续模块引入）或调用者不是 active membership 时，普通组织 API 一律返回 `404 ORGANIZATION_NOT_FOUND`，不得以 `403` 区分。

资源 `content` 的 schema 校验是纯函数（§4.4），在业务事务外先做；配额必须在锁内按订阅快照计量，因此上述「配额 -> schema 校验」仅描述授权门与业务门的相对次序，不表示配额先于 schema 求值。

Phase 1 的组织订阅永久 active，因此不实现、不验收订阅到期只读降级；`expired/canceled` 只是为商业专项预留的状态值，其冻结语义由该专项冻结。

关闭组织在单一事务内把 organization 置 closed、写 `closed_time`、撤销全部有效邀请并把对应 invited membership 置 removed；已 active 的 membership、目录和资源保留原状，不做级联删除。关闭不可撤销，Phase 1 不提供恢复路由。

### 5.1 Phase 1 请求 DTO

所有 ID 在 DTO 中为十进制字符串。请求体必须严格闭合，出现未知字段即拒绝。

```ts
type RegisterRequest = { email: string; password: string; displayName?: string };
type LoginRequest = DeviceFields & { email: string; password: string };
type RefreshRequest = DeviceFields & { refreshToken: string };
type ChangePasswordRequest = { currentPassword: string; newPassword: string };
type CreateOrganizationRequest = { name: string };
type UpdateOrganizationRequest = { name: string };
type CreateInvitationRequest = { email: string; role?: OrganizationRole };
type AssignRoleRequest = { role: OrganizationRole };
type CreateFolderRequest = { name: string; parentId?: string | null };
type UpdateFolderRequest = { name?: string; parentId?: string | null };
type CreateResourceRequest = {
  resourceType: 'connection_template' | 'query';
  name: string;
  folderId?: string | null;
  content: object;
};
type UpdateResourceRequest = {
  baseVersion: number;
  name?: string;
  folderId?: string | null;
  content?: object;
};
```

长度与空白约束：`email` 最长 255 并规范化为小写；`password`/`newPassword` 为 12..128 个 Unicode code points；`displayName` 1..100；组织 `name` 1..100；目录与资源 `name` 1..200；上述名称去除首尾空白后不得为空。`UpdateFolderRequest` 与 `UpdateResourceRequest` 至少含一个可变字段。`content` 按 4.4 节闭合 schema 校验。`DeviceFields` 见 4.6 节。

`GET /api/organizations/:organizationId/members` 只返回 `{membershipId,displayName,role,status,joinedTime}`。Phase 1 不向任何组织成员返回其他成员的 email，邀请列表只对 `member.invite` 持有者返回被邀请 email。

统一错误：`400 VALIDATION_FAILED`、`401 UNAUTHORIZED`、`403 USER_DISABLED`、`403 PERSONAL_FEATURE_REQUIRED`、`404 ORGANIZATION_NOT_FOUND`、`403 FORBIDDEN`、`404 RESOURCE_NOT_FOUND`、`403 ORGANIZATION_FEATURE_REQUIRED`、`400 RESOURCE_CONTENT_INVALID`、`409 ORGANIZATION_QUOTA_EXCEEDED`、`409 RESOURCE_VERSION_CONFLICT`、`409 FOLDER_NOT_EMPTY`、`409 FOLDER_MOVE_CYCLE`、`409 ORGANIZATION_ADMIN_REQUIRED`、`400 INVITATION_INVALID`、`400 INVITATION_TARGET_NOT_ELIGIBLE`、`429 TOO_MANY_REQUESTS`。`400 VALIDATION_FAILED` 用于结构、长度、枚举和空白校验；`400 RESOURCE_CONTENT_INVALID` 用于资源 `content` 违反 4.4 节闭合 schema；不允许的模板引擎返回 `403 ORGANIZATION_FEATURE_REQUIRED`。跨组织作用域的实体 id 在目标组织内不存在或不属于该组织时，membership、invitation、folder 一律返回 `404 NOT_FOUND`，resource 返回 `404 RESOURCE_NOT_FOUND`（§9.1 的 ACL 语义依赖此码；两者同为 404，均不区分不存在与无权访问，防枚举）；仅当 id 属于本组织但状态非法（如邀请已接受/已撤销/已过期）时才返回 `400 INVITATION_INVALID`。

注册对已存在邮箱不返回冲突：服务端返回与新注册相同的成功响应，不创建重复用户，也不改动既有账号，只向该地址发送一封说明该邮箱已注册的邮件，以避免账号枚举。因此 Phase 1 不使用 `409 EMAIL_ALREADY_IN_USE`；邮箱变更冲突语义由账号生命周期专项冻结。错误不得回显 SQL、token、密码、私钥、E2E 内容或未授权资源存在性。

## 6. Phase 1 包级实施与验收

### 6.1 Server

重建 MySQL migration、domain、repository、policy、service、middleware、route 与测试。删除 V2 mixed plan/subscription/order、personal organization、跨组织个人权益计算、直接 `{userId,role}` 激活成员、组织资源写入个人 sync、V2 route fallback 和双写。统一权限 middleware 必须使用本文件的静态权限目录，不得在业务处理器中散落 admin/member 判断。

### 6.2 VS Code Extension

Personal 与 Organization Workspace 使用独立数据源。个人连接树、Connection Group 与 SecretStorage 始终留在 Personal；组织资源不写入个人连接持久化。个人 E2E sync 不属于 Phase 1。组织模板通过 `organizationId + resourceId` 映射用户自己的本地凭据，映射不上传。组织缓存只在内存中、按 `userId + organizationId` 分区；`401` 清认证，`403/404` 清无权/失效资源，`409` 保留本地编辑供冲突处理。成员角色或状态变更、退出、移除或关闭后立即重新拉取权限或清空缓存。

Phase 1 的 Organization Workspace 不提供权限映射或角色管理 UI。具有 `member.role.assign` 的 admin 可在邀请或成员编辑中选择 admin/member，其他邀请固定为 member。动态权限映射 UI 仅在相应专项模块通过服务端契约、失效与并发测试后实现。

### 6.3 Admin UI

Phase 1 不实现 Platform Admin、支付、seat、审计、ACL、账号生命周期或 suspend/resume 页面、命令和空请求。仅在将来阶段按服务端 `/api/admin` 返回的脱敏数据构建运营界面；浏览器不计算组织或平台权限，不能读取 E2E 内容、个人/本地凭据或组织资源内容。

### 6.4 必需验收

1. 注册只创建个人 Free，不创建 personal organization；成员状态或组织权限不改变个人权益。
2. 并发邀请、接受、撤销、过期、移除、退出不能超过 `seat_limit`；邀请 hash、邮箱匹配和反枚举错误正确。
3. 固定角色权限立即在服务端生效；admin 始终拥有 Phase 1 全部组织权限，member 仅拥有固定只读权限。不能删除或降级最后 active admin，违规返回 `409 ORGANIZATION_ADMIN_REQUIRED`。
4. 跨组织 resource/folder/membership ID 不可访问；非 active member 与不存在或 closed 组织均返回 `404 ORGANIZATION_NOT_FOUND`；资源和目录 API 逐项按静态 permission code 拒绝。
5. 组织模板只接受 MySQL 与无秘密 schema；个人 Free 只允许 MySQL/SQLite；组织资源不包含个人连接或本地凭据映射。
6. 配额、资源版本冲突、永久 Free 订阅、组织关闭副作用和缓存失效均按本规格工作；Phase 1 不实现订阅到期只读降级。
7. Argon2id 参数、Ed25519 签名密钥选择、access/refresh token 生命周期、refresh rotation/reuse、device upsert 与撤销、改密全量撤销和跨实例共享限流均按 4.5、4.6 节工作。
8. 邮箱验证与邀请 token 的 24 小时/7 天有效期、单次消费、旧 token 作废、发送失败不回滚和可重发路径均按 4.7 节工作；过期邀请经懒判定和清理任务释放容量。
9. 注册重复邮箱返回与新注册一致的响应且不改动既有账号；成员目录不泄漏其他成员 email；非法请求体、非法 content 和不允许引擎分别返回 `400 VALIDATION_FAILED`、`400 RESOURCE_CONTENT_INVALID`、`403 ORGANIZATION_FEATURE_REQUIRED`。
10. 运行 server 单元/集成测试、extension 测试、typecheck、lint、build、Phase 1 route smoke test、`git diff --check`；route smoke 只覆盖本节路由集合，不含 ACL、资源历史、支付或 Platform Admin。

### 8.1 已冻结：个人 E2E 同步 V1

本节是「个人 E2E 同步」专项的**冻结契约**（设计冻结，实施准入复核已通过，逐切片 S1–S5 实施中：S1–S4 已合并、S5 待合并）。冻结范围不含组织资源、组织权限、Platform Admin、支付、账号删除或 V2 fallback。红线：**服务端零明文、零可派生密钥**；同步主密码（SMP）、恢复码、DEK、KEK 与所有签名私钥永不离开客户端，服务端只存密文、envelope 元数据与公开签名材料。

**8.1.1 定案**
- 同步能力对 Free 开放，不新增权限码（authenticated personal capability）。
- `max_connection_metas=500`、`sync_storage_bytes=33554432`（32 MiB）、单 record encrypted blob ≤256 KiB；三者均为 plan 级数值配额，`0=unlimited` 语义（V1 Free 实际值固定为 500 / 33554432）。
- payload = 完整个人连接配置，可含数据库密码、SSH 密码、SSH 私钥口令；**不含** SQLite 本地路径、SSH 私钥文件路径/**内容**、任何本机路径、OS keychain 引用、组织资源引用或组织凭据映射（V3 相对 V2「excluding passwords」的语义变更）。

**8.1.2 密钥与签名层级（per-keyEpoch）**
- DEK：32B CSPRNG，随 keyEpoch 轮换。
- `syncSignPriv = Ed25519(HKDF-SHA-256(ikm=DEK, salt=空 0 长, info=UTF-8("dbclient/sync/v1/signing"), L=32))`；32B 作 Ed25519 seed、按 RFC8032 派生，公私钥对。`syncSignPub` 存服务端。
- `recoverSignPriv = Ed25519(HKDF-SHA-256(ikm=恢复码 256bit, salt=空, info=UTF-8("dbclient/sync/v1/recover-signing"), L=32))`；`recoverSignPub` 存服务端，随恢复码轮换。
- `KEK_smp = Argon2id(SMP, smpKdf.salt)`（memory 65536‥262144 KiB、iterations 3‥10、parallelism 1‥4、salt=16B、output=32B）。`KEK_recovery = HKDF-SHA-256(ikm=恢复码 256bit, salt=recoveryKdf.salt, info=UTF-8("dbclient/sync/v1/kek/recovery"), L=32)`。逐 record 的 AEAD 密钥即 `recordAeadKey = DEK` 本体：`AES-256-GCM(key=DEK, nonce, AAD)`；同一 DEK 下由 `personal_sync_nonces` 永久防 nonce 复用。
- **envelope 每版专用 AEAD key**：`HKDF-SHA-256(ikm=KEK_purpose, salt=空, info=UTF-8("dbclient/sync/v1/envelope/"+keyEpoch+"/"+purpose+"/"+envelopeVersion), L=32)`；每个 envelope 用自己的 `envelopeVersion`，12B 随机 nonce 在其派生 key 下只用一次。AEAD = AES-256-GCM，nonce 12B、tag 16B（显式字段，不拼进 ciphertext）。
- **envelope 版本单调规则**：init/destroy/reset 的两个 envelope 版本均从 1 起；change-key 要求 `envelopeSmp.envelopeVersion = 存量 smp 版本 + 1`（recovery envelope 的字段与版本不变）；recover 要求两个提交的 envelope 版本各自 = 其存量版本 + 1；其它任何版本 → `400 VALIDATION_FAILED`。服务端持久化两个当前 envelope 版本，绝不接受同一 (purpose, version, nonce) 组合重复。
- 日志/metrics/错误不得出现 request body、canonicalBody、AAD、密文、nonce、recordId、mutationId、SMP、恢复码、token、邮件或解密错误细节。

**8.1.3 密钥轮换矩阵**
| 动作 | DEK/syncSignKey | 恢复码/recoverSignKey | keyEpoch | stateVersion | record 密文 |
|---|---|---|---|---|---|
| init | 新 | 新 | 1 | 1 | — |
| change-key | 不变 | 不变 | 不变 | +1 | 不变 |
| recover | 不变 | **轮换** | 不变 | +1 | 不变 |
| destroy（DEK 签名） | **新** | **新** | +1 | 1 | 全 tombstone |
| reset-after-loss（邮箱挑战） | **新** | **新** | +1 | 1 | 全 tombstone(abandon) |

**8.1.4 状态 / epoch / 变更序列**
- `personal_sync_state` **严格单行**（PK=user_id，无 (user_id,key_epoch) 复合）。`stateVersion` **每个 epoch 从 1 起**：init 建 (keyEpoch=1, stateVersion=1)；change-key/recover 于本 epoch 内 +1；destroy/reset 建 (keyEpoch+1, stateVersion=1)。签名/乐观锁/stale 判定始终同时绑定 `keyEpoch + stateVersion`。
- `change_sequence` 是用户级全局单调序列，**永不随 keyEpoch 重置**；每个 create/update/delete 在同 tx 内锁 state、`change_sequence+1`、写一条 record/tombstone（一个序列恰对应一条变更，禁止批量复用）。
- 所有 record GET/create/update/delete 与 change-key/recover/destroy：先锁读 active state，`request.keyEpoch !== activeState.keyEpoch` → `409 SYNC_EPOCH_STALE {currentKeyEpoch}`；pull 只返回 active epoch。
- destroy/reset 同 tx 完成「旧 epoch records 全 tombstone + state epoch 递增 + 新 epoch state 建立」，外部不可见无 active epoch 窗口；独立 `init` 仅当无 state（重复→`409 SYNC_STATE_EXISTS`）。reset-after-loss 在无 active state 时等价建 `keyEpoch=1` 新 epoch（不返回 `SYNC_NOT_INITIALIZED`）。

**8.1.5 数据模型（新增，forward-only）**
| 表 | 关键列/约束 |
|---|---|
| `personal_sync_state` | user_id PK、key_epoch、state_version、change_sequence、protocol/cipher/format、`smp_kdf_json`、`recovery_kdf_json`、envelope_smp/recovery 各 `(version, nonce, ct, tag)`、sign_pub/recover_sign_pub BINARY(32)、recovery_code_set_time |
| `personal_connection_meta` | (user_id, key_epoch, record_id) UNIQUE；record_id VARCHAR 无语义随机 base64url 1‥128B；cipher_suite、format_version、nonce BINARY(12)、ciphertext LONGBLOB、tag BINARY(16)、version(单调=写入后版本)、change_sequence、update_time、delete_time。tombstone：delete_time 非空、**清空 ciphertext/tag**，保留 record_id/nonce/version/change_sequence |
| `personal_sync_nonces` | PRIMARY KEY(user_id, key_epoch, nonce)；永久留存至 destroy/账号生命周期；每次 create/update 先 INSERT nonce，冲突→`409 SYNC_NONCE_REUSED` |
| `personal_sync_mutations` | UNIQUE(user_id, key_epoch, mutation_id)；存 request_digest、action、epoch、result_version、`result_change_sequence`、status、expires_time(24h)。仅保留期，不存 body/AAD/密文/nonce/recordId |
| `personal_sync_reset_tokens` | token_hash BINARY(32) UNIQUE、expires_time、consumed_time、**revoked_time** |

**8.1.7 请求 DTO（`additionalProperties:false`；二进制一律 base64url 无 padding）**
| 编码 | 意义 |
|---|---|
| Base64Url22 | 16 raw bytes（mutationId / tag） |
| Base64Url43 | 32 raw bytes（DEK / 公钥 / reset token） |
| Base64Url86 | 64 raw bytes（Ed25519 签名） |
| NonceB64 | 12 raw bytes（16 字符） |

```ts
type Decimal = string; // BIGINT 十进制；sequence ∈ [0, 2^64-1]
type SignedMutation = {
  protocolVersion: 1; keyEpoch: Decimal; mutationId: Base64Url22; signature: Base64Url86;
};
type Envelope = {
  protocolVersion: 1; cipherSuite: 'AES-256-GCM'; formatVersion: 1;
  envelopeVersion: Decimal; nonce: NonceB64; ciphertext: Base64Url43; tag: Base64Url22;
};
type SmpKdf = { alg: 'argon2id'; version: 1; memoryKiB: number; iterations: number; parallelism: number; salt: Base64Url22; outputBytes: 32 };
type RecoveryKdf = { alg: 'hkdf-sha256'; version: 1; salt: Base64Url22; outputBytes: 32 };
type NewState = {
  protocolVersion: 1; cipherSuite: 'AES-256-GCM'; formatVersion: 1;
  smpKdf: SmpKdf; recoveryKdf: RecoveryKdf;
  envelopeSmp: Envelope; envelopeRecovery: Envelope;
  signPub: Base64Url43; recoverSignPub: Base64Url43;
};
type InitRequest = { newState: NewState };                       // 先行先得；无签名
type PutRecordRequest = SignedMutation & { recordId: string; baseVersion: Decimal;
  cipherSuite: 'AES-256-GCM'; formatVersion: 1; nonce: NonceB64; ciphertext: string; tag: Base64Url22 };
type DeleteRecordRequest = SignedMutation & { recordId: string; baseVersion: Decimal };
type ChangeKeyRequest = SignedMutation & { expectedStateVersion: Decimal; smpKdf: SmpKdf; envelopeSmp: Envelope };
type RecoverRequest = SignedMutation & { expectedStateVersion: Decimal;
  smpKdf: SmpKdf; envelopeSmp: Envelope; recoveryKdf: RecoveryKdf; envelopeRecovery: Envelope; recoverSignPub: Base64Url43 };
type DestroyRequest = SignedMutation & { expectedStateVersion: Decimal; newState: NewState };
type ResetAfterLossRequest = { protocolVersion: 1; resetToken: Base64Url43;
  confirmIrreversible: true; confirmDataLoss: true; confirmNoRecovery: true; newState: NewState };
```

```ts
  mutationId: Base64Url22; requestDigest: Base64Url43 };
```
- `signature = Ed25519.sign(UTF8(RFC8785.canonicalize(signingInput)))`；`requestDigest = SHA-256(JCS(body 除 signature))`；`action` 由服务端按 method/path 决定，不信任 body 声称；每 action 允许字段集固定（record mutation 必含 recordId+baseVersion，state mutation 必含 expectedStateVersion）。
- create `baseVersion="0"`（record 必须不存在）→ 写入 version=1；update/delete 用当前 version → 写入 version=baseVersion+1。**record AAD 的 recordVersion = 写入后版本**（客户端加密前即知）。baseVersion 须可解析为 u64 十进制，否则 `400 VALIDATION_FAILED`。对 tombstone record 再次 create/update/delete 统一 `409 SYNC_VERSION_CONFLICT`（`currentVersion`=tombstone 版本）；同 epoch 从未存在的 record → `404 NOT_FOUND`。
- record AAD = `{userId, keyEpoch, recordId, recordVersion(写入后), protocolVersion, cipherSuite, formatVersion, purpose}`；envelope AAD = `{userId, keyEpoch, envelopeVersion, protocolVersion, cipherSuite, formatVersion, purpose}`。
- mutation receipt：同 (userId,keyEpoch,mutationId) 同 requestDigest 命中→版本比较前返回原成功（含 version+change_sequence）；同 id 异 digest→`409 CONFLICT`；24h 仅为保留期，过期后靠 record version 乐观锁 + `UNIQUE(user_id,key_epoch,record_id)` 兜底防重，绝不绕过版本/签名/nonce 校验。

**8.1.9 变更 feed 游标**
- `GET /api/sync/records?after=<seq>&limit=<1..256>&snapshotSequence=<固定>`：首页 `after=0` 或省略，锁 active state 后取 `snapshotSequence=change_sequence`；后续页 `snapshotSequence` 严格等于首次值，服务端约束 `change_sequence > after AND change_sequence <= snapshotSequence`。limit∈[1,256]；条目边界截断（下一条会使总密文超 2 MiB 则返回已取 + `nextAfter`=末条 change_sequence）。
- `syncStorageBytes` = active record `raw ciphertext + 16B tag + 12B nonce` 之和；envelope 与 tombstone 不计。

**8.1.10 reset-after-loss 挑战协议**
- `POST /api/sync/reset-challenges`（认证）：向已验证邮箱发挑战，不回传 token；对 active/none/abandoned 恒 `202` 同形防枚举。token=256-bit CSPRNG、DB 只存 SHA-256、24h、单次消费、重发 Set `revoked_time`；用户+源 IP 各 3/时→`429 TOO_MANY_REQUESTS`。**事务 commit 后发送**，发送失败不回滚（用户重发）；生产走既有 EmailSender，开发/测试不得发真实地址。
- `POST /api/sync/reset-after-loss`（认证）：body 含 resetToken + 三个固定 `true` 确认 + newState；单 tx 验证→消费 token→旧 epoch+records 标 abandon→建新 epoch active。对不存在/过期/已消费/他用户 token 恒同 `400` code+body。reset 扩大的是可用性 DoS 面（账户+邮箱皆被控可毁数据），非机密性面（旧密文仍不可读）。

**8.1.11 错误码（增补）**
| code | 触发 |
|---|---|
| `400 SYNC_NOT_INITIALIZED` | 无 active state 的读写（与从未注册同形） |
| `400 SYNC_PROTOCOL_UNSUPPORTED` | 请求 protocol/cipher/format 不在支持集（含 >max/<min）|
| `400 VALIDATION_FAILED` | 结构/长度/枚举/非法 cursor/单 record >256 KiB（协议长度）/baseVersion 非 u64/缺 output 长度/非 16B salt/SMP 用 hkdf |
| `403 SYNC_SIGNATURE_INVALID` | 签名验证失败（未证持钥=无权） |
| `409 SYNC_STATE_EXISTS` | 重复 init |
| `409 SYNC_EPOCH_STALE` | 请求 keyEpoch ≠ active keyEpoch | body `{currentKeyEpoch}` |
| `409 SYNC_VERSION_CONFLICT` | baseVersion ≠ 当前 version（含重放）| body `{currentVersion}` |
| `409 SYNC_NONCE_REUSED` | (user_id,key_epoch) 下 nonce 复用 |
| `409 SYNC_QUOTA_EXCEEDED` | count 或 bytes 超限 | body `{code, quota:'count'|'bytes', limit, used}`，`used`=当前已用量（写入前 count/bytes） |
| `409 CONFLICT` | 同 mutationId 异 digest |
| `429 TOO_MANY_REQUESTS` / `401` / `403 USER_DISABLED` / `404 NOT_FOUND` | 复用 Phase 1 |

**8.1.12 迁移与回滚（forward-only）**
- MySQL DDL 隐式提交，不可靠「回滚本事务」：migration 运行前备份并记录已成功执行的 migration ID；各 migration 独立顺序执行；DDL 或 snapshot backfill 失败即停部署、不启依赖新 schema 的应用版本；已完成 DDL 不回滚，由审查通过的前向 repair migration 修复。
- 顺序：①`ALTER personal_plans` 新增两列 + Free seed；②`personal_sync_state`；③`personal_connection_meta`；④`personal_sync_nonces`；⑤`personal_sync_mutations`；⑥`personal_sync_reset_tokens`；⑦`JSON_SET` 回填既有 subscription snapshot。
- 写入任何 sync state/record 后，禁止 down migration、`DROP TABLE`、移除 plan 配额列；回退仅能部署兼容旧版本或再前向修复。migration/seed smoke 须在空 MySQL 8 与已存在 Phase 1 数据两种库各跑一次。
- V1 无后台任务：无 token/tombstone/物理删除清理；过期 reset token 读取时懒判定；tombstone 与 nonce ledger 永久保留至 destroy 或账号生命周期专项接管。

组织 checkout 的目标 `seat_limit` 固定为 target plan 的 `included_seats`，金额为该周期的 plan base price。组织 change 计算 `targetSeatLimit=currentSeatLimit+seatDelta`，要求目标不低于 target plan `included_seats`、不低于 invited/active 占用且不等于当前值；`seatDelta<0` 必须不带 provider，立即降低 `seat_limit`、不创建订单且不退款。plan 变更或 `seatDelta>0` 必须创建支付订单；其金额为目标 plan 对应周期 base price 加 `max(0,targetSeatLimit-included_seats)` 个对应周期 seat price，支付成功后立即以目标 plan/seat limit 开启新的完整计费周期。该规则刻意不按剩余天数折算、不提供信用额度或部分退款；失败/取消不改变当前订阅。个人 checkout/change 同样以支付成功时开始新的完整周期。套餐目录只影响未来 checkout/renewal；创建、续费或显式 change 时复制价格、额度和引擎权益到 snapshot。目录编辑绝不追溯修改既有订单、当期权益或金额。取消在周期末生效，到期降级，已确认全额退款立即降级；首版不支持部分退款、信用额度、订阅期内价格调整或 Trial。关闭组织停止自动续费、seat 全部 revoked、不自动退款且不可恢复；后续 webhook 只能补全订单，不能恢复组织、订阅或 seat。

监控只保存聚合指标，Platform Admin 可读取平台和指定组织的聚合，组织 admin 只能凭固定 `monitoring.read` 读取本组织聚合。允许的 `metric_code` 只能是 `request.count`、`request.latency`、`request.error`、`organization.member_count`、`organization.seat_used`、`organization.resource_count`、`organization.resource_bytes`、`organization.invitation_count`、`authorization.denied`、`resource.version_conflict`、`payment.order_count`、`payment.refund_count`、`webhook.event_count`、`webhook.backlog`、`deletion.sla_overdue`、`encryption.key_rotation`、`encryption.failure`、`health.check`；不得自由写入其他代码。`request.*`、`health.check`、payment/webhook/deletion/encryption 指标仅 platform scope；`organization.*`、`authorization.denied` 和 `resource.version_conflict` 仅 organization scope。`dimensions` 只允许 route ID、status class、latency bucket、provider、event status 和固定错误 code；不得保存请求体、Authorization、token、密码、同步/资源正文、私有连接元数据、资源 ID、用户 email 或明文 IP。限流排障如必须保留 IP，只能以轮换盐 HMAC 的 `ip_hash` 短期内存保存，不能进入 rollup。minute 实时诊断可进程内保留最多 60 分钟；hour/day rollup、订单和审计均保留 1 年，并由受控清理任务在保留期后删除聚合桶。

从 Phase 1 迁移 seat 时，锁定 subscription 与所有 invited/active memberships，断言占用不超过 `seat_limit`，创建 `seat_limit` 行：稳定排序 active membership 后分配 assigned、再为 invited 分配 reserved、其余 available。非 revoked 行数必须等于 `seat_limit`；任何不变量失败中止并人工修复。之后创建邀请 `available -> reserved`，接受 `reserved -> assigned`，撤销/过期 `reserved -> available`，移除/退出 `assigned -> available`。减席仅在 available 行足够时允许，否则 `409 ORGANIZATION_SEAT_IN_USE`；不得强制移除成员。

每个 checkout/change 命令先提交 `pending_payment` 内部订单、不可预测的 `merchantOrderNo` 和冻结的 plan snapshot，再调用已启用 provider 创建外部支付意图；adapter 必须将 `merchantOrderNo` 作为渠道侧幂等商户单号。确定未创建外部意图时可将内部订单置 `failed`；网络超时或未知结果必须保留 pending 并用相同 `merchantOrderNo` 重试，绝不另建订单。`merchantOrderNo` 使用全局命名空间：personal 订单前缀 `p_`、organization 订单前缀 `o_`，退款保留相同主体前缀；两张订单表的生成器不得重复。成功响应固定为 `{orderId,merchantOrderNo,provider,amountMinor,currency:'CNY',expiresAt,checkout}`：`orderId` 和 `merchantOrderNo` 为字符串，`checkout` 只含客户端启动该渠道支付所需的 provider 白名单字段（二维码 URL、跳转 URL或签名参数），manual 为 `null`。支付商 callback 必须按前缀以 `merchantOrderNo` 锁定内部订单、把支付商交易号写入订单，并在同一事务插入 `payment_provider_transactions`；其唯一键是跨 personal/organization 订单的 provider transaction 防重放边界，冲突返回 `409 PAYMENT_STATE_CONFLICT`。未经验证的 callback、未知订单、金额/币种/snapshot 不匹配均不得创建或更新权益。用户命令以规范化的 plan、周期、seat delta、provider 和 CNY 币种计算 `request_digest`：同主体同 key 同摘要返回原订单，不同摘要返回 `409 IDEMPOTENCY_KEY_REUSED`。仅微信支付和支付宝 webhook 先验签，再原子创建或认领 `(provider,event_key)`；只有 pending、租约过期 processing 或到达 next retry 的 retryable failed 可处理。按 provider sequence，或无 sequence 时按 provider event time，拒绝旧状态覆盖新状态。手动支付只能由 Platform Admin 的 manual-confirmation 路由推进状态，且不得使用 webhook_events。成功才标记 processed；可恢复失败写 retryable failed；不可恢复失败写 terminal failed。未知订单、验签失败、金额/币种/快照不匹配不得改权益，错误为 `400 PAYMENT_EVENT_INVALID` 或 `409 PAYMENT_STATE_CONFLICT`。

原支付订单只能按 `pending_payment -> paid|canceled|failed`、`paid -> refunded` 迁移；退款命令仅从 paid 原订单创建金额与 currency 相同的关联 `kind=refund,status=refund_pending` 订单。微信/支付宝退款确认 webhook 或 manual-refund-confirmation 只允许 `refund_pending -> refunded|refund_failed`，并在 `refunded` 时原子将原订单置 refunded、立即降级相关个人/组织权益。重复 paid/refunded 事件按幂等成功返回，其他回退或跳转返回 `409 PAYMENT_STATE_CONFLICT`；任何主体最多存在一个未终结退款订单。仅从 `pending_payment` 到 `paid` 的原子事务可以写订阅权益、seat 或个人 Pro。Phase 2 的 VS Code Extension 只显示调用者可见的个人/组织订阅、seat、组织审计和组织监控摘要；Phase 2 的 Platform Admin UI 只显示脱敏的用户/组织、订阅、订单、Webhook、审计和聚合监控数据，并支持商业目录、渠道启停/引用、Platform Admin 管理、session/device 撤销、手动收款与手动退款确认。Admin UI 不得读取组织资源内容、个人同步内容、私有连接元数据、凭据或密钥。

### 候选模块：受限协作

候选前提（未冻结）：Phase 1 的组织资源与成员身份可用，且第 8 节关于版本配额归属与 ACL 可见性的未决项已有结论。候选方案中资源增加 `access_scope VARCHAR(16) NOT NULL DEFAULT 'organization' CHECK(organization,restricted)`，既有资源回填 organization。新增 permissions（`organization_id`、`resource_id`、`membership_id`、`permission CHECK(read,write)`、`UNIQUE(resource_id,membership_id)`、同组织复合外键）与 versions（`organization_id`、`resource_id`、`version`、`content JSON`、`created_by_membership_id`、时间、`UNIQUE(resource_id,version)`、同组织复合 FK）。Phase 3 migration 必须为每个未删除资源插入其当前 `{version,content,updated_by_membership_id,update_time}` 的 immutable baseline snapshot；若同一 `{resource_id,version}` 已存在则校验内容 hash 一致后跳过，否则中止 migration。资源当前内容仍以 `organization_resources` 为权威，versions 保存 immutable baseline 与更新前的历史 snapshot；baseline 在首次迁移时可以与 current 相同。组织资源版本默认长期保留：在新的、经审计的保留策略明确生效前，禁止自动删除任何版本或仅为节省空间截断历史。

资源 ACL 只授予 active member `read/write`，不能授予组织管理或个人数据访问。目录不是 ACL 主体；列表和目录 SQL 必须过滤不可见资源，祖先目录仅在含可见资源时返回。转 organization 时删除 ACL，转 restricted 时普通 Member 默认无权。Member write 仅可更新获授权 restricted resource 的 content 和必要显示字段，不可移动、删除、改 scope/type、管理 ACL 或回滚。每次更新先将旧 content 写 versions，再条件更新资源；冲突不写版本。`GET versions` 返回 `{currentVersion,versions}`，其中 `versions` 包含 immutable baseline 和 historical snapshot；版本等于 `currentVersion` 的 baseline 只作来源留档，不能作为 rollback source，其他 `sourceVersion` 必须引用 historical snapshot。回滚读取 `{sourceVersion,baseVersion}`，将回滚前当前内容写版本，再以新 version 复制目标版本内容。

| Method | Path | 所需权限 | 说明 |
|---|---|---|---|
| `GET` | `/api/organizations/:organizationId/resources/:resourceId/permissions` | `resource.permission.manage` | 列 restricted ACL。 |
| `PUT/DELETE` | `/api/organizations/:organizationId/resources/:resourceId/permissions/:membershipId` | `resource.permission.manage` | `{permission:'read' \| 'write'}` 或删除 ACL。 |
| `GET` | `/api/organizations/:organizationId/resources/:resourceId/versions` | `resource.version.read` | 分页版本元数据。 |
| `POST` | `/api/organizations/:organizationId/resources/:resourceId/rollback` | `resource.rollback` | `{sourceVersion,baseVersion}` 创建新版本。 |

错误：非 restricted 资源读写 ACL 返回 `409 RESOURCE_PERMISSION_SCOPE_INVALID`；已授权者请求不存在版本返回 `400 RESOURCE_VERSION_NOT_FOUND`；无读取权限始终为 `404 RESOURCE_NOT_FOUND`。

### 候选模块：合规运营

候选前提（未冻结）：审计与资源版本模块可用，第 8 节关于密钥职责隔离、`content` 过渡和账号删除策略的未决项已有结论，且已完成加密故障模式、密钥轮换与恢复演练。候选方案中 organizations 增加 `suspended_time NULL`、`suspension_reason VARCHAR(64) NULL`、`suspended_by_user_id NULL`，status 扩展为 `active/suspended/closed`。suspended 与订阅冻结独立：普通组织 API 对 suspended/closed 返回 `404 ORGANIZATION_NOT_FOUND`，不得由付款失败自动置 suspended。Platform Admin suspend/resume 写 `admin_audit_log`；resume 仅恢复 active，不恢复过期订阅或已撤销 membership。

新增 `organization_encryption_keys`：`organization_id BIGINT UNSIGNED`、`key_version SMALLINT UNSIGNED`、`wrapped_data_key MEDIUMBLOB`、`wrap_algorithm VARCHAR(32)`、`status CHECK(active,retired,destroyed)`、`retired_time NULL`、`destroyed_time NULL`、`UNIQUE(organization_id,key_version)`；FK -> organizations。服务层必须在同一事务内保证每个组织至多一把 active key。新增 `account_deletion_requests`：`user_id BIGINT UNSIGNED UNIQUE`、`status CHECK(requested,processing,completed,blocked)`、`requested_time`、`due_time`、`completed_time NULL`、`blocked_reason NULL`；FK -> users。创建请求时写入 `due_time=requested_time + 30 days`；后台受控任务必须在 SLA 内完成或标记 blocked 并保留可审计原因。

users 增加 `pending_email NULL`、`pending_email_requested_time NULL`；email verification token 增加 `purpose CHECK(initial,email_change)`。`PATCH /api/me/email` 写 pending email、作废旧 email-change token 并发新 token；既有 `POST /api/auth/email-verifications/:token/confirm` 按 purpose 消费。email-change token 在事务内重新检查 email 唯一性和 pending 值后原子替换 email；用途、地址、过期或已消费不符返回 `400 EMAIL_CHANGE_TOKEN_INVALID`，目标已占用为 `409 EMAIL_ALREADY_IN_USE`。

`POST /api/me/deletion-request` 为受控异步命令。若删除会使组织不存在 active admin，返回 `409 ORGANIZATION_ADMIN_REQUIRED`；若请求人是最后一名 active Platform Admin，返回 `409 PLATFORM_ADMIN_REQUIRED`；两种情形均不创建请求。否则禁用用户、撤销 refresh token、删除个人 sync/meta、将 memberships removed 并释放 Phase 2 seat/Phase 3 ACL。保留与匿名化依法律策略，未确认前不得承诺立即物理删除。

组织资源和历史版本增加 `encrypted_content MEDIUMTEXT`、`key_version SMALLINT`、`format_version SMALLINT`。`V3_MASTER_KEY` 必须是部署环境提供的 32-byte base64 密钥；根密钥及数据密钥均使用 AES-256-GCM，随机 96-bit IV 和认证 tag 与密文共同编码在 versioned envelope 中。服务端仅从 `V3_MASTER_KEY` 取得根密钥；每个组织的数据密钥及版本必须按 `organization_encryption_keys` 被根密钥包装后保存到数据库，根密钥绝不入库。资源使用数据密钥认证加密，并将 organization/resource/format 作为附加认证数据。迁移按资源原子校验、加密、可解密验证后才移除明文；轮换在同时可读新旧 key 时批量重加密。由于版本默认长期保留，旧数据密钥在默认策略下只能标记 retired，不得 destroyed；只有经审计的版本清理完成且确认资源、版本和保留记录均无旧 key 引用后才可标记 destroyed。密钥不可用返回 `503 ORGANIZATION_ENCRYPTION_UNAVAILABLE`，绝不明文降级。

| `POST` | `/api/admin/organizations/:organizationId/suspend` | Platform Admin | `{reason}` 暂停并写 admin audit。 |
| `POST` | `/api/admin/organizations/:organizationId/resume` | Platform Admin | 可选 `{note}`，恢复 active。 |
| `PATCH` | `/api/me/email` | authenticated | `{email}` 创建 email-change token。 |
| `POST` | `/api/me/deletion-request` | authenticated | 提交受控注销。 |
