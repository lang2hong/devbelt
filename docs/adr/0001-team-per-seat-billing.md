# ADR-0001：Team 套餐采用 per-seat 席位计费的团队模型

- 状态：Accepted
- 日期：2026-08-25

## 背景（Context）

当前 `Team` 套餐在命名、feature 位与计费语义上自相矛盾，显得「不伦不类」：

1. **数据模型是个人订阅**：`users.plan_code` + 单条 `subscriptions` 记录，一份订阅对应一个账号，所有配额（500 连接 / 20 设备 / 1GB）都绑定在单个用户上。
2. **命名与 feature 位暗示团队**：套餐名叫 "Team"，且占着 `team_share` feature 位（`Feature.team_share = 1 << 4`），但该 feature 从未落地，没有任何组织/成员/协作能力。
3. **计费语义模糊**：`plans.price_month = 20` 是「一个账号的整体月费」，既不是每人（per-seat）也不是每组织（per-org）。用户拿 20 元买到的「团队」，实际只能一个账号使用，无法解释清楚。

这三处相互冲撞，导致产品定位失真：要么名字是虚的，要么价格是虚的，要么 feature 位是空的。

## 决策（Decision）

**Team 套餐长期方向改为：真·团队模型，按席位（per-seat）计费。**

1. 引入组织（organization）与成员（membership）模型，一个组织下挂多个用户。
2. 计费按席位：原「¥20/月整体」改为「基础价 + 每席位 ¥X/月」或纯「¥X/席位/月」，以产品定价为准（见开放问题）。
3. 落地 `team_share` feature：团队共享连接、协作与成员管理、审计能力随之纳入同一期规划。
4. 配额归属重新定义：连接/设备/存储等额度由「组织总量 + 每席位明细」共同作用，取代当前「全绑个人」的语义。
5. 商业 Owner 的唯一权威是 `organizations.owner_user_id`；`memberships.role` 仅表达 `admin` / `member`，不再另设 owner 角色。
6. 私人资源按用户与有效席位计量；同一用户的私人配额取所有有效席位套餐中的最高值，不叠加。共享资源按组织计量。
7. 首期共享资源由服务端授权和服务端静态加密保护；禁止把数据库密码、SSH 密码和 SSH 私钥写入共享资源。
8. Greenfield 部署：不迁移存量用户、订单、会话、设备或同步密文，也不兼容旧客户端。

在成员/席位模型落地之前，`Team` 暂不作为个人最高档售卖，避免继续误导。

## 理由（Rationale）

- **命名与能力对齐**：叫 "Team" 就必须有团队能力，否则不如改名收敛。选择把能力补上，而非把名字去掉，符合既有 `team_share` feature 位的产品意图。
- **计费可解释**：per-seat 让「为什么加人要多付钱」成为自然语义，消除「20 元=整团一个人」的歧义。
- **货币化空间**：对比「个人最高档」的封面价，席位计费随团队规模线性增长，长期 LTV 更高。

## 后果（Consequences）

- 正面：Team 定位清晰；`team_share`、成员管理、团队审计等能力有明确归属；计费模型可解释。
- 负面/成本：需要新增组织/成员/席位和共享资源能力，计费周期与席位增减对齐逻辑、共享连接的授权模型，工作量显著大于个人订阅。
- Greenfield：新模型从首次部署开始生效；旧库不提供升级、迁移或兼容路径。

## 开放问题（Open Questions）

1. 定价结构：当前 seed 为“基础价包含 1 席位，额外席位同价”；正式定价是否保持此模型仍待商业确认。
2. 席位变更：加/减席位如何与计费周期（月/年）对齐，是否按比例折算？
3. 共享粒度：首期为连接模板、查询、文件夹；项目、仪表盘等后续资源的授权语义如何设计？
4. 订单历史：套餐价格/额度变化后，是否保留每笔订单的不可变套餐快照？
