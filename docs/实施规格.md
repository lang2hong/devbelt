# DB Client 实施规格

本文定义**当前已实现**系统的数据边界、授权模型、API、安全要求和个人同步协议。精确字段以当前 schema、route 和测试为准。

本文不定义尚未交付的管理后台、支付或插件运行时接线。完整新增交付的设计、顺序与验收以[完整交付实施规格](完整交付实施规格.md)为唯一基线；在相应 migration、路由、运行时和测试交付前，它们不是当前能力。

## 1. 系统范围

| 包 | 职责 |
|---|---|
| `packages/db-core` | 数据库驱动、SQL 方言、连接、查询、元数据和数据操作 |
| `packages/vscode-ext` | VS Code 命令、树、webview、连接与凭据、本地状态和组织 Workspace |
| `packages/server` | 身份、个人权益、设备、组织授权、资源、个人同步协议和 MySQL 持久化 |

当前状态：

- 数据库客户端主体和组织 Workspace 已接入扩展 activation。
- 服务端身份、设备、组织、资源和个人同步路由已注册。
- 个人同步扩展端已有协议客户端、本地 store、record 应用、同步循环（`SyncEngine`）、出站生成（`SyncMutator`）与本地变更协调（`SyncCoordinator`）；尚未接入 activation（无 compose root），无密钥生命周期与冲突 UI。
- 平台管理、支付、资源 ACL、资源版本、账号删除和组织内容加密不在当前实现中。
- 平台运营后台和组织管理后台的目标边界与实施顺序见[管理后台架构](管理后台架构.md)；该文档不表示后台已实现。

## 2. 数据与授权边界

1. 服务端元数据使用 MySQL 8。主键使用 `BIGINT UNSIGNED AUTO_INCREMENT`，时间使用 UTC `DATETIME(3)`，数据库列使用 `snake_case`，HTTP JSON 使用 `camelCase`。
2. 用户拥有个人空间，组织拥有协作空间。个人套餐、订阅、设备、会话和个人同步归 `user_id`；组织套餐、订阅、成员、邀请、目录和资源归 `organization_id`。
3. 组织成员、角色和席位不能读取、修改或提升个人连接、设备、同步和数据库引擎权益。
4. 组织资源不得保存数据库密码、SSH 密码、SSH 私钥、私钥口令、个人连接 ID、客户端密钥、凭据映射或本机路径。
5. 组织请求从 URL 获取 `organizationId`。服务端验证用户、组织、membership、权限、订阅和配额；客户端 Workspace 选择不参与授权。
6. `db-core` 不依赖 VS Code、身份、组织、套餐或同步领域。

## 3. 服务端启动

`createApp()` 当前按以下顺序执行：

1. 创建 Fastify，注册错误处理、CORS、Helmet 和 Sensible。
2. 尝试创建目标数据库。
3. 注册 MySQL pool 并初始化 UTC 时区。
4. 创建 repository 和 service。
5. 启动限流与邀请过期清理任务。
6. 注册 `/health`，以及认证、当前用户、个人、组织、邀请和同步路由。
7. 执行 `app.ready()`。
8. 执行 migration。

`GET /health` 当前只返回 `{status:'ok'}`，不探测数据库、SMTP 或后台任务。

## 5. 身份与设备

### 5.1 安全要求

- 密码使用 Argon2id：memory `65536 KiB`、iterations `3`、parallelism `1`、salt `16 bytes`、output `32 bytes`。
- access token 使用 Ed25519，默认有效期 15 分钟。
- refresh token 至少包含 256 bits 随机熵，数据库只保存 SHA-256 hash，默认有效期 30 天。
- refresh token 每次使用后原子轮换；撤销或被替换的 token 再次使用时撤销整个 family。
- 登录、refresh 和设备注册携带客户端生成的 `deviceKey`。
- 撤销设备时同时撤销该设备的 refresh token。
- 未知邮箱、错误密码、未验证邮箱和 disabled 用户返回一致的未认证响应。
- 邮箱验证 token 只保存 hash、单次消费；业务事务提交后再发送邮件。

## 6. 组织与资源

### 6.1 角色权限

组织只有 `admin` 和 `member`：

| 权限 | admin | member |
|---|---:|---:|
| `organization.read`、`member.read`、`folder.read`、`resource.read` | Y | Y |
| `organization.update`、`organization.close` | Y | - |
| `member.invite`、`member.remove`、`member.role.assign` | Y | - |
| `folder.manage`、`resource.write`、`resource.delete` | Y | - |

创建组织的用户成为首位 active admin。服务端拒绝移除、退出或降级最后一位 active admin。组织不存在、已关闭或调用者不是 active member 时统一返回 `404 ORGANIZATION_NOT_FOUND`。

### 6.2 事务与冲突

组织写事务按 `organization -> subscription -> membership -> invitation` 加锁，目录和资源随后按 `folder -> resource` 加锁。配额在事务内计算。

授权中间件的角色判定发生在事务外，因此每个组织写事务在取得组织锁后必须重新锁定**操作者** membership、确认其仍为 active 并重算所需 permission code；操作者已非 active member 时按 §6.1 口径返回 `404 ORGANIZATION_NOT_FOUND`，权限不足返回 `403 FORBIDDEN`。资源写入的作者字段取事务内解析出的 membership，不使用中间件传入的值。

资源更新使用 `(id,organization_id,version)` 乐观锁。版本冲突返回 `409 RESOURCE_VERSION_CONFLICT` 和当前版本。目录移动拒绝环；非空目录不能删除。

### 6.3 资源内容

组织资源只允许：

- `connection_template`：数据库类型、host、port、database、可选 username 和 SSL；
- `query`：非空 SQL 和可选 dialect。

两类内容均为严格闭合对象。密码、secret、SSH、证书、连接 ID 和本机路径全部拒绝。

## 7. 个人同步

### 7.1 安全模型

个人同步只处理个人连接。服务端保存 ciphertext、公开签名材料、nonce ledger、mutation receipt、版本和配额元数据；不保存连接明文、DEK、同步口令、恢复码或签名私钥。

- DEK 为 32B CSPRNG，只存 `SecretStorage`，按 user 和 `keyEpoch` 隔离。
- 同步签名私钥由 DEK 通过 HKDF-SHA-256 即时派生。
- 恢复签名私钥由 256-bit 恢复码即时派生。
- record 使用 AES-256-GCM，nonce 12B、tag 16B。
- record AAD 的 `purpose` 固定为 `record`；envelope AAD 的 `purpose` 为 `smp` 或 `recovery`。
- u64 使用无前导零十进制字符串；二进制使用无 padding base64url。
- recordId 生成口径：16 个 CSPRNG 随机字节编码为 22 字符无 padding base64url（新 record 的唯一生成方式）。
- recordId 接受口径：无 padding base64url 解码 1‥128 字节，超限 fail-closed；128 字节上限来自数据库列宽（`record_id VARBINARY(128)`），属兼容边界，不改变生成规格。
- Argon2id 必须在 Worker 中执行；`KEK_smp` 经 `deriveKekSmpInWorker` 派生，主线程不执行 Argon2id。Worker 不可用或超时即 fail-closed 拒绝解锁，不 fallback、不排队；每次派生新建 worker、不池化。参数域与服务端 `syncStateService.ts`/`schemas.ts` 一致（memoryKiB 65536..262144 / iterations 3..10 / parallelism 1..4 / salt 16B / output 32B）。
- 本地存储键按 userId（+ keyEpoch）隔离，无版本段：
  - `dbclient.sync.dek.<userId>.<keyEpoch>`（`SecretStorage`）
  - `dbclient.sync.state.<userId>`（globalState）
  - `dbclient.sync.recordMap.<userId>.<keyEpoch>`（globalState）
  - `dbclient.sync.outbox.<userId>.<keyEpoch>`（globalState）
  - `dbclient.sync.epochCleanup.<userId>`（globalState，epoch 切换可重放清理标记）
- 读路径对持久化形状 fail-closed：非对象、缺失字段或非法条目必须抛错，不得静默降级为空。
- fail-closed 错误不得包含秘密；引擎不得静默重试或静默清空损坏状态。用户可见恢复动作（清空对应 store，或执行 destroy / reset-after-loss）属路线图任务 4 的 UI 义务。
- 键格式演进必须启用新键前缀，禁止就地重新解释旧值。
- `state` 快照单调性按 epoch 分段：`keyEpoch` 不得回退、`changeSequence` 全局不得回退；`stateVersion` 仅在同一 `keyEpoch` 内不得回退；`keyEpoch` 增加时允许 `stateVersion` 从旧 epoch 任意值切到新 epoch 初始值 `1`。`setSnapshot` 按此条件实施守卫，不逐字段独立拒绝。
- `recordMap` 条目形状：`{ connectionId: string, recordVersion: u64 十进制串, revision: 非负安全整数, status: 'pending' | 'confirmed' }`；`byRecordId`↔`byConnectionId` 正反向一一对应（双射不变量，读取时校验）；`status` 字段缺失即判损坏。
- `outbox` 条目形状：以 `pendingMutationStore.ts` 的 `assertMutation` 为唯一口径（`assertBase` + nonce/tag 长度 + put/delete 字段分判），`put()` 与 `list()` 共用。
- 上述 store 尚未随扩展出货（除测试外零引用），本次形状变更不触发换前缀义务；一旦出货，任何形状变更都必须换新键前缀。

### 7.2 Payload

加密 payload 可以包含数据库密码、SSH 密码和 SSH 私钥口令。禁止包含 SQLite 本机路径、私钥文件路径或内容、OS keychain 引用、组织引用、`sqliteCommand`、`connectionUrl`、`useConnectionString`、本地 connectionId、时间戳、删除标记和未知字段。

解密后必须校验字段、类型、端口和引擎。不在个人权益中的引擎逐条跳过并汇总提示；tombstone 不经过引擎门禁。

### 7.3 状态与版本

- 每个用户只有一条 `personal_sync_state`。
- init 创建 `keyEpoch=1,stateVersion=1`。
- change-key 和 recover 增加当前 epoch 的 `stateVersion`。
- destroy 和 reset 建立下一个 epoch，`stateVersion` 从 1 开始。
- 同步循环同 epoch 状态对账：远端 `stateVersion` 高于本地 → 采用远端 `stateVersion`、保留本地 `changeSequence`；写快照失败即本轮 `error`，不进 outbox 与 feed。远端低于本地 → 单调防回退，本轮 `error`，不进 outbox/feed，不覆写本地快照（`stateVersion` 是 change-key/recover/destroy 的 `expectedStateVersion` 输入，本机不跟进将在密钥生命周期操作中命中版本冲突）。
- `changeSequence` 在用户范围内单调增加，epoch 变化时不重置。
- epoch 切换（destroy/reset-after-loss）本地清理固定顺序：① 服务端确认 → ② GET state 取新 epoch → ③ 持久化新快照 → ④ 清旧 epoch recordMap/outbox → ⑤ 删旧 epoch DEK。清理前写 `dbclient.sync.epochCleanup.<userId>` = `{fromKeyEpoch,toKeyEpoch}`，完成即删；启动时检测到标记即完整幂等重放（`clear()`/`delete()` 幂等、`setSnapshot` 等值重放不抛——守卫只拒更小值）。`changeSequence` 全局不回退、绝不本地重置（本清理只删 recordMap/outbox/DEK，不动 changeSequence）。
- record create 使用 `baseVersion="0"`；update/delete 使用当前版本。
- tombstone 不能再次创建、更新或删除。
- outbox mutation 持久化其 payload 对应的本地 revision（生成密文那刻连接的 `updateTime`）；`record.put` 成功后以该持久化 revision（非「当前」`updateTime`）将映射置 `confirmed`，`recordVersion`=receipt `version`；随后重新对账，仅当连接当前 `updateTime` 高于已确认 revision 才创建下一条 mutation（每 record 至多一个 pending、pending 不覆盖）。`record.delete` 成功后删除映射（与入站 tombstone 分支一致）。`outbox` 的 revision 为非负安全整数，读取时由 `assertMutation` 校验。
- feed 使用固定 `snapshotSequence` 分页，客户端只持久化服务端确认的 cursor。
- 页内部分应用后发生冲突/失败时，本地 cursor 停在最后确认页；下一轮从该 cursor 重拉，并靠 record 幂等（`confirmed` 且 version ≤ recordVersion 跳过）收敛，不重复写。

### 7.4 签名与幂等

签名输入使用 RFC8785 JCS。`requestDigest` 是客户端从实际发送 body（除 `signature` 外）本地派生的签名输入，不是 HTTP body 字段；服务端以同法重算核对。action 由 method/path 决定。服务端先验签，再记录 nonce 或写状态。

客户端在发送前持久化完整签名 mutation。重试必须原样复用 `mutationId`、nonce、ciphertext、tag、digest 和 signature。同 mutationId、同 digest 返回原 receipt；同 ID 异 digest 返回 `409 CONFLICT`。

签名 mutation 发送成功即「确认」并回写 recordMap；确认 revision=该 mutation 持久化的 payload revision（非当前 `updateTime`，见 §7.3 outbound 确认），确认后立即重对账，仅当连接当前 `updateTime` 高于已确认 revision 才生成下一条 mutation。重放不重签、逐字复用，确认由服务端 receipt 的 `version`/`changeSequence` 驱动。

确认与删除顺序契约（对齐完整交付实施规格 §4 编排第 4 条）：push 成功 → 回写 recordMap（`recordVersion`=receipt `version`、`revision`=持久化 revision、`status='confirmed'`；delete 则删映射）→ 才删除 outbox 条目。确认写失败则保留条目并以 `stage='error'` 结束本轮，下轮原样重放，由服务端幂等 receipt 返回同一 version/changeSequence 收敛。禁止先删条目再确认，否则确认失败会停在旧 recordVersion，下轮以旧 baseVersion 生成新 mutation 触发虚假 `SYNC_VERSION_CONFLICT`。

record.put / record.delete 发送结果按 code 分类（重放与错误处置，引擎按此表实现）。本表仅适用 record 两个 mutation；init/change-key/recover/destroy 属 state 侧签名 mutation，按 §7.3 对账口径处置（其 `SYNC_VERSION_CONFLICT` 表 expectedStateVersion 不符；`SYNC_STATE_EXISTS` 表 init 冲突，交任务 4）：

| code | 处置（stage） | 说明 |
|---|---|---|
| `SYNC_PROTOCOL_UNSUPPORTED` / `SYNC_SIGNATURE_INVALID` / `VALIDATION_FAILED` | terminal | 不可自愈；保留 outbox 条目，停在该条，交任务 4 |
| `SYNC_NONCE_REUSED` | terminal | 同 nonce 被不同 mutation 消费，重试必再失败 |
| `SYNC_QUOTA_EXCEEDED` | terminal | 配额不足，重试不恢复 |
| `CONFLICT` | terminal | 同 mutationId 异 digest（生成侧逐字复用被破坏） |
| `SYNC_EPOCH_STALE` | terminal（epoch） | reason 须含 currentKeyEpoch，任务 4 据其走 epoch 对账/清理，不与普通 terminal 混同 |
| `SYNC_NOT_INITIALIZED` | terminal(state) | 远端 destroy 后本机残留 outbox；reason 须可被任务 4 识别为「需 init / epoch 处理」 |
| `SYNC_VERSION_CONFLICT` | conflict（recordId+code+currentVersion） | baseVersion 落后；一律保留原 mutation 与本地连接、不自动改写/重签（§7.4 全量 mutation 逐字复用，改 baseVersion 必变 digest/signature）；把 recordId/code/currentVersion 结构化交任务 4，决定取舍与新 mutation 生成 |
| 其余 4xx/5xx/网络/401/429 | error | 保留 outbox，下轮重演 |

结果字段契约：`terminal` 携带 `{mutationId, code}`；`conflict` 携带 `{recordId, code, currentVersion?}`；epoch 类携带 `currentKeyEpoch`；state 侧按 §7.3 对账。`stalled` 为结构化同步结果，不得写入日志（日志契约禁止暴露 mutationId）。

可重试失败的保序与恢复：每个 pending mutation 持久化 `consecutiveFailureCount`，仅对可重试 error 递增；成功 receipt、terminal 或 conflict 时删除/终止该计数，计数随 outbox 条目持久化、重启不丢失。第 1–4 次可重试失败：保留原条目、结束本轮（`stage='error'`）、禁止入站 pull。第 5 次及以后：保留原条目与失败计数、结果附 `stalled`、允许继续入站 pull，但不得跳过/删除/重签该条目，也不得生成同 record 的后续 outbound mutation。后续每次 sync 仍先重试 stalled 条目；成功后先按 receipt 确认映射、再重对账，之后才允许下一条本地 mutation。

### 7.5 API

| Method | Path | 作用 |
|---|---|---|
| `GET` | `/api/sync/state` | 读取状态 |
| `PUT` | `/api/sync/init` | 初始化 |
| `GET` | `/api/sync/records` | 拉取 record feed |
| `PUT` | `/api/sync/records/:recordId` | 写入 record |
| `DELETE` | `/api/sync/records/:recordId` | 写入 tombstone |
| `POST` | `/api/sync/change-key` | 更换同步口令 envelope |
| `POST` | `/api/sync/recover` | 使用恢复码恢复并轮换恢复材料 |
| `POST` | `/api/sync/destroy` | 销毁当前同步数据并推进 epoch |
| `POST` | `/api/sync/reset-challenges` | 发送丢失后重置挑战 |
| `POST` | `/api/sync/reset-after-loss` | 确认数据丢失并建立新 epoch |

#### 7.5.1 请求体契约

以 `route/schemas.ts` 严格 schema（`additionalProperties:false`）为唯一事实源。公共签名件：`protocolVersion`(int=1)、`keyEpoch`(u64 十进制串)、`mutationId`(base64url 22 字符=16B)、`signature`(base64url 86 字符=64B)。

- put record：公共件 + `recordId`(≤171 字符=128B)、`baseVersion`(u64)、`cipherSuite`(`AES-256-GCM`)、`formatVersion`(=1)、`nonce`(16 字符=12B)、`ciphertext`(1..349526 字符)、`tag`(22 字符=16B)。
- delete record：公共件 + `recordId`、`baseVersion`；禁止 `nonce`/`ciphertext`/`tag`。
- destroy：公共件 + `expectedStateVersion`、`newState`（无确认字段）。
- reset-after-loss：`protocolVersion`、`resetToken`(base64url 43 字符=32B)、`newState` + `confirmIrreversible`/`confirmDataLoss`/`confirmNoRecovery` 必须字面量 true。

## 8. 错误与日志

通用错误包括 `VALIDATION_FAILED`、`UNAUTHORIZED`、`USER_DISABLED`、`PERSONAL_FEATURE_REQUIRED`、`ORGANIZATION_NOT_FOUND`、`FORBIDDEN`、`RESOURCE_NOT_FOUND`、`ORGANIZATION_FEATURE_REQUIRED`、`RESOURCE_CONTENT_INVALID`、`ORGANIZATION_QUOTA_EXCEEDED`、`RESOURCE_VERSION_CONFLICT`、`FOLDER_NOT_EMPTY`、`FOLDER_MOVE_CYCLE`、`ORGANIZATION_ADMIN_REQUIRED`、`INVITATION_INVALID`、`INVITATION_TARGET_NOT_ELIGIBLE` 和 `TOO_MANY_REQUESTS`。

同步错误包括 `SYNC_NOT_INITIALIZED`、`SYNC_PROTOCOL_UNSUPPORTED`、`SYNC_SIGNATURE_INVALID`、`SYNC_STATE_EXISTS`、`SYNC_EPOCH_STALE`、`SYNC_VERSION_CONFLICT`、`SYNC_NONCE_REUSED`、`SYNC_QUOTA_EXCEEDED` 和 `CONFLICT`。

日志和错误不得包含密码、token、请求正文、组织资源正文、ciphertext、nonce、recordId、mutationId、同步口令、恢复码、私钥或解密细节。

邮箱验证与组织邀请 token 出现在 URL path 中，因此访问日志使用自定义 req 序列化器：只记录 method、脱敏后的 URL 和客户端地址，替换 token 段并抹掉 `token`、`accessToken`、`refreshToken`、`recoveryCode` 查询参数，不记录 header 与 body。

route 层只负责把 `DomainError` 映射为响应；未知异常必须冒泡到全局 error handler，由其记录堆栈与请求上下文后返回固定 500 文案。
