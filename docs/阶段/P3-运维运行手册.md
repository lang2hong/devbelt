# P3 运维运行手册（Runbook）

切片 5 声明性运维手册，覆盖健康检查、发布/回滚、功能开关、监控告警、数据清理与
备份恢复演练。本文档只记录策略与阈值；具体命令/字段以部署层（k8s / nginx / 监控后端）为准。

## 1. 健康检查（§11.1）

| 端点 | 用途 | 语义 |
|---|---|---|
| `GET /health/live` | k8s liveness probe | 进程存活，不连 DB，恒 200 `{ status: "ok" }` |
| `GET /health/ready` | k8s readiness probe / LB 摘除 | DB 连通 + schema 账本对齐 + mail 依赖就绪；200/503，体含 `{ status, db, schema, mail }` |

- 两者 `Cache-Control: no-store`、不设 Cookie、响应体 `< 500B`、**不泄露版本号/库名/hostname**。
- `/health/ready` 的 DB 探活带 2s 超时：DB 假死时快速返回 503，避免探针挂死。
- 版本号走独立的受控 `/api/console/version`（仅平台管理员）。

探针配置建议：
- liveness: `GET /health/live`，period 10s，failureThreshold 3。
- readiness: `GET /health/ready`，period 5s，failureThreshold 3（摘除后自动重建）。

## 2. 发布与回滚（§11.4）

- 前端静态资源按**内容 hash** 发布；HTML 不缓存，静态资源 immutable 一年。
- 回滚只切换 HTML/服务端版本，**不删除**已发布的 hash 静态文件，至少保留 7 天。
- **邮件入口至少保留两个前端发布版本**，覆盖「邮件发送 → 用户点击」之间的部署窗口。
- 控制台前端与服务端经 `consoleApiVersion` 协商，前端只调用当前及前一个兼容 API 版本。

发布顺序：
1. 先发服务端（含新 migration，`/health/ready` 会在未迁移完成前 503）。
2. 再发前端（旧前端仍指向兼容的旧 API）。
3. 观察监控（见 §4），异常按回滚流程切换 HTML/服务端版本。

## 3. 功能开关（§11.4）

策略：`browser-auth` / `mail-flow` / `sync-handoff` / `payment` 各自独立开关；**关闭时
返回 `503 FEATURE_TEMPORARILY_DISABLED`，不回退到旧的弱安全链路**。

> 现状：`FeatureFlags` 已实现，`payment` 已按 opt-in 接线（`DEVBELT_DB_FEATURE_PAYMENT=true/1/on` 才启用，
> 关闭返回 `503 FEATURE_TEMPORARILY_DISABLED`）。`browser-auth` / `mail-flow` / `sync-handoff`
> 仅为**预留命名、未接线**——不要把它们当作可用的紧急关闭开关。落地其余开关须满足：
> - 关闭路径在路由/服务入口统一拦截（未通过开关的请求不得落库副作用）。

安全事件下的开关动作见 §6。

## 4. 监控与告警（§11.3）

### 4.1 打点与日志

- 请求链路注入 `X-Request-ID`（未携带则生成 UUIDv4 回显）。
- 结构化 JSON 日志最少含 `requestId/timestamp/route/method/status/latencyMs/userId(sessionId 摘要)/errorCode`；**不记录**请求/响应原文、Cookie、Authorization、query token、密码、E2EE 密文/密钥、handoffTicket/resetToken/CSRF/Idempotency-Key。
- 请求速率/错误率按 `(route, method, status_code)` 打点：进程内 `MetricsRegistry` 以 `http:<method>:<route>:<status>` 键累加，`snapshot()` 供部署层采集（Prometheus/云监控）。

### 4.2 指标与告警阈值

| 类别 | 指标 | 告警条件 |
|---|---|---|
| 可用性 | `/health/ready` 成功率、HTTP 5xx 比例、p95/p99 延迟 | 5min 窗口健康检查失败；5xx > 1% 持续 3min；p95 超 SLO |
| 认证 | 登录成功/失败率、refresh 失败率、CSRF/Origin 拒绝数、session 撤销数 | 失败率突发偏离 7 日基线；CSRF 拒绝数突增 |
| 邮件流 | link-flow 认领/完成/过期率、handoff 创建/消费/过期/失败率 | 完成率异常下降；认领/消费失败率异常升高；过期率 > 30% |
| 同步重置 | reset challenge、handoff、最终 reset 成功/失败/重试数 | 最终 reset 失败率 > 5%；同用户重复失败 > 3 次/h；重置成功到消费完成 p95 > 60s |
| 数据与运营 | schema 初始化状态、审计写入失败、receipt/handoff 清理滞后、DB 池饱和度、慢查询、限流命中 | schema 初始化失败；清理滞后 > 24h；池使用 > 80%；p99 查询 > 1s 持续 5min |
| 安全 | 匿名接口限流触发速率、账号枚举模式、大量无效 token 尝试 | 单 IP 限流命中 > 100/min；同 IP 多账号登录失败；link-flows 大量 401 |

告警通知只含 `requestId`、匿名聚合信息与错误码；排障经受控日志查询关联。**所有告警绑定
本 Runbook 的验证步骤与回滚开关指引**。

## 5. 数据清理（§11.2 / retentionCleanup）

| 表 | 动作 | 保留/触发 |
|---|---|---|
| `refresh_tokens` | DELETE | 终结后 7 天 |
| `email_verification_tokens` / `personal_sync_reset_tokens` | DELETE | 终结后 24h |
| `personal_sync_mutations` | DELETE | 过 `expires_time` |
| `mail_flows` | DELETE | 过期/消费后 24h |
| `idempotency_receipts` | DELETE + 系统审计摘要 | 过 `expires_time` |
| `sync_reset_handoffs` | ① expire ② prune | ① issued/processing 过 `expires_time` → expired；② completed/revoked/expired 后 24h 物理删除 |

- 周期默认 1h；每表每轮 ≤ 1000 行（防长事务/长锁）；失败只记日志、下轮重试；`timer.unref()` 不阻塞退出。
- 清理账号最小权限：各保留表的范围受限 `DELETE`；**`sync_reset_handoffs` 额外需要只针对
  `status`/`update_time` 的受控 `UPDATE`**（expire 阶段把过期 issued/processing 置 `expired`，
  是协议要求的终态迁移，非任意业务字段的 UPDATE）。除这两个字段外，清理账号不得 UPDATE 任何业务字段。

## 6. 安全事件响应（§11.4）

若浏览器认证、邮件流或 handoff 出现安全事件：

1. 立即关闭对应功能开关（§3）。
2. 撤销受影响 session / mail-flow / handoff ticket。
3. 保留审计与取证数据（不清理、不覆盖）。
4. 发布用户可见状态页说明。
5. 恢复前完成根因、修复、复测与安全评审。

## 7. 备份、恢复与演练（§11.5）

- 每日全量、至少每小时增量/日志备份；加密保存并跨故障域复制。
- **每季度**执行一次「备份恢复到隔离环境」演练，验证用户、订阅、审计、mail flow、同步元数据一致性；恢复环境不得连接生产 SMTP / 支付 / 遥测。
- SLO 目标：**RPO ≤ 1h，RTO ≤ 4h**。基础设施无法满足时，不得宣称该 SLO。

## 8. 挂账 / 观察项（随切片 5 关闭时的交接）

- CI 实库并发用例（`syncReset.test.ts` 同票并发重放）以 `main` 触发 CI 为准。
- 一处 flake 观察（server 全量首轮 1 瞬态失败，双重复跑干净）。
- 扩展对 `409 SYNC_RESET_IN_PROGRESS` 无特判：走通用错误 + 页面「我已打开 VS Code，重试」恢复，窗口秒级，可接受。
- `bind` 失败抛 `INVITATION_INVALID`（名实不符）：已改为中性码 `LINK_FLOW_INVALID`（切片 5 收口）。

## 9. P4 支付挂账 / 观察项（随切片 2 关闭时交接）

- **过期 pending 订单无 sweep**：`orders.status='pending'` 且 `expires_time` 过期后无周期任务置 `expired`，仅回调时惰性拒绝（`recorded`）。启用真实支付前，须在订单生命周期切片或 `retentionCleanup` 增加过期 sweep，否则 pending 行长期残留。
- **Team 套餐（seat 计费 + 组织订阅写入）整体缺失**：组织套餐订单/回调/权益生效（`organization_subscriptions`）未实现，划入独立切片，不属切片 2。
- **多渠道并行下单策略**：同套餐可同时存在微信、支付宝两张 pending 订单，旧订单不本地单边过期（避免「渠道侧已付款、本地却判过期」的确认但不履约风险）；任一渠道成功回调即履约并续期。代价是两个渠道都可能被用户支付 → 产生重复扣款，须在对账/人工退款切片（4C）提供处置与补偿流程，上线真实资金前必须闭环。
- **真实渠道适配器（微信/支付宝）归切片 4**：`resolvePaymentGateway` 切到真实 WeChat/Alipay 适配器并注入商户凭据后方可注册支付路由；回调防重放当前由「签名完整性 + 时间戳 freshness（±5min）+ `(channel, channel_trade_no)` 唯一约束 + 订单状态机幂等」构成，**不持久化/拒绝 nonce 重放**（窗口内同 nonce 可重放进入回调路径，但被交易号幂等拦住、不重复履约）；nonce receipt 持久化拒绝重放记为后续安全强化项。
- **订阅续购版本冲突瞬态语义**：`applyEntitlementInTx` 乐观 CAS 失败抛 `ORDER_INVALID_STATE` → 4xx → 渠道重试 → 重放轮读新 version 通过。语义正确，但真实接入时须确认渠道对 4xx 的重试策略不会放大为风暴（当前验签后领域失败已回 200 rejected 止重试）。

## 10. P4 支付凭据配置（切片 4B）

支付渠道均走环境变量注入，全部 base64 编码 PEM，绝不入库、入仓库或落日志。**每个渠道「凭据齐全 + 回调 URL 合法」才视为已配置**，任一缺失则整渠道静默未配置（fail-closed，不暴露下单/回调路由）。

| 变量 | 渠道 | 说明 |
|---|---|---|
| `DEVBELT_DB_PAYMENT_CALLBACK_BASE_URL` | 两者 | HTTPS 裸 origin（无路径/query），作为回调 URL 前缀；非法/缺失→两渠道均未配置 |
| `DEVBELT_DB_WECHAT_MCH_ID` / `DEVBELT_DB_WECHAT_APP_ID` | wechat | 商户号 / 应用 appid |
| `DEVBELT_DB_WECHAT_MERCHANT_CERT_SERIAL` | wechat | 商户证书序列号（16 进制），v3 Authorization 元数据必填；非法→未配置 |
| `DEVBELT_DB_WECHAT_PLATFORM_CERT_SERIAL` | wechat | **平台证书序列号（16 进制），回调验签绑定**；入站 `wechatpay-serial` 不匹配即拒；非法→未配置 |
| `DEVBELT_DB_WECHAT_PRIVATE_KEY_B64` | wechat | 商户私钥 PKCS8 PEM 的 base64（下单签名） |
| `DEVBELT_DB_WECHAT_PLATFORM_CERT_B64` | wechat | 平台证书 SPKI PEM 的 base64（回调验签） |
| `DEVBELT_DB_WECHAT_API_V3_KEY` | wechat | **恰好 32 字节**（AES-256-GCM 回调解密）；短/长→未配置，不截断 |
| `DEVBELT_DB_ALIPAY_APP_ID` | alipay | 应用 appid |
| `DEVBELT_DB_ALIPAY_PRIVATE_KEY_B64` | alipay | 应用私钥 PKCS8 PEM 的 base64（表单签名） |
| `DEVBELT_DB_ALIPAY_PUBLIC_KEY_B64` | alipay | 支付宝公钥 SPKI PEM 的 base64（回调验签） |

- 回调 URL 由 `<DEVBELT_DB_PAYMENT_CALLBACK_BASE_URL>/api/public/payment-callback/<wechat|alipay>` 构造，随下单请求序列化交给渠道（非空通知地址，避免「已付款但永不履约」的资金不一致）。
- 功能开关：支付为 **opt-in 默认关闭**——完备的微信/支付宝凭据仅使渠道「已配置」，需再显式设 `DEVBELT_DB_FEATURE_PAYMENT=true` 并重启，才注册下单 + 回调路由；仅配凭据而未开启 => 支付保持关闭（下单/回调返回 503 或路由未注册）。上线顺序固定为「配全凭据 → 设 `DEVBELT_DB_FEATURE_PAYMENT=true` → 重启 → 沙箱人工验收」，不颠倒。关闭时下单/回调返回 503 `FEATURE_TEMPORARILY_DISABLED`（不回退弱路径）；`DEVBELT_DB_FEATURE_BROWSER_AUTH`/`DEVBELT_DB_FEATURE_MAIL_FLOW`/`DEVBELT_DB_FEATURE_SYNC_HANDOFF` 为预留命名，尚未接线。
- 真实到微信/支付宝沙箱的 HTTP 端到端联调与真实资金验证属部署后人工验收（§83/§84），不进 CI。

### 10.1 支付运营注意事项（切片 4B 收口）

- **功能开关是启动期快照**：`FEATURE_*` 在进程启动时读取，改动需**重启生效**，不是运行时即时 kill switch。若需立即止血，重启前先走「关闭外部支付意图」：微信端关单/支付宝端关闭交易，否则已发出的二维码/跳转链接在其有效期内仍可被付款，回调会被 503 拒绝直至开关恢复——不可把 503 当作资金对账策略。
- **微信平台证书轮换**：当前为**静态单证书**配置（`DEVBELT_DB_WECHAT_PLATFORM_CERT_SERIAL` + `DEVBELT_DB_WECHAT_PLATFORM_CERT_B64`）。轮换流程：下载新平台证书 → 更新两变量 → 部署重启；期间旧证书签名的在途回调会失败，属可接受的短窗口（渠道会重试）。**不支持多证书重叠/自动轮换/过期监控**；正式生产接入前需评估是否升级为 serial→证书集合。
- **回调身份绑定**：微信回调解密后校验 `appid`/`mchid`、支付宝校验 `app_id` 与配置一致，不匹配按解析失败拒绝（不泄露具体渠道）。
- **支付宝回调确认**：异步通知要求响应体字面 `success`（`text/plain`）；微信 v3 用 JSON `{code:'SUCCESS'}`。重复/已处理回调同样返回确认以终止渠道重试。
- **支付宝通知时间 freshness**：按标准通知字段 `notify_time`（回退 `gmt_payment`）校验 ±5 分钟窗口；超窗按签名拒绝。注意渠道重试间隔可能超过 5 分钟，若线上出现「合法回调被 freshness 拒绝」需评估放宽窗口，而非静默接受。
- **套餐停用在飞订单**：支付成功但 `plan_code` 已停用 → `UnknownPlanError` 回滚 → 渠道重试 → 「款已收、权益未落」。属人工退款兜底（契约 §25）；运营停用套餐前应留意在飞订单数，并在 Runbook 预留处置预案。
