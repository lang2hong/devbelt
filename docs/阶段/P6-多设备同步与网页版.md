# P6 — 验证器多设备同步与网页版

> 状态：draft v2（据 2026-09-23 决策与实现评审修订：D1 保持 E2EE / D2 web 主密码解锁→DEK→本地解密 /
> D3 secret 允许以 E2EE 密文离机 / D4 服务端可加**可选**明文 `entity_kind` / D5 顺序 扩展同步 →
> 服务端计数/后台 → Web）。本阶段在 P5（本地验证器）之上叠加同步能力。
>
> v2 修正：补同步 ingest API、id↔recordId 映射与改动文件清单、配额拒绝对账、entity_kind 灰度、
> Web 前置项；并对齐 P5 真实口径与若干事实精度。

## 一、这个阶段要做什么

- **多设备同步（扩展 ↔ 扩展）**：条目/分组/标签作为**新的 E2EE 同步实体**接入现有个人同步通道
  （AES-256-GCM，DEK 派生自同步主密码），冲突/墓碑/epoch 复用现有机制。
- **网页端查看与操作**：浏览器实现"主密码解锁 → 派生 DEK → 本地解密"，`db-ui` 提供验证器视图。
- **管理后台**：**在 E2EE 前提下不可见条目明文、不可操作条目**；仅管理套餐额度
  `maxAuthenticatorEntries`（P5 已有）+ 展示**密文元数据**（按类型条数/字节/设备/时间）。
- **不做**：服务端明文存储、后台明文查看/编辑条目。

## 二、关键决策

| # | 决策 | 影响 |
|---|---|---|
| D1 | 保持 E2EE，后台不能查看/操作条目 | 后台能力=配额+元数据 |
| D2 | Web 用**主密码**解锁派生 DEK，浏览器本地解密 | 新增浏览器 E2EE 与密钥生命周期 |
| D3 | secret 允许离机，但**仅以 E2EE 密文** | 见下"口径说明" |
| D4 | 服务端新增**可选**明文 `entity_kind`（仅类型名） | 支撑按类型计数/配额/后台统计 |
| D5 | 切片顺序：扩展同步 → 服务端计数/后台 → Web | 见 §九 |

> **口径说明（修正 v1 的失真引用）**：P5 **从未**写"secret 不离机"——P5 的「安全（用大白话）」章与
> 「附：数据与安全的分级」章已明确"**以后同步时密钥在本地加密成密文再上传 / 未来仅以 DEK 密文上行**"。
> 因此 P6 与 P5 **不冲突**。P6 需要更新的仅是 P5 的**范围性表述**：「这个阶段要做什么」/「交付切片」/
> 「附：数据与安全的分级」中"本阶段不联网""不做多设备同步/网页版"的边界声明——P6 作为后续阶段接续实现。
> 另更正 P5「交付切片」里「作为第 5/6 种同步实体」→ 实为 **3 类**（现 4 类 + 3 = 第 5/6/7 种）。

## 三、现状与改造点（架构事实，已核对）

- 同步实体 4 类：`connection | group | queryFolder | query`
  （`packages/db-host/src/sync/e2e/syncEntity.ts`），全链路类型化。
- 密文：`packages/db-host/src/sync/crypto/aead.ts` 提供 `sealAes256Gcm/openAes256Gcm`
  （与 `purpose` 无关）；`purpose='record'` 由 `recordCodec.ts` 的 `recordAad` 设置。
- 记录上限：协议 JSON schema 的 `ciphertext` 是 base64url 字符串长度 ≤ 349526（
  `apps/server/src/route/schemas.ts`），**语义**为解码后 ≤ 256 KiB；客户端/服务端各自另有 256 KiB 校验。
- 服务端 records 落 `personal_connection_meta`（`record_id/cipher_suite/nonce/ciphertext/tag/
  version/change_sequence/delete_time`），**内容不可见、无实体类型**。
- Web：`apps/db-ui/src/api/sync.ts` 仅只读聚合元数据，**无密文/E2EE**；`auth-client` 只做会话。

## 四、同步实体与落地（含 H1/H2 补齐）

新增 3 类实体（对齐 `apps/vscode-ext/src/authenticator/types.ts`）：
`authenticatorEntry`（含 **secret**）/`authenticatorGroup`/`authenticatorTag`。

### 4.1 同步 ingest API（H1，S2 必须新增到 `AuthenticatorStore`）
远端落地**不能**复用 `addEntry`（它会生成新本地 id、触发本地配额），必须新增：
```ts
/** 以远端 recordId 映射到的本地 id 写入/覆盖条目；显式 id、跳过本地配额、直接写 secretCache+SecretStorage、发事件。 */
upsertFromSync(entry: AuthenticatorEntry, secret: string): Promise<void>;
/** 按本地 id 删除（墓碑落地）；幂等。 */
removeFromSync(id: string): Promise<void>;
```
语义：显式使用映射后的本地 id（经 §4.2）；**不做 checkQuota**（配额由服务端强校验 + 客户端在"用户本地新增"
路径处理）；写入 secret 走 `secretKey(id)`；成功后 `publishAuthenticatorChangedEvent`。
- **首次拉取 vs 更新（须区分）**：首次 pull 某 record 时本地**尚无映射** → 需**铸造新本地 id**（`ae/ag/at`）
  并**新建 `RecordMapStore` 映射**后再写；后续 pull 同一 record 则**复用既有映射**、按更新处理。
  `upsertFromSync` 的"以映射到的本地 id 写入"仅描述**更新**路径；create 由现有 apply 机制先行建映射。

### 4.2 id ↔ recordId 映射与改动文件清单（H2）
- 本地前缀：条目 `ae`、分组 `ag`、标签 `at`（`uniqueId` 生成）。
- 映射规则：本地 `localId ⇄ recordId` 经 `RecordMapStore`（现有机制）；引用字段一律存 **recordId**
  （`entry.groupId → group recordId`、`entry.tags[] → tag recordId[]`）；目标未到达/pending 时保留
  unresolved（对齐现有 §D3）。
- **applyOrder**：`group`/`tag` 必须先于 `entry` 落地（`entityStore.applyOrder` 需纳入新类型）。
- **改动文件清单（S2）**：
  | 文件 | 改动 |
  |---|---|
  | `sync/e2e/syncEntity.ts` | 加 3 类型；`assertSyncEntityType` |
  | `sync/e2e/recordCodec.ts` | 3 类 payload + 校验（见 4.3） |
  | `sync/e2e/applyRecords.ts` / `syncMutator.ts` / `conflictResolver.ts` | 新类型分支、引用修补 |
  | `sync/e2e/entityStore.ts` | **关键**：其构造函数硬绑单一 `ConnectionStore` → 引入**同步实体适配端口**（或第二套 store 适配）供 authenticator 落地 |
  | `sync/e2e/syncEngine.ts` | 4 字面量 allow-list 扩为新类型 |
  | `sync/session.ts` | `LOCAL_ID_PREFIX: Record<SyncEntityType,string>` 必须补齐（否则编译失败） |
  | `apps/vscode-ext/src/authenticator/store.ts` | 新增 `upsertFromSync/removeFromSync` |
  | `apps/vscode-ext/src/authenticator/types.ts` | `AuthenticatorEntry` 增 `localOnly?`/`syncError?: 'quota'`（§六对账用；**仅本地派生态，不进 payload**） |
  | `apps/vscode-ext/src/result/protocol.ts` + `authenticatorViewProvider.ts` | 快照下发 `localOnly/syncError` 状态 |
  | `apps/vscode-ext/webview/src/views/AuthenticatorView.vue` | 显示"未同步 / 升级 Pro"提示 |
  | 测试 | codec/apply/mutator/conflict/store 适配 |

### 4.3 编码白名单与边界
- `secret`：规范化 base32（大写无 padding），字符 `[A-Z2-7]`；长度上限 **512 字符**（远超 64 字符典型值，
  fail-closed）。
- `algorithm ∈ {SHA1,SHA256,SHA512}`、`digits ∈ {6,8}`、`period ∈ {30,60}`、`tag.color` 取 8 色白名单。
- 单条 record 内存上限沿用现有 **256 KiB**（远高于本 payload）。
- **secretMissing 同步策略**：本地 secret 丢失（`missingSecrets`）的条目**不同步**（跳过 push），避免
  把空 secret 传播到其他设备；UI 已有灰条提示。
- **冲突语义**：以**整条 record 为单位**的 LWW（**含 secret**），不做字段级合并；并发编辑（含密钥轮换）
  时败方整条被覆盖——实现时不得期望字段级合并。
- **本地派生态不进 payload**：`AuthenticatorEntry.localOnly?`/`syncError?: 'quota'` 只用于本地 UI 与
  对账（§六），**必须排除在 codec payload 之外**（§4.3 的编码字段不含它们）；否则该状态会被同步并随
  整条 LWW 被覆盖，导致"已同步覆盖 quota 标记"之类的错误。

## 五、服务端（元数据 + 计数）

- 迁移新增列 `personal_connection_meta.entity_kind VARCHAR(32) NULL`（明文，仅类型名）。
- **灰度（H4）**：PUT body 的 `entityKind` **必须为可选**；服务端**缺省按 `NULL`/unknown 处理**。
  注意：`additionalProperties:false` 只影响"多带字段"——**旧服务端会拒绝带 `entityKind` 的新客户端**，
  因此**必须先上服务端（接受该可选字段），再上客户端**；新服务端对不带该字段的旧客户端需照常接受。
- **签名**：`requestDigest = SHA-256(JCS(body − signature))` 已覆盖整个 body，新增字段自动进入摘要与签名，
  **无需**显式改 `buildRecordSigningInput`。
- **配额强校验**（S4）：新增**按 kind 计数查询**
  （`count(* WHERE user_id,key_epoch,entity_kind='authenticatorEntry',delete_time IS NULL)`），
  超 `maxAuthenticatorEntries` 拒绝 push。这是**新建查询**，**不是**"与现有 `maxConnectionMetas`
  总条数校验并列"——`maxConnectionMetas` 是**全类型总活跃条数**校验（`syncRecordService.ts:273-293`）。
- 控制台/后台新增只读按类型计数/字节接口（不含密文）。

## 六、客户端（扩展）接入与配额对账（H3）

- `SyncSessionFactory` 注入 authenticator 实体；push 读元数据+secret 组 payload，pull 经 apply 落地。
- **未解锁时验证器照常本地可用**（P5 行为不变）。由此产生的**本地超过上限**必须在 push 被拒时对账，
  规则：
  1. 服务端返回配额拒绝 → 该 mutation 标**永久失败**并**停止重试**（不静默循环）；
  2. 对应本地条目**保留但标 `localOnly`/`quota`**（UI 提示"未同步，升级 Pro"），不回滚用户数据；
  3. 展示「升级 Pro」入口；用户升级后**重新入队**该条；
  4. 幂等：同一 record 重复拒绝视为同一状态（按 `mutationId` 去重）。
- 客户端 `checkQuota` 仍作用于"本地新增"路径，服务端强校验为兜底。

## 七、Web（主密码解锁 → DEK → 本地解密）（H5 前置）

S5 显式前置（否则开工即卡）：
1. **密文读取接口**：现有 record 路由在 `aud:'extension'`/`scope:['sync']` 下，浏览器控制台会话调不通 →
   新增 **console 作用域**的密文读取接口（或扩展 token audience）。
2. **SMP/KDF 参数接口**：浏览器解 DEK 需要 SMP envelope + KDF 盐/参数，`db-ui` 现无此 API → 新增。
3. **Argon2id WASM**：参数必须与扩展 SMP **同构**，共享同一参数来源（常量/接口）。
4. **CSP**：**db-ui（浏览器应用）**需允许 `wasm-unsafe-eval` 与 `worker-src`（与扩展的
   `webview/html.ts` 无关，后者不需要改）。
5. **DEK 生命周期**：**默认不持久化**（仅内存），登出即清（去掉 v1 的 sessionStorage 选项）。

## 八、后台/控制台（仅元数据）

- 管理套餐 `maxAuthenticatorEntries`（已有）；展示按类型密文条数/字节/设备/时间。
- 不可查看/编辑条目；UI 明示"内容端到端加密，后台不可见"。

- **S4 · 服务端配额强校验**：按 kind 计数拒绝 + §六对账。
- **S5 · Web E2EE + 验证器页**：§七前置 + `auth-client` 解锁→DEK + `db-ui` 视图增删改查。
- **S6 · 后台元数据**：按类型计数/字节/设备（只读）。

## 十、安全与隐私

- E2EE 不变；`entity_kind` 为唯一新增明文元数据（仅类型名）。
- secret：本机 SecretStorage 明文；跨设备仅密文；Web 仅内存。
- 日志禁止 URI/secret/密文；后台只聚合元数据。
- **威胁披露**：`entity_kind` + `change_sequence`/时间可暴露"用户何时新增验证器条目"的**时间元数据**；
  后台 UI 与文档需一并披露（条数/类型/时间）。

## 十一、风险与回滚

- 风险：新实体参与现有冲突/引用修补；`entityStore` 适配层改动面大；Web 密钥管理与 WASM Argon2id 是新安全面。
- **回滚（修正 v1）**：`entity_kind` **列**可保留（`NULL` 兼容）；但 **S1 的协议字段不可单独回退**——
  一旦客户端开始携带 `entityKind`，回滚服务端需先回滚客户端（或确保服务端始终接受该可选字段）。
  列与可选字段的"向后兼容"成立；"S1 可单独 revert" **不成立**，须按此排序发布。

## 十二、验证

- 根级 `pnpm typecheck && pnpm lint && pnpm test` 全绿；各包单测。
- **灰度协议兼容用例（H4）**：旧客户端×新服务端（不带 `entityKind` 照常 PUT）；新客户端×旧服务端
  （应被拒 → 验证发布顺序：先服务端后客户端）。
- 双端同步：A 机新增（含 secret）→ B 机出现可出码；删除/分组/标签/冲突；配额拒绝→§六对账。
- Web：主密码解锁、查看/复制/增删改；验证明文不落持久化。
- 安全评审清单：密钥生命周期、日志、元数据披露（含时间）、CSP。
