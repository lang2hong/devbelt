# P3 — 控制台（Console UI）

## 1. 目标与边界

P3 提供浏览器访问的管理控制台，覆盖账户、设备、个人同步概览、平台运营和套餐展示。前端位于独立包 `apps/db-ui`，生产环境由 Fastify 同源托管；不引入 GraphQL、WebSocket 或浏览器直连数据库。

控制台只处理账户与运营元数据，绝不处理端到端加密（E2EE）材料。浏览器不得接收、生成、存储、记录或显示 DEK、同步主口令（SMP）派生材料、恢复码、签名密钥、envelope、KDF 参数或同步密文。密钥生命周期和最终同步重置仅在 VS Code 扩展内完成。

> 注（P6 更新，取代上文部分结论）：自 P6 阶段起，浏览器侧新增 **console 作用域** 的 E2EE 能力——账号本人可在 `apps/db-ui` 通过密文 feed 接口 + 内存态 DEK 解锁/解密查看验证器条目（见 `docs/阶段/P6-多设备同步与网页版.md` 与 `docs/P6-安全评审清单.md`）。因此上段「浏览器不得接收/存储/显示…同步密文」由 P6 规格取代；但「密钥生命周期与最终同步重置仅在 VS Code 扩展内完成」「后台不可见明文」仍成立。

### 1.1 P3 范围

- 账户概览：邮箱、显示名、邮箱验证状态、个人套餐和到期时间。
- 个人同步概览：初始化状态、最近同步活动、活跃记录数、密文字节用量和配额；仅使用专用聚合接口。
- 设备管理：列出和撤销本人设备；Web 控制台作为独立设备展示。
- 账户设置：修改显示名、修改登录密码；P3 不支持修改邮箱。
- 平台运营：用户/订阅查询与受控调整、审计日志、脱敏系统状态。
- 套餐展示：Free、Pro 的权益对比；支付、订单和发票仅预留入口。
- 根路径邮件落地页：邮箱验证、同步重置交接。

### 1.2 不在 P3 范围

- 浏览器内 SQL 编辑、数据库连接或任何直连用户数据库的能力。
- 浏览器内 E2EE 密钥操作、恢复或最终同步重置。
- 团队实时协作、评论和多因素认证。
- 修改邮箱；该能力需要独立的双邮箱验证设计。
- 支付下单、支付回调、订单履约、退款、订单历史和发票下载；全部属于 P4。
- 平台管理员登录用户账号或重置用户密码。

## 2. 用户、数据与权限

### 2.1 数据分级

| 数据级别 | 内容 | 控制台规则 |
|---|---|---|
| 账户/运营元数据 | 用户状态、套餐、设备数量、审计事件 | 按角色最小化展示 |
| 受限管理数据 | 用户邮箱、来源 IP 脱敏值 | 仅平台管理员的必要运营页面可见；读取要审计 |
| E2EE 材料 | 密钥、envelope、KDF、密文、恢复材料 | 浏览器和平台后台均不得接收或读取 |

### 2.2 角色权限矩阵

| 角色 | 可访问范围 | 强制限制 |
|---|---|---|
| 未登录访客 | 邮件落地页、登录、注册、套餐页 | 所有受保护 API 返回 `401` |
| 登录用户 | 自己的账户、设备、同步概览 | 不可访问其他用户和运营后台 |
| 平台管理员 | 用户、订阅、审计和系统状态的运营元数据 | 不得读取任何 E2EE 材料；高危写操作必须填写原因 |

前端隐藏或禁用入口仅用于体验；服务端角色授权始终是最终授权边界。常规 `403` 只显示无权限页，不得把有效用户强制登出。

### 2.3 平台管理员边界

平台管理员可读取运营所必需的用户元数据，包括用户邮箱、状态、订阅、设备数量；这类受限读取必须写审计日志。平台管理员不得默认读取查询文本、连接信息或扩展凭据。

若未来需要排障读取受限业务数据，必须另行设计 break-glass 流程：工单编号、明确业务理由、双人审批、最小字段、限时授权、全程审计和自动撤销。P3 不实现该流程，也不允许绕过它。

## 4. 浏览器认证与会话

### 4.1 会话原则

浏览器控制台与 VS Code 扩展使用不同 audience 的访问令牌。授权以服务端验证的 `aud`、scope、用户状态和设备会话为准；不得依赖 User-Agent、前端路径或可伪造的客户端标识区分权限。

| API 分类 | 路径/能力 | 允许 audience | 必需 scope |
|---|---|---|---|
| 共享业务 API | 本人资料、设备 | `console`、`extension` | 对应 `account.*`、`device.*` |
| 控制台专属 API | Cookie 会话、邮件流、同步概览、平台运营后台 | 仅 `console` | 对应 `console.*`、`platform.*` |
| 扩展专属 API | `/api/sync/*` 状态、记录、初始化、换钥、恢复、销毁、最终重置 | 仅 `extension` | `sync.*` |

共享业务 API 保持既有 `/api/*` 路径，不因 P3 复制为 `/api/console/*`；其 schema、权限和错误语义对两端完全一致。P3 仅为浏览器特有会话、展示聚合和运营能力增加 `/api/console/*` 路由。任何 access token 的 `aud` 不匹配或缺 scope 时返回 `403 TOKEN_AUDIENCE_FORBIDDEN` 或 `403 FORBIDDEN`。

每个用户只保留一个 `platform='web'` 的 `Web Console` 设备槽位，浏览器登录按 `(userId, platform='web')` upsert，而不是每次登录新增设备行。Web 设备不计入 `maxDevices`；该配额只计算可同步的扩展设备。浏览器在首次控制台登录前生成随机 `deviceKey` 并持久化在 localStorage：它不是 token、密钥或 E2EE 材料，清除站点数据、使用新浏览器或显式退出并清除浏览器数据后可重新生成。新 key 认领同一 web 槽位时，服务端必须原子撤销该槽位既有 refresh-token family，再写入新 key/family；因此同一用户最多一个有效 Web Console 会话，且不会积累幽灵设备或占用扩展设备配额。撤销当前 Web Console 设备后立即注销当前浏览器；撤销扩展设备不影响当前控制台。

| 凭证 | 存储与属性 | 生命周期 |
|---|---|---|
| Refresh Token | `__Host-devbelt_refresh` Cookie；`HttpOnly; Secure; SameSite=Lax; Path=/`；**无 `Domain`** | 服务端可撤销、轮换；不进入 JavaScript；Top-level 导航跟随 cookie 以支持用户点击邮件链接登录完成后 refresh 自动回跳 |
| Access Token | JavaScript 内存变量；不落 localStorage、sessionStorage、IndexedDB 或日志 | 短时有效；刷新页面后通过 refresh 恢复 |
| CSRF Token | `__Host-devbelt_csrf` Cookie；`Secure; SameSite=Lax; Path=/`；非 HttpOnly；**无 `Domain`** | 与服务端签名的会话绑定，前端仅回显到请求头；Lax 允许导航页读取 CSRF 初始化 token |
| 邮件流 Cookie | `__Host-devbelt_link_flow` Cookie；`HttpOnly; Secure; SameSite=Lax; Path=/`；无 `Domain` | 10 分钟短时有效；跨站点击邮件链接导航时携带，支持用户从邮件直接进入认领流程 |

生产环境必须 HTTPS。页面和 API 响应不得缓存 Access Token、Refresh Token、CSRF Token 或认证 JSON。

除 refresh/logout 外，受保护的控制台 API 使用内存中的 `Authorization: Bearer <aud=console access token>` 认证；共享业务 API 也可接受 `aud=extension` access token。refresh 仅使用 Refresh Cookie 签发新的 console access token。控制台写 API 在 Bearer access token 之外还必须满足 CSRF 规则，不能只依赖 Cookie。

每个 access token 必须包含不可复用的 `sessionId`、`deviceId`、`sessionVersion`、`sub`、`aud`、scope、`iat`、`exp`。服务端 `requireSession` 在每个受保护请求中核验用户状态、设备状态、refresh family/session 的撤销状态与 `sessionVersion`；该校验可使用只读缓存，但撤销/禁用事务必须同步失效所有相关缓存，缓存 TTL 不得超过 30 秒。若无法完成同步失效，生产环境必须改为每请求查权威存储。由此保证撤销设备、禁用用户和改密后的有效 access token 最长只存活到撤销事务提交，不以 JWT `exp` 为唯一失效边界。

### 4.2 浏览器认证 API 契约

所有控制台认证接口均位于 `/api/console/auth/*`，与扩展使用的 token-in-body API 分离。控制台 API 仅接受/签发 `aud=console` 令牌。

| 接口 | 请求 | 成功响应 | 规则 |
|---|---|---|---|
| `GET /api/console/auth/csrf` | 无 | `204`，签发/轮换 CSRF Cookie | `Cache-Control: no-store`；匿名可调；单 IP 120/min |
| `POST /api/console/auth/register` | `email`、`password`、`displayName?` | `{ ok: true, requiresEmailVerification: true }`；不签发任何 token、Cookie，也不创建设备记录 | 必须校验 `Origin` 和匿名 CSRF Token；邮箱规范化（trim+lowercase）、密码符合现有策略（12--128 Unicode code points，无字符类别要求）、displayName 校验同 PATCH /me；注册成功原子创建账户 + 签发验证邮件；为防枚举，重复邮箱返回相同的通用成功响应（同时向该邮箱静默发送"已有账号"提示邮件）；注册接口直接调用现有 `AuthService.register()` 语义，不复制业务逻辑；按 `IP + 规范化邮箱` 双维度限流，复用现有 MySQL `rate_limit_entries` 固定窗口计数器（注册：IP 10/h，单邮箱不单独限流但冲突路径均触发同速率邮件发送） |
| `POST /api/console/auth/login` | `email`、`password`、设备显示字段 | `{ accessToken, user }`，设置 Refresh Cookie | 必须校验 `Origin` 和匿名 CSRF Token；不要求已有 Refresh Cookie；失败统一返回 `INVALID_CREDENTIALS` 不泄露账户存在性；按 `IP + 规范化邮箱` 双维度限流，复用现有 `AuthService.login()` 双层阈值（与扩展共享同一桶）：15 分钟窗口内同 email/IP 失败 5 次后触发 429（正确密码永远不被拒绝，不做账户锁定），失败 20 次触发 Argon2 滥用闸在密码校验前廉价拒绝，响应带 `Retry-After`；未验证邮箱用户登录失败，返回与凭证错误相同的 `INVALID_CREDENTIALS` 不泄露邮箱验证状态 |
| `POST /api/public/link-flows/resend-verification` | 匿名：body `{ email }`；已登录：无 body（发往绑定邮箱） | `{ ok: true }` | 匿名重发需 CSRF + `Origin` 校验、邮箱参数；已登录用户必须通过 console session 认证；不泄露邮箱是否存在/已验证（不存在/已验证均返回相同成功）；直接调用现有 `AuthService.resendVerification()` 语义（匿名路径）或内部等价逻辑（已登录路径）：每小时内仅对"存在且未验证"用户作废旧 token、重建并重新发送；按 `IP + 邮箱` 双维度限流，复用现有阈值：单 IP 3/h，单邮箱 3/h；响应带 `Retry-After` |
| `POST /api/console/auth/refresh` | 无 body | `{ accessToken }`，轮换 Refresh Cookie | 必须带 CSRF 头、Cookie 和同源 `Origin`；失败清除 Refresh Cookie；每 session 30/min |
| `POST /api/console/auth/logout` | 无 body | `{ ok: true }`，撤销当前 family 并清 Cookie | 必须带 CSRF 头；幂等成功；每 session 10/min |

CSRF 校验仅适用于**浏览器携带 Refresh/mail-flow Cookie 的写请求**，纯 Bearer token 请求（包括所有 `aud=extension` 扩展调用）天然无 CSRF 风险，跳过 CSRF 校验，仅校验 audience、scope、session/device 有效性和用户状态。具体规则：
1. 所有 `aud=console` 的浏览器写请求（POST/PATCH/PUT/DELETE）：必须通过 HTTPS、同源 `Origin` 和 `X-CSRF-Token` 与 CSRF Cookie 的会话绑定校验。
2. refresh/logout 以 Refresh Cookie 取得 session；其他控制台写 API 必须验证 Bearer session，且 Bearer `sessionId` 必须与 CSRF Cookie 绑定的 session 相同。
3. login、公开邮件流接口（除了已登录后的邮件流消费接口）使用由 `GET /api/console/auth/csrf` 取得的匿名 CSRF Token；认证成功后轮换为会话绑定 Token。
4. 所有 `aud=extension` 的扩展调用：不校验 CSRF，仅以 Bearer token 的 audience/scope/session 为权威。
CSRF Token 采用签名双提交模式：服务端验证 Cookie 签名、会话绑定和请求头常量时间相等；不得只比较两个客户端可伪造值。

登出、改密、设备撤销、禁用用户和邮件流完成时，服务端必须用同名、`Path=/`、无 `Domain`、`Max-Age=0` 的 `Set-Cookie` 同时清除相关 `__Host-` Cookie；前端清理内存 access token 只是体验兜底，不能替代服务端撤销。

### 4.3 401、403 与会话变更

| 情况 | 前端行为 |
|---|---|
| Access Token 过期 | 对原请求最多静默 refresh 一次；成功后重放一次幂等读请求，不自动重放写请求 |
| Refresh 失败、用户禁用、当前设备被撤销 | 清空内存 token，调用本地 Cookie 清理兜底，跳 `/login?returnTo=`；展示会话已失效 |
| 一般资源/管理员权限 `403` | 保留会话，显示无权限页或操作提示 |
| 反枚举 `404` | 保留会话，显示资源不可访问；不得区分不存在与无权访问 |

`returnTo` 只允许本站相对路径、以 `/` 开头且不含协议/主机名；登录页必须拒绝开放重定向。包含一次性 token 的原始 URL 不能作为 `returnTo` 保存，见第 5 节的邮件流规则。

### 4.4 高风险账户操作

- 显示名：长度 1--100 个 Unicode 字符，去除首尾空白、控制字符和零宽字符；trim 后不能为空串；更新使用 `PATCH /api/console/me`，成功后返回更新后的当前用户（含新 displayName）。仅记录“显示名已修改”审计事件，不记录旧/新值。
- 改密：要求当前密码和符合现有密码策略的新密码。成功时原子撤销该用户全部 refresh-token family（包括当前控制台），清除浏览器 Cookie 和内存 token，返回 `PASSWORD_CHANGED_RELOGIN_REQUIRED`，前端跳登录页；向已验证邮箱发送不含敏感信息的安全通知。
- 禁用用户：平台管理员提交原因后，原子修改状态、撤销该用户全部会话；被禁用用户下一次请求收到 `USER_DISABLED` 并退出。

## 5. 一次性邮件链接与同步重置交接

### 5.1 通用安全规则

邮件落地页为独立 HTML entry，不使用第三方脚本、字体、图片、埋点或错误上报。其响应必须至少带：

- `Referrer-Policy: no-referrer`
- 严格 CSP：`default-src 'self'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'; object-src 'none'`，仅对构建产物所需脚本/style 放行
- `Cache-Control: no-store`
- 不记录 URL query 的应用、代理、分析和错误日志策略

页面启动后先从 URL 读取 token，并立即调用 `POST /api/public/link-flows` 认领该链接；请求 body 为 `{ type, token }`，服务端仅保存 token hash/目标记录引用，不保存明文。认领成功后服务端签发 10 分钟有效的 `__Host-devbelt_link_flow` Cookie（`HttpOnly; Secure; SameSite=Lax; Path=/`；无 `Domain`），Cookie 值为服务端签名的随机 opaque nonce（32 字节 base64url），服务端仅存储该 nonce 的 SHA-256 hash；页面随即执行 `history.replaceState` 清除 query，再加载业务逻辑。token 绝不进入 localStorage、sessionStorage、IndexedDB、分析事件、错误事件或 `returnTo` 参数。

邮件流 Cookie 是短时、不可猜测、服务端可撤销的 opaque reference；它只代表“持有过有效邮件链接”，不代表登录态，也不直接授予账户权限。服务端必须持久化 `mail_flows` 表，字段如下（UTC `DATETIME(3)`，所有 token 只存 hash）：

| 字段 | 约束 |
|---|---|
| `id` | `BIGINT UNSIGNED` 主键 |
| `type` | `ENUM('verify-email','sync-reset')` |
| `target_token_hash` | `BINARY(32)`；认领时传入 token 的 SHA-256，对应原 token 表记录 |
| `target_record_id` | `BIGINT UNSIGNED`；解析后对应 token 表行 id（邮箱验证为 `email_verification_tokens.id`，同步重置为 `personal_sync_reset_tokens.id`） |
| `user_id` | `BIGINT UNSIGNED NULL`；认领时未知用户（未登录）为 `NULL`，完成登录绑定或已认领时写入 |
| `nonce_hash` | `BINARY(32)` 唯一；Cookie nonce 的 SHA-256 |
| `status` | `ENUM('issued','consumed','expired','revoked')`；一次邮件流只能消费一次 |
| `expires_time` | 签发后 10 分钟 UTC；到期后不可消费 |
| `consumed_time`、`create_time`、`update_time` | UTC `DATETIME(3)` |

唯一索引：`nonce_hash`；查询索引：`(target_token_hash, status, expires_time)`、`(user_id, status, expires_time)`。

服务端必须按 `type` 在对应 token 表中解析 hash，禁止类型混用：
- `type` 必须是枚举值 `verify-email`、`sync-reset` 之一；未知类型返回 `422 VALIDATION_FAILED`，拒绝处理。
- `token` 必须是 URL-safe base64url、长度恰好 43 个字符（32 字节随机值编码后长度）；过长、非法字符、编码失败直接 `422`，不计算 hash、不写审计事件（仅入指标计数）。
- 认领是幂等操作：同一浏览器（由签名 Cookie nonce 识别）重复认领同一有效 token 时返回同一已签发 mail-flow，不重复创建记录、不重复发邮件；同一 token 被不同 nonce 重复认领时，若该 token 仅允许单次消费（如 sync-reset）则后续认领返回 400/401，若允许多次只读结果（已消费的邮箱验证）则返回只读幂等流。
认领接口必须校验同源 `Origin`、`Content-Type: application/json`、和 `Accept: application/json`；以 token possession 为前提，并按 `endpoint + IP + token_hash` 维度限流：单 IP 每秒 10 次、每分钟 60 次；同一 token hash 每分钟 5 次。认领必须记录日志（脱敏），但不要求会话 Cookie 或 CSRF。若认领网络失败，当前页只可用内存 token 重试；刷新、关闭或重新打开页面后不恢复 token，统一显示“链接需要重新打开，请从原邮件重新进入”。一旦认领成功，后续登录可跨独立 HTML 页面继续（通过 Cookie nonce 绑定已创建的 mail_flow 行），浏览器不再持有原始 token。

### 5.2 邮箱验证

`/verify-email?token=` 完成邮件流认领后调用 `POST /api/public/link-flows/verify-email`。服务端以 link-flow 引用查找并消费对应验证 token；未消费有效 token 返回 `{ ok: true }`，已消费 token 返回 `409 EMAIL_VERIFICATION_ALREADY_CONFIRMED`，前端展示“该链接已使用，邮箱已验证”。过期、撤销、不存在或邮件流失效统一返回 `401 EMAIL_VERIFICATION_INVALID`。浏览器不再将原始 token 放入请求路径。invalid/expired 页面必须提供 `POST /api/public/link-flows/resend-verification` 的“重新发送验证邮件”入口，匿名用户填写邮箱并使用切片 1 的匿名 CSRF；已登录用户不提交邮箱，服务端使用绑定邮箱。

验证成功后服务端撤销邮件流 Cookie。若页面在成功前刷新，Cookie 仍有效时可继续完成；Cookie 已失效则提示重新打开邮件。网络/5xx 失败允许在 Cookie 未失效期间重试。

切片 1 新增 link-flow 不替代或删除既有扩展路径：`POST /api/auth/email-verifications/:token/confirm` 与 `POST /api/auth/email-verifications`（重发）继续保留，后者仍是 `loginFormView`/`syncClient` 的活跃调用路径。两端保持其既有匿名 token/body 契约，切片 1 不得改为 Bearer-only、不得要求 `aud=extension`。仅未来新增的、由已认证扩展发起的验证后操作才校验 `aud=extension`。

### 5.4 同步重置两阶段交接

浏览器绝不调用 `/api/sync/reset-after-loss`。邮件 token 只用于认领重置挑战，最终 E2EE state 只由扩展提交。

1. 用户打开 `/sync-reset?token=`，页面按 5.1 认领并清理 URL；未登录时进入登录流程，邮件流 Cookie 保留短时交接状态（mail_flow.user_id 在登录成功后绑定到 authUserId，不在客户端暴露）。
2. 已登录页面调用 `POST /api/console/link-flows/create-sync-reset-handoff`，body 为空；请求需 `aud=console`、CSRF 和当前用户会话，服务端通过 Cookie nonce 解析 mail_flow。
3. 服务端事务锁序（**必须严格按此顺序加锁以避免死锁**）：
   a. 非锁定读取 mail_flow（按 Cookie nonce hash）→ 得到 `type`、`target_record_id`（即 `personal_sync_reset_tokens.id`）、`user_id`（必须与 authUserId 一致）、状态；拒绝非 `sync-reset` 类型、已消费、已过期的 flow。
   b. `SELECT ... FOR UPDATE` 锁定 `personal_sync_reset_tokens` 行（`id = target_record_id`）→ 校验未消费、未撤销、未过期、`user_id === authUserId`。
   c. `SELECT ... FOR UPDATE` 锁定 mail_flow 行 → 二次校验未消费、未过期、用户匹配（防止 a 到 c 之间被并发消费或被别的用户绑定）。
   d. 撤销同一 reset token 下所有现有 `issued/processing` handoff（置 `revoked`）。
   e. 创建新的 15 分钟有效、单次消费的随机 `handoffTicket`，数据库仅保存 SHA-256 hash 到 `sync_reset_handoffs`，绑定 `reset_token_id` 和 `user_id`。
   f. 将 mail_flow 置 `consumed`（消费邮件流，防止同一 flow 重复签发多个 handoff）。
   此步骤不消费原 reset token；锁序方向（reset token → mail_flow → handoff 子操作）与扩展最终消费接口的锁序（reset token → handoff，见 P2）保持一致（均先锁 reset token 作为最高优先级锁），避免跨接口并发死锁。
4. 成功响应仅返回 `{ openUri: "vscode://devbelt.sync/reset-after-loss?handoffTicket=...", expiresTime }`。浏览器立即提供“在 VS Code 中继续”按钮；ticket 仅保留在按钮 href 内存，不持久化、不显示、不复制。扩展 URI handler、扩展日志和错误上报必须脱敏该 query 参数（日志中只打印 ticket hash 前缀 `handoff:<8hex>...`）。
5. **深链残留风险（必须在扩展和浏览器侧双重缓解）**：
   - 浏览器通过 `window.location.assign(openUri)` 唤起 VS Code 后立即从内存移除 `openUri` 与 ticket，并调用 `history.replaceState` 将当前页改为结果页。
   - 扩展 `vscode://devbelt.sync/reset-after-loss` handler 接收 ticket 后**只放入内存变量**，立即进入消费流程；绝不写入 extension log（仅脱敏记录 hash 前缀）、绝不写入 globalState/SecretStorage、绝不弹出包含 ticket 的任何 UI。消费成功或终态失败后立即从内存移除。
   - 操作系统/浏览器历史、最近打开列表可能残留带 ticket 的 URI；ticket 15 分钟过期、单次消费、且绑定 user，使用后即失效。若用户本机被恶意软件窃取 ticket，攻击窗口仅限 15 分钟且只能在同一用户登录的扩展中消费一次，不会泄露密钥材料（newState 由扩展本地生成不经过网页）。
   - 若唤起 VS Code 失败，页面提供“我已打开 VS Code，重试”按钮（仅内存复用 ticket；注意：由于 mail_flow 已被步骤 3f 消费，重试必须依赖已签发的 handoff ticket，页面不得允许绕过 handoff 重新申请 ticket）；并给出“重新发送重置邮件”入口。
6. 扩展收到深链后要求其自身 `aud=extension` 登录态，再调用 `POST /api/sync/reset-after-loss`，body 为 `{ handoffTicket, newState }`。服务端严格按 P2 定义的锁序执行：先 SHA-256 handoffTicket 非锁定查询 handoff → `FOR UPDATE` 锁关联 reset token 行 → `FOR UPDATE` 锁 handoff 行（校验 ticket/user/过期/撤销状态）；若 handoff 处于 `processing` 超过 60 秒自动回退为 `issued`（崩溃恢复）；校验通过后在同一事务内消费 ticket、消费原 reset token、tombstone 旧 records、写入新 E2EE state，并持久化完整 `StateDto` 结果用于幂等重放。详细事务流程与错误码见 P2 §控制台重置交接协议。
7. 成功后服务端返回完整新 `StateDto`，扩展显示重置完成；ticket 或 reset token 已消费时返回统一 `400 SYNC_RESET_HANDOFF_INVALID`，processing 中返回 `409 SYNC_RESET_IN_PROGRESS` 带 `Retry-After: 2`。扩展只可在网络/5xx 失败或 IN_PROGRESS 时以同一未消费 ticket 重试（最多 3 次）；业务校验失败不得重试。

若本机未安装扩展或深链唤起失败，浏览器说明“请安装/打开 DB Client VS Code 扩展后重新申请重置邮件”。P3 不提供 ticket 手工复制、二维码或浏览器内备用重置，避免 ticket 扩散。

## 6. 控制台 API 契约

控制台 API 统一返回 JSON。ID 以十进制字符串传输；时间使用 ISO 8601 UTC；未知字段一律拒绝。所有请求必须携带 `Accept: application/json`；写请求必须携带 `Content-Type: application/json; charset=utf-8`，服务端必须拒绝 `application/x-www-form-urlencoded`、`multipart/form-data` 或其他非 JSON Content-Type，返回 `415 UNSUPPORTED_MEDIA_TYPE`。

新增 `/api/console/*` 与 `/api/public/*` 的错误响应统一使用信封：`{ "error": { "code": "ERROR_CODE", "message": "用户友好提示" } }`；成功响应按契约返回，不包裹统一 envelope。既有共享 `/api/*` 维持平铺 `{ "code": "ERROR_CODE", "message": "用户友好提示" }`，不得为控制台改动扩展既有消费者的错误形状。所有响应的关联 ID 统一由 `X-Request-ID` 响应头提供，不写入两种错误 body。分页 cursor 使用不透明 base64url 编码，包含 `(lastId, lastTime)` 与服务端签名，前端不得解析或拼装 cursor；非法/过期/签名失败的 cursor 返回 `422 INVALID_CURSOR`。列表接口使用 cursor 分页，默认 50、最大 100，排序固定为 `(createTime DESC, id DESC)` 或契约注明的稳定排序；响应形状为 `{ items, nextCursor }`。所有适用第 6.1 节的写接口返回修改后的摘要或 `{ ok: true }`，并接受 `Idempotency-Key`（UUIDv4，长度 22-48 字符）以保证用户触发的高风险写操作可安全重试。

| 接口 | 权限 | 输入/输出与规则 | 限流 |

`/api/sync/state`、records、初始化、换钥、恢复、销毁和最终重置只接受 `aud=extension`，控制台 audience 一律返回 `403 TOKEN_AUDIENCE_FORBIDDEN`。这既保证浏览器不接触 E2EE 材料，也不依赖前端“不调用”的约定。

错误码的 UI 映射：`400` 为客户端可理解的业务错误（邮件链接无效等，展示详情）；`401` 表示认证/会话失效；`403` 表示已认证但无权限；`404` 表示资源不可访问；`409` 表示可解释的状态冲突或幂等结果；`415` 为非法 Content-Type；`422` 表示字段校验失败；`429` 表示限流，响应必须包含 `Retry-After: <seconds>` 头；`5xx` 只显示可重试的通用错误。Console UI 对每个 4xx/5xx 以 `error.message ?? message` 读取两种契约的用户提示，缺失时使用通用文案；不得把服务端原始错误或堆栈直接显示给用户。

### 6.1 写请求幂等契约

用户可重复触发且会改变服务端状态的控制台/共享写接口必须支持 `Idempotency-Key`，除改密、登录、refresh、logout、邮件 token 认领和最终同步重置外。客户端生成 UUIDv4；同一次业务意图在网络/5xx 后重试时复用原 key，不得为重试生成新 key。

服务端创建 `idempotency_receipts`，唯一键为 `(actor_user_id, session_id, method, normalized_path, idempotency_key)`；`normalized_path` 不含 query，路径参数使用规范十进制形式。写入前计算请求 body 的规范 JSON SHA-256 摘要，规则如下：

| 情况 | 服务端行为 |
|---|---|
| 首次请求 | 在同一业务事务内创建 `processing` receipt，完成业务写入后写入 status、HTTP status、响应体摘要/可重放响应 |
| 同 key、同摘要、已完成 | 不再执行业务写入，返回第一次的完整 HTTP status 和响应 body |
| 同 key、不同摘要 | 返回 `409 IDEMPOTENCY_KEY_REUSED` |
| 同 key、同摘要、仍 processing | 最多等待 5 秒；仍未完成返回 `409 IDEMPOTENCY_IN_PROGRESS` 并附 `Retry-After: 1` |
| 事务回滚 | receipt 与业务写入一同回滚；客户端可用相同 key 重新提交 |

receipt 在线保留 24 小时；订阅调整和禁用用户保留 30 天，满足审计关联与人工排障。清理任务分批删除过期 receipt，删除本身写系统审计摘要。邮件流和最终同步重置使用各自的单次消费/结果 receipt，绝不复用登录用户幂等空间。

### 6.2 订阅与平台写事务

平台订阅调整在一个事务内执行：锁定订阅行与套餐行 → 校验 `expectedVersion`、目标套餐 active 与时间范围 → 重写 `entitlement_snapshot` → 递增 `subscriptionVersion` → 写审计事件与 idempotency receipt。个人套餐调整不得改变已完成订单事实。`periodEndTime` 必须为未来 UTC 时间或 `null`（永久/未设到期），不能早于 `periodStartTime`。

所有平台高危写操作都必须在提交前写不可省略的 `reason`（1--500 Unicode 字符）；原因进入受限审计 metadata，不向普通用户展示。平台管理员不能调整自身平台角色，也不能通过订阅接口改变资源访问权限。

## 7. 核心交互与页面状态

### 7.1 账户与设备

- 设备页显示平台、名称、客户端版本、最后活跃时间和创建时间。登录 IP 仅在后续有合规数据模型时增加；P3 不承诺存储或展示 IP。
- 撤销设备需要二次确认。若撤销当前 Web Console 设备，操作成功后立即跳登录页；若目标已撤销，返回幂等成功。
- 改密、禁用用户、调整订阅均需二次确认；平台写操作额外要求原因。

### 7.3 通用状态

每页必须实现加载、空、错误、无权限和成功状态。读请求网络/5xx 错误显示重试；写请求失败保留用户输入但不自动重放；无权限页面不显示不可用操作入口。所有异步失败必须被捕获，禁止白屏或未处理 Promise rejection。

## 8. 静态部署、安全头与邮件链接

构建产物包含控制台 SPA、公开页和三份独立邮件入口 HTML。邮件页是独立 entry，不走 `/console/*` SPA fallback。生产环境 CORS **必须禁用**：不注册 `@fastify/cors` 或设置为 `origin: false`，控制台所有请求同源；`Access-Control-Allow-Origin` 不得返回 `*`。开发环境下 CORS 仅允许 Vite dev server 源 `http(s)://localhost:5173`，且不得带 credentials。

服务端路由优先级固定为：

1. `/api/*` API；
2. 根路径公开页和邮件页；
3. 已存在的静态资源文件；
4. `/console/*` 的 `console/index.html` SPA fallback；
5. 其他路径返回 404。

所有 HTTP 响应必须统一设置以下安全头（公开页/SPA 页/API 均适用，开发 profile 可放宽 CSP 但不能禁用其他头）：

| 头 | 值 | 说明 |
|---|---|---|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | 生产强制 HTTPS |
| `X-Content-Type-Options` | `nosniff` | 禁止 MIME 嗅探 |
| `X-Frame-Options` | `DENY` | 禁止 iframe 嵌入 |
| `Referrer-Policy` | `no-referrer` | 全局禁 Referrer；邮件页已设，API/SPA 也必须设 |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=()` | 禁用无关浏览器能力 |
| `Content-Security-Policy` | 见下 | 静态页面严格 CSP，API 响应 `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'` |

- 邮件入口/公开页 CSP：`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'`（仅构建产物 inline style 白名单）；`img-src 'self' data:;` 如无图片则 `'none'`；`connect-src 'self'`；`frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none';`。
- `/console/*` SPA CSP 同上，Vite 构建产物的 hash script/style 经 CSP 允许；不得使用 `unsafe-eval`。
- 所有 Cookie 设置 `Secure; Path=/;`（`__Host-` 前缀自动包含 Path=/ 且无 Domain，显式声明以增强可读性）。

`/console` 规范化重定向到 `/console/`。带内容 hash 的 JS、CSS、字体和图片使用 `Cache-Control: public, max-age=31536000, immutable`；HTML、公开页和邮件页使用 `Cache-Control: no-store`；认证与 token 相关 API 使用 `Cache-Control: no-store` 且 `Pragma: no-cache`。带文件扩展名但不存在的请求不得落到 SPA fallback。

生产环境的 `DEVBELT_DB_SMTP_BASE_URL` 为控制台 HTTPS 域名。开发环境优先使用受信本地证书的 `https://localhost:5173`，以覆盖 `Secure`/`__Host-` Cookie 的真实行为；只有本地开发 profile 可允许 `http://localhost:5173` 并使用不带 `__Host-` 前缀、`Secure=false` 的显式 `dev_` Cookie 名称。该例外必须由 `NODE_ENV=development` 和 loopback host 双条件限制，禁止出现在测试、预发和生产环境。

`DEVBELT_DB_SMTP_BASE_URL` 只负责邮件链接前缀；部署前自动校验三个邮件路径均可访问（HEAD/GET 返回 200）。服务器、CDN、反向代理、应用日志和错误上报必须脱敏或移除 `token`、`resetToken`、`handoffTicket`、`password`、`newState`、`Authorization`、Cookie、CSRF 等敏感字段；query string 在应用入口即从 URL 和日志上下文剥离。

## 9. 审计日志

审计事件覆盖：认证（登录成功/失败、登出、改密、设备撤销）、身份与邮件（验证、重发）、同步安全事件（初始化、换钥、恢复、销毁、重置挑战和重置完成）、平台受限读取、订阅调整，以及 P4 的支付/退款事件。

每条记录至少包含：`eventTime`、`actorUserId`（系统任务为 `null`）、`actorRole`、`eventType`、`targetType`、`targetId`、脱敏 `sourceIp`、`requestId`、`result`、可空失败码和高危操作原因。审计 metadata 使用事件类型白名单，绝不记录密码、token、哈希、密钥、密文、KDF、验证码、支付敏感字段、数据库凭据、原始资源内容或显示名旧/新值。

审计表为 append-only：应用运行账号对该表只拥有 `INSERT` 和 `SELECT`，没有 `UPDATE`/`DELETE`；不暴露修改/删除接口；导出本身生成审计事件。系统清理任务使用独立受限凭证，按保留策略写入归档后再批量删除。在线保留至少 1 年；到期后按合规要求归档或销毁，并记录执行摘要。审计查询和导出只向平台管理员开放，且均被审计。

平台读取审计采用会话窗口聚合：同一 `actorUserId + sessionId + eventType + targetType + targetId + normalizedFilterDigest` 在 5 分钟窗口内只记录一条 `read` 事件，并累加 `accessCount` 和最后访问时间；导出、订阅调整、禁用/启用、角色/成员变更和所有失败的高危写入始终逐次记录，不做聚合。分页、刷新、前端轮询必须使用同一过滤摘要，避免日志量失控。

## 10. 实施切片与交付顺序

P3 按以下五个可独立验收、可受控发布的切片实施。除切片 5 外，任何切片不得修改已交付的 `/api/sync/reset-after-loss` `{ resetToken, newState }` 协议、扩展同步重置客户端或 URI handler。每个切片只创建自身实际需要的 schema 和接口；不得依赖未来切片的表、角色或会话能力。

### 10.1 切片 1：邮件 link-flow 与 verify-email 返工

**范围**：创建 `mail_flows` 基础表、基础审计表/writer、匿名 CSRF bootstrap；交付 `verify-email` 类型的 `POST /api/public/link-flows`、`POST /api/public/link-flows/verify-email`、`POST /api/public/link-flows/resend-verification` 与重写后的 `/verify-email` 独立邮件页。邮件页最小托管、`no-store`、严格 CSP、`Referrer-Policy: no-referrer`、URL query 脱敏和公开 API 的最小安全头随本切片交付。

`mail_flows` 的 schema 可预留 `sync-reset` type，但本切片只启用 `verify-email`；不得认领同步重置 token、签发 handoff ticket、调用同步 API 或处理 `newState`。审计 writer 必须从本切片起可用，认证与邮件安全事件不得等切片 4 再补写。

既有 `POST /api/auth/email-verifications/:token/confirm` 与 `POST /api/auth/email-verifications` 保持扩展匿名调用兼容；本切片只新增 link-flow 路径，不删除、重定向或将旧路径改为 Bearer-only。

**依赖与验收**：依赖现有注册、验证 token、SMTP 发送能力；不依赖浏览器登录会话。验证邮件认领、消费、重复消费、过期、刷新后继续、网络重试、invalid/expired 后重发、URL 清理与日志脱敏必须有端到端测试。

### 10.2 切片 2：浏览器认证与会话

**范围**：实现 console/extension token audience 与 scope 分离、`sessionId`/`deviceId`/`sessionVersion` 会话核验、Cookie Refresh 会话、匿名与会话绑定的 CSRF、`/login`、`/register`、`/api/console/me` 与 console auth API。注册不签发会话，邮箱验证后才允许登录；登录、刷新、改密、撤销设备和禁用用户必须即时撤销或失效相关 session。

切片 1 的匿名 CSRF bootstrap 是本切片的基础；本切片将其升级为与 `sessionId` 绑定的双提交 CSRF，并实现 §4.1 的单 Web Console 设备槽位。aud 强校验上线时，仍存活的无 `aud` access token 按默认 15 分钟 TTL 返回 `403 TOKEN_AUDIENCE_FORBIDDEN` 是可接受的短暂升级窗口；不引入“缺 aud 即视为 extension”的宽限分支，实施报告必须记录该窗口与观测结果。切片 2 不实现账户控制台页面、平台管理员能力或同步 handoff。

**依赖与验收**：依赖切片 1 的公开邮件页与基础审计 writer。验证 `aud`/scope 拒绝、未验证邮箱登录拒绝、Cookie 属性、Origin/CSRF、refresh 轮换、session 撤销、设备撤销和账户禁用的自动化测试。

### 10.3 切片 3：用户侧控制台

**范围**：交付 `/console/*` SPA 完整托管、全局页面安全头、静态资源缓存策略和所有用户页面：账户、设备、同步概览。

本切片创建 `idempotency_receipts` 与通用幂等处理。

邮件页最小安全头已在切片 1 交付；本切片负责 `/console/*` 的 CSP、SPA fallback、静态 JS/CSS/font/image 的内容 hash 缓存、HTML/API 的 `no-store` 和全局安全头接线。切片 5 只验证部署环境未削弱这些规则，不重复实现第 8 节安全头。

**依赖与验收**：依赖切片 1、2。验证账户角色矩阵、E2EE 数据不可达、静态路由优先级与缓存/安全头。

### 10.4 切片 4：平台运营与审计查询

**范围**：创建 `users.role`、订阅版本字段和平台查询索引；实现 `requireAdmin`、平台用户/订阅 API、审计查询与导出。审计事件写入由切片 1 已提供，本切片只增加平台受限读取的聚合规则、查询、筛选、导出及其审计，不创建第二套审计 writer。

`DEVBELT_DB_PLATFORM_ADMIN_EMAILS` 仅可作为首次受控引导来源：应用启动或受控初始化任务读取，使用与注册相同的 trim + lowercase 规范化规则；不得暴露给 API、前端或日志。生产环境该配置缺失时平台运营功能必须 fail-closed，禁止将首个注册用户或任意普通用户自动提升为管理员。首次引导、角色变更、撤权和失败尝试均写审计；每次授权以服务端当前角色为准，不信任 access token 中长期缓存的管理员声明。

**依赖与验收**：依赖切片 2；可在切片 3 后或与切片 5 调整顺序，但不得与切片 2、5 合并。验证 fail-closed 引导、平台权限隔离、受限读取审计、订阅 optimistic concurrency、导出边界与高危操作幂等。

### 10.5 切片 5：sync-reset handoff 与部署硬化

**范围**：这是唯一允许改动已交付同步重置协议的高风险切片。创建 `sync_reset_handoffs`；启用 `sync-reset` mail-flow；实现浏览器 handoff 签发与 VS Code 深链；将 `/api/sync/reset-after-loss` 改为仅接受 `aud=extension` 的 `{ handoffTicket, newState }`；实现完整 `StateDto` 结果 receipt、并发消费、崩溃恢复和扩展 URI handler。本切片不得和低风险 UI、认证或平台运营工作混合提交。

旧 `{ resetToken, newState }` 端点已经存在外部扩展消费者，替换必须受控进行：先发布具备深链和 handoff 能力但受功能开关保护的新扩展与服务端能力；切换时必须二选一并记录在发布 Runbook 中：保留旧请求 schema 与行为直至全部已发旧 reset token 的最大有效期结束，或在切换事务中统一撤销所有未消费旧 token。前者到期后、后者切换后，旧调用必须返回明确、可行动的升级/重新申请挑战错误；不得静默降级或将 reset token 解释为 handoff ticket。确认最小支持扩展版本覆盖后，再移除旧请求 schema、路由分支、客户端调用和遗留 token 流程；同一旧挑战不得同时处于保留和撤销策略。

本切片负责第 11 节的部署收尾：功能开关、生产环境安全头/缓存验证、监控告警、Runbook、备份/恢复演练与发布/回滚演练。它验证切片 1--3 已交付的安全头未被 CDN、反向代理或部署配置削弱，不重复实现静态托管和安全头逻辑。

**依赖与验收**：依赖切片 1、2 以及 P2 定义的 state/record 重置基础；切片 3/4 不构成技术前置。验证旧协议受控退役、错误扩展版本、错误用户、过期/撤销、双消费、响应丢失重放、processing 超时恢复、锁序死锁、浏览器永不接触 `newState`、扩展 URI 参数脱敏和灾难恢复演练。

切片 1--3 实现过程中的非破坏性语义注记（仅澄清实现口径，不改动已交付契约）：

| 主题 | 注记 |
|---|---|
| bind 端点（消费前置） | `/api/console/link-flows/bind` 用于「已登录用户打开邮件链接、绕过登录时绑定」场景：消费 `sync-reset` 前必须先调用此接口，凭 link-flow Cookie nonce 把 held mail-flow 绑定到当前 authUserId；受 Origin 同源 + session-bound CSRF 保护。绑定失败保留 Cookie（业务终态除外）；消费端点会二次校验归属。 |

## 11. 生产运行与发布

### 11.1 健康检查

提供两个健康端点：
- `GET /health/live`：进程存活，200 返回 `{ status: "ok" }`，不连接 DB，用于 k8s liveness probe。
- `GET /health/ready`：就绪检查，验证 MySQL 连接池可连通、schema 已初始化到最新版本、必需依赖已初始化；返回 200/503，含各依赖状态简表 `{ db: "ok", schema: "ok", mail: "ok" }`（不泄露连接串）；用于 readiness probe 和负载均衡摘除。
健康端点不得设置任何 Cookie，`Cache-Control: no-store`，响应 < 500 字节；禁止暴露版本号、hostname、数据库名等信息，版本号走独立的受控 `/api/console/version`（仅平台管理员）。

### 11.2 Schema 初始化与数据安全

当前处于开发阶段，无生产数据迁移负担。每个实施切片只创建其范围内新增的 schema，以新增 migration 文件一次性初始化；不设计旧新 schema 兼容层或无关字段退役流程：

- schema 归属固定：切片 1 创建 `mail_flows`、审计表；切片 2 创建 session/version 相关字段；切片 3 创建 `idempotency_receipts`；切片 4 创建 `users.role`、订阅版本字段和平台查询索引；切片 5 创建 `sync_reset_handoffs`。切片不得预建或依赖未来切片的表；同一切片内的 migration 在同一 PR 创建并执行，不做灰度/分批 DDL。
- 所有时间字段使用 UTC `DATETIME(3)`；所有 token/ticket/nonce 只存固定长度 SHA-256 hash，不存明文；敏感表必须声明必要的唯一键、查询索引和外键约束（允许无外键的逻辑引用需在注释中说明原因）。
- 首次启动必须执行 schema 初始化到最新版本才能接受请求；`/health/ready` 检查 schema 版本一致性。Schema 初始化失败时进程启动失败，不得在缺失表/字段的情况下降级运行。
- 审计、mail flow、handoff 和 idempotency 表的清理任务使用独立受限账号执行，只允许 DELETE 过期数据，不允许 UPDATE 业务字段；清理分批执行，单次不超过 1000 行，避免长事务。

### 11.3 可观测性与告警

日志采用结构化 JSON，最少包含 `requestId`、`timestamp`、`route`、`method`、`status`、`latencyMs`、`userId`（如有、脱敏为 hash 或 ID）、`sessionId` 摘要、`errorCode`（如有）；不得记录请求/响应原文、Cookie、Authorization 头、query token、密码、资源 content、E2EE 密文/密钥/信封、handoffTicket/resetToken/CSRF/Idempotency-Key 原文。错误日志只记录 error name、code 和 stack 的一帧摘要，stack 仅进入非用户访问的服务端 error log channel（同样脱敏）。

请求链路必须注入 `X-Request-ID`：若请求未携带，服务端生成 UUIDv4 放入响应头 `X-Request-ID` 并贯穿所有日志；前端读取后在错误上报中附带，用于排障。请求速率和错误率指标按 `(route, method, status_code)` 维度打点。

必须发布以下指标与告警：

| 类别 | 指标 | 告警条件 |
|---|---|---|
| 可用性 | `/health/ready` 成功率、HTTP 5xx 比例、p95/p99 延迟 | 5 分钟窗口健康检查失败；5xx > 1% 持续 3 分钟；p95 超 SLO 阈值 |
| 认证 | 登录成功/失败率、refresh 失败率、CSRF/Origin 拒绝数、session 撤销数、Cookie 签发失败率 | 失败率突发偏离 7 日基线；CSRF 拒绝数突增（CSRF 攻击迹象） |
| 邮件流 | link-flow 认领/完成/过期率、handoff 创建/消费/过期/失败率 | 完成率异常下降；认领或消费失败率异常升高；过期率 > 30% 说明邮件/页面断裂 |
| 同步重置 | reset challenge、handoff、最终 reset 成功/失败/重试数 | 最终 reset 失败率 > 5%；同用户重复失败 > 3 次/小时；重置成功到消费完成 p95 > 60s |
| 数据与运营 | schema 初始化状态、审计写入失败、idempotency receipt 清理滞后、DB 连接池饱和度、慢查询数、限流命中数 | schema 初始化失败；审计写入失败；清理延迟 > 24h；池使用 > 80%；p99 查询 > 1s 持续 5 分钟 |
| 安全 | 匿名接口限流触发速率、账号枚举模式、大量无效 token 尝试 | 单 IP 限流命中 > 100/min；同一 IP 对多账号登录失败；大量 401 对 link-flows（token 枚举） |

告警通知中只包含 requestId、匿名化聚合信息和错误码；需要排障时通过受控日志查询关联，不在通知正文发送用户邮箱、token 或业务内容。所有告警必须绑定 Runbook，包含验证步骤和回滚开关指引。

### 11.4 发布、回滚与功能开关

- 控制台前端与服务端通过 `consoleApiVersion` 协商；前端只能调用当前及前一个兼容 API 版本。邮件入口需要至少保留两个前端发布版本，覆盖邮件发送与用户点击之间的部署窗口。
- 平台运营、邮件流、浏览器认证、同步 handoff、支付占位均有独立服务端功能开关。关闭开关时返回明确 `503 FEATURE_TEMPORARILY_DISABLED`，不回退到旧的弱安全链路。
- 前端静态文件以内容 hash 发布，HTML 不缓存；回滚只切换 HTML/服务端版本，不删除已发布的 hash 静态文件，至少保留 7 天。
- 若浏览器认证、邮件流或 handoff 出现安全事件，立即关闭对应功能开关、撤销受影响 session/flow/ticket、保留审计和取证数据、发布用户可见的状态页；恢复前必须完成根因、修复、复测和安全评审。

### 11.5 备份、恢复与演练

- 每日全量、至少每小时增量/日志备份（能力由基础设施实现），加密保存并跨故障域复制；审计归档与业务库使用同一恢复演练标准。
- 每季度执行一次从备份恢复到隔离环境的演练，验证用户、订阅、审计、mail flow 和同步元数据的一致性；恢复环境不得连接生产 SMTP、支付或遥测端点。
- 设定并在部署文档中记录 RPO/RTO；P3 默认目标为 RPO 不超过 1 小时、RTO 不超过 4 小时，若基础设施无法满足则不得宣称该 SLO。

## 12. 前置依赖与验收

### 12.1 前置依赖（P3 首个切片开始前必须完成）

- 现有账户、验证邮件和个人同步基础能力可用；切片 5 所替换的旧 `/api/sync/reset-after-loss` `{ resetToken, newState }` 协议保持原行为，直到该切片的受控切换开始。
- Fastify 能按切片部署新增 API 与静态产物；生产 HTTPS、日志脱敏和 SMTP 基础配置已可用。邮件页、控制台 SPA、完整安全头、Cookie/CSRF、audience/session 和平台角色分别由对应切片交付，不作为切片 1 的全局前置条件。
- P2 的 handoff 协议、`sync_reset_handoffs`、完整 `StateDto` receipt 和扩展 `vscode://devbelt.sync/reset-after-loss?handoffTicket=` URI handler 是**切片 5**的范围与验收，不阻塞切片 1--4。
- P4 支付功能开关默认关闭，账单/支付入口在 P4 上线前隐藏。

### 12.2 全量验收

#### 功能
- 未登录访问 `/console/*` 跳转登录；登录后只回到经过白名单验证的本站路径。
- 用户和平台管理员的页面入口与 API 权限均符合第 2 节矩阵。
- 同步概览不依赖、也无法访问 E2EE 同步接口。
- 邮箱验证和同步重置交接按第 5 节完成所有成功、过期、已消费、网络失败和重试分支。

#### 安全
- 浏览器不在 JavaScript 可读持久存储中保存 Access/Refresh Token、邮件原始 token 或 E2EE 材料；仅允许使用本文规定的 `HttpOnly` Refresh/mail-flow Cookie 和非 HttpOnly、会话绑定的 CSRF Cookie；console token 无法调用 extension/sync API。
- Cookie、CSRF、Origin、CSP、Referrer-Policy、无缓存和日志脱敏规则均有自动化测试。
- 邮件 token 从 URL 清理后不进入 Referrer、存储、埋点或日志。
- handoff ticket 只能由同一用户的扩展在 15 分钟内一次性消费；浏览器永不提交 `newState`。
- 平台管理员不能读取 E2EE 材料；所有受限读取和高危写入都有审计事件。
- 生产环境禁用 CORS，所有安全头（HSTS/CSP/XFO/Referrer-Policy等）按第8节配置。
- 统一错误信封与限流`Retry-After`头在所有端点一致。
- 深度健康检查和所有指标/告警规则可被监控系统采集。

#### 体验与部署
- 所有页面覆盖加载、空、错误、无权限和成功状态；写操作不自动重放。
- 高危操作均有后果明确的二次确认，平台高危写入必须提供原因。
- API、公开页、静态资源和 SPA fallback 路由不冲突；更新后 HTML 不走陈旧缓存，带 hash 静态资源可长期缓存。
- 开发和生产环境的三条 SMTP 链接均可访问，并通过端到端验证。
- 备份/恢复演练、RPO/RTO SLO 有明确记录和验收测试。
