# P2 — 个人同步 v1：连接同步

## 目标

同一账户跨多台 VS Code 实例（双设备及以上）端到端加密同步个人连接配置。服务端无法读取连接明文、DEK、同步口令（SMP）、恢复码或签名私钥。

## 范围

**同步对象**：仅个人连接配置（`SavedConnection`）。
**不同步**：连接分组（`ConnectionGroup`）、保存查询（`SavedQuery`/`QueryFolder`）、组织连接（`org:` 前缀）、本机路径类字段。分组和保存查询将在后续 P2.x 阶段有独立的 record 类型设计，不在 v1。

## 本地路径类字段（不跨端）

以下字段**故意不进入加密 payload**，因为它们指向本机文件系统位置，跨设备无意义且可能泄露本机路径信息；同步到新设备后这些字段为空，UI 将连接标记为"需要配置"：

| 字段 | 原因 |
|---|---|
| `dbPath` | SQLite 数据库文件路径，每台机器不同 |
| `sqliteCommand` | SQLite CLI 可执行文件路径 |
| `sshPrivateKeyPath` | SSH 私钥文件路径 |
| `caPath`/`clientCertPath`/`clientKeyPath` | SSL 证书路径 |
| `connectionUrl`/`useConnectionString` | 连接串可能内嵌路径或密码 |
| `groupId` | v1 不同步分组，远端 groupId 无对应实体 |

同步下来的连接若缺少必需的本机字段（例如 SQLite 缺 `dbPath`，或 SSH 连接引用 `sshPrivateKeyPath` 但路径不存在），在树中显示 warning 图标 + 描述"需要配置"，点击打开补齐对话框，补齐前不允许建连。补齐后字段保存在本机 `globalState`/`SecretStorage`，不进入后续出站 payload。

## 按引擎划分的 Payload

`recordCodec.ts` 的白名单改为按引擎区分，`encodeRecordPayload` 对非白名单字段 fail-closed（显式抛错，不静默丢弃）：

**MySQL / PostgreSQL** 必需字段：`name`、`dbType`（`mysql`/`postgresql` engine 字符串）、`host`、`port`、`user`。
可选字段：`password`、`database`、`schema`、`timezone`、`environment`、`readOnly`、`useSSL`、`sshHost`、`sshPort`、`sshUser`、`sshPassword`、`sshPassphrase`。

**SQLite** 必需字段：`name`、`dbType`（`sqlite` engine 字符串）。
可选字段：`password`、`database`、`timezone`、`environment`、`readOnly`。
禁止出现：`host`、`port`、`user`、`useSSL`、`ssh*`——编码时若这些字段非空抛错（SQLite 不走 TCP/SSH）。

解码时未知 engine fail-closed；`dbType` 字符串还原为 `DatabaseType` 枚举。

## 安全模型

- 服务端只保存 ciphertext、公开签名材料（signPub/recoverSignPub）、nonce 账本、幂等回执、版本和配额元数据。
- 所有密钥派生与加解密在客户端完成；SMP 的 Argon2id KDF 在独立 Worker 线程执行，主线程不执行 Argon2id。
- DEK 是唯一长期保存在客户端的对称密钥，存在 `SecretStorage`（键 `dbclient.sync.dek.<userId>.<keyEpoch>`）。
- 登录不等于同步解锁；同步必须用户显式输入 SMP 后才派生 KEK、解封 DEK、启动同步。
- 同步密码（SMP）、恢复码、DEK、KEK、私钥均不写日志、不通过 Webview postMessage 发送、不出现在错误消息中。

## 密码学原语

| 用途 | 算法 | 参数 |
|---|---|---|
| 数据加密 | AES-256-GCM | 32B key，12B nonce，16B tag |
| 密钥派生 | HKDF-SHA-256 | output 32B |
| 签名 | Ed25519 | 32B seed，32B public key，64B signature |
| SMP 密钥派生 | Argon2id | m=64-256MiB, t=3-10, p=1-4, salt=16B, output=32B |
| 哈希 | SHA-256 | output 32B |
| 规范化 | RFC 8785 JCS | UTF-8 |
| 二进制编码 | base64url（无 padding） | — |
| 整数编码 | u64 十进制字符串，无前导零 | — |

HKDF info 字符串、密钥层级、Envelope AAD、Record AAD、签名输入格式沿用现有 `sync/crypto/` 和 `sync/e2e/types.ts` 中的实现（已单测覆盖）。v1 不改变密码学参数。

## 客户端持久化键

所有键按 userId 隔离，u64 字段使用十进制字符串。

| 键 | 位置 | 说明 |
|---|---|---|
| `dbclient.auth.accessToken` / `refreshToken` / `email` | SecretStorage | 登录令牌 |
| `dbclient.sync.cachedEntitlement` | globalState | 权益快照 |
| `dbclient.sync.dek.<userId>.<keyEpoch>` | SecretStorage | base64url 编码的 32B DEK |
| `dbclient.sync.state.<userId>` | globalState | `{ keyEpoch, stateVersion, changeSequence }` |
| `dbclient.sync.recordMap.<userId>.<keyEpoch>` | globalState | recordId↔connectionId 双射 |
| `dbclient.sync.outbox.<userId>.<keyEpoch>` | globalState | 待重放的已签名 mutation |
| `dbclient.sync.epochCleanup.<userId>` | globalState | epoch 切换可重放 intent |
| `dbclient.sync.fieldOverrides.<userId>.<connectionId>` | globalState | **新增**：本设备路径类字段覆盖（dbPath/sshPrivateKeyPath/certPaths/sqliteCommand/connectionUrl），不进入同步 payload |
| `dbclient.org.credential.<orgId>.<resourceId>` | SecretStorage | 组织模板本机凭据 |

Snapshot 单调性守卫（stateStore 已实现）：`changeSequence` 全局单调递增跨 epoch 不重置；`keyEpoch` 只增不减；`stateVersion` 同 epoch 内只增不减，epoch 推进时重置为 "1"。违反任一项抛错，不静默降级。

## 服务端 API

服务端路径与现有 `route/sync.ts` 一致（10 个端点），但以下接口**必须修正**以满足 v1 契约（在协议修复切片中完成）：

### 1. State DTO 字段名修正（阻断）

现有 `syncStateService.toDto()` 输出 envelope 字段 `version`/`ct`，与客户端 `EnvelopeDto`（`envelopeVersion`/`ciphertext`）及请求体字段名不对称。**必须**统一为长名 `envelopeVersion`/`ciphertext`。修正后服务端 `StateDto`：

```
protocolVersion=1, cipherSuite="AES-256-GCM", formatVersion=1,
keyEpoch(u64), stateVersion(u64), changeSequence(u64),
signPub(b64url 32B), recoverSignPub(b64url 32B),
smpKdf{alg,version,memoryKiB,iterations,parallelism,salt(b64url 16B),outputBytes=32},
recoveryKdf{alg,version,salt(b64url 16B),outputBytes=32},
envelopeSmp: EnvelopeDto, envelopeRecovery: EnvelopeDto,
recoveryCodeSetTime(ISO 8601 | null)
```

其中 `EnvelopeDto = { protocolVersion, cipherSuite, formatVersion, envelopeVersion, nonce, ciphertext, tag }`。路由层 `decodeEnvelope()` 和 `toDto()` 同步修改；同步添加跨包测试：服务端 `toDto()` 输出对象必须通过客户端 `validateSyncState()`（见下）。

### 2. destroy/reset-after-loss 返回完整快照（阻断）

现有 `SyncStateService.destroy()` 和 `SyncResetService.resetAfterLoss()` 只返回 `{ keyEpoch }`。必须扩展为返回完整 `{ keyEpoch, stateVersion, changeSequence }`，使客户端 cleanup 流程无需再发一次 GET state。
- destroy 返回 `{ keyEpoch: inc(oldKeyEpoch), stateVersion: "1", changeSequence: <逐条 tombstone 后的 seq> }`。
- reset-after-loss（有旧 state）返回 `{ keyEpoch: inc(oldKeyEpoch), stateVersion: "1", changeSequence: <tombstone 后的 seq> }`。
- reset-after-loss（无旧 state）返回 `{ keyEpoch: "1", stateVersion: "1", changeSequence: "0" }`。

幂等 receipt 分支（重试 destroy/reset 返回已存结果）也要返回完整快照：`recordReceipt` 需同时存 `resultVersion` 和 `resultChangeSequence`（当前 `putRecord`/`deleteRecord` 已存，state mutation 的 receipt 需补 `resultChangeSequence`）。

### 3. feed page 响应严格契约

`GET /api/sync/records` 返回：
```
{ snapshotSequence(u64), nextAfter(u64)?,
  records: [ { recordId, version, changeSequence, cipherSuite, formatVersion,
               nonce(b64url 12B), ciphertext(b64url ≤256KiB), tag(b64url 16B),
               updateTime(ISO 8601) }
           | { recordId, version, changeSequence, deleteTime(ISO 8601) } ] }
```
服务端 `toRecordDto()` 当前已输出 cipherSuite/formatVersion/nonce/ciphertext/tag（见 `syncRecordService.ts:80-97`），与文档一致；客户端解析需严格校验。

### 4. 客户端新增 validateSyncState

在 `sync/e2e/types.ts` 中新增 `validateSyncState(raw: unknown): StateDto`，覆盖完整 State DTO 的字段（envelope、smpKdf、recoveryKdf、signPub/recoverSignPub、counters），复用现有 `validateEnvelope`/`validateSmpKdf`/`validateRecoveryKdf`/`assertU64Decimal`/`assertBase64UrlNoPad`，rejectExtraKeys 拒绝未知字段。`SyncEngine.parseState()` 改为调用 `validateSyncState` 而非只解析三个计数器。

### 5. 客户端 feed record 严格校验

`SyncEngine.parsePage()` 对每条 active record 必须校验：
- `cipherSuite === "AES-256-GCM"` 且 `formatVersion === 1`，否则 terminal `SYNC_PROTOCOL_UNSUPPORTED`；
- `nonce`/`ciphertext`/`tag` 均为无 padding base64url，解码长度分别为 12/32/16 字节（ciphertext 长度可以是任意 ≤256KiB，但必须是合法 base64url）；
- `ciphertext` 解码后长度 ≤ 256*1024；
- tombstone 不得携带 nonce/ciphertext/tag；
- `recordId`、`version`、`changeSequence` 经 `assertRecordId`/`assertU64Decimal` 校验。

对未知字段闭合（reject 整条 page 为 error）。

### 6. record put/delete receipt 补 changeSequence

`SyncRecordService.putRecord()`/`deleteRecord()` 的返回值从 `{ version }` 扩展为 `{ version, changeSequence }`（destroy/reset 也是）。客户端 `confirmOutbound` 用两个字段更新本地 snapshot。

### API 汇总

| Method | Path | 签名 | 重试 | 成功返回 |
|---|---|---|---|---|
| GET | `/api/sync/state` | — | 是（5xx 退避） | 完整 StateDto |
| PUT | `/api/sync/init` | — | 否（无幂等回执） | 201 空 |
| GET | `/api/sync/records?after=&snapshotSequence=&limit=` | — | 是 | PullResult |
| PUT | `/api/sync/records/:recordId` | record.put | 是（幂等 receipt） | `{ version, changeSequence }` |
| DELETE | `/api/sync/records/:recordId` | record.delete | 是 | `{ version, changeSequence }` |
| POST | `/api/sync/change-key` | state.change-key（syncSign） | 是 | `{ keyEpoch, stateVersion }` |
| POST | `/api/sync/recover` | state.recover（recoverSign） | 是 | `{ keyEpoch, stateVersion, recoveryCodeSetTime }` |
| POST | `/api/sync/destroy` | state.destroy（syncSign） | 是 | `{ keyEpoch, stateVersion, changeSequence }` |
| POST | `/api/sync/reset-challenges` | — | 是 | 202 空 |
| POST | `/api/sync/reset-after-loss` | `aud=extension` + handoff ticket 认证（P3 邮件流签发） | 是（结果 receipt 可重放） | 完整 `StateDto`（与 `/api/sync/state` 返回结构完全一致，包含新 epoch 的所有 envelope/KDF/公钥/计数器字段） |

重试规则（沿用现有 `SyncClient.fetchWithRetry`）：
- 401 单飞 refresh+重发（始终启用，是 token 续期语义）；
- 5xx/网络错误指数退避 1s/2s/4s（MAX_ATTEMPTS=3，现有默认）；
- init `retry: false`（无幂等 receipt，禁止自动重发）；
- reset-after-loss：P3 handoff 路径具备结果 receipt，仅对网络/5xx 使用同一 `handoffTicket` 与相同 `newState` 自动重试，最多 3 次；业务校验失败不重试；
- 4xx 除 401 外不重试。

### 控制台重置交接协议（最终方案，无迁移）

P3 控制台邮件流完成 reset challenge 认领后，扩展通过浏览器深链获得 handoffTicket，最终 reset 仅由扩展调用并携带 `newState`。浏览器绝不接触 E2EE 材料。

#### 1. 新增表 `sync_reset_handoffs`

| 字段 | 约束与语义 |
|---|---|
| `id` | `BIGINT UNSIGNED` 主键 |
| `user_id` | 必填；必须等于原 reset token 的用户 |
| `reset_token_id` | 必填；关联 `personal_sync_reset_tokens.id`（逻辑引用，无外键） |
| `ticket_hash` | `BINARY(32)`、唯一；只保存 SHA-256(raw handoff ticket) |
| `request_digest` | `BINARY(32)` 可空；首次最终 reset 时写入规范 JSON `{ newState }` 的 SHA-256 摘要 |
| `result_state_dto_json` | `MEDIUMTEXT` 可空；完成后保存规范 JSON 格式的完整 `StateDto`，用于幂等重放（客户端必须拿到完整新状态才能持久化新 epoch 快照） |
| `result_key_epoch/state_version/change_sequence` | 完成后保存；冗余存储用于快速查询/校验 |
| `status` | `issued`、`processing`、`completed`、`revoked`、`expired` |
| `expires_time` | 签发后 15 分钟 UTC；过期后不可消费 |
| `consumed_time`、`create_time`、`update_time` | UTC `DATETIME(3)` |

唯一索引：`ticket_hash`；查询索引：`(reset_token_id, status, expires_time)`、`(user_id, status, expires_time)`。一个 reset token 同时最多拥有一个 `issued/processing` handoff；创建新 handoff 前必须撤销旧的未终结 handoff。

#### 2. 最终 reset 事务与重放

新扩展调用（aud=extension）：

```http
POST /api/sync/reset-after-loss
Content-Type: application/json

{ "handoffTicket": "base64url-256bit", "newState": { "...SyncNewState" } }
```

服务端固定锁顺序**严格一致**，避免死锁：始终先锁 reset token 行，再操作关联 handoff 行。完整事务流程：
1. SHA-256 handoffTicket，查询 handoff 行，检查 `user_id === authUserId`、过期时间；若 `status = completed`：比较 request_digest，相同返回保存的完整 `StateDto`；不同返回 `409 SYNC_RESET_HANDOFF_REUSED`。
2. 若 `status = processing`：检查 `update_time`，若已超过 60 秒（进程崩溃恢复超时），自动将 status 回退为 `issued`；未超时返回 `409 SYNC_RESET_IN_PROGRESS` 并附 `Retry-After: 2`。
3. 若 `status = issued`：**先以 `FOR UPDATE` 锁定关联 reset token 行**，确认未消费、未撤销、未过期且与 handoff 绑定；再以 `FOR UPDATE` 锁定 handoff 行，置为 `processing` 并写 request_digest。
4. 按既有 `resetAfterLoss` 规则锁 state、逐条 tombstone active epoch records、写入新 epoch/state、生成完整新 `StateDto`；在同一事务内将 reset token 置 consumed、handoff 置 completed、写入 `result_state_dto_json` 和冗余计数字段。
5. 任一步失败事务回滚，handoff 保持 `issued`（或超时自动回退为 issued），网络/5xx 后可用同一 ticket 和相同 newState 重试。

错误处理：
- 无 ticket、hash 不匹配、用户不匹配、已撤销、已过期、reset token 无效 → `400 SYNC_RESET_HANDOFF_INVALID`（不区分存在性）。
- `newState` 校验失败 → `422 VALIDATION_FAILED`，handoff 保持 `issued`，允许修正后重试。
- request_digest 不同且已 completed → `409 SYNC_RESET_HANDOFF_REUSED`。

#### 3. 清理、审计与测试

- `issued/processing` 在 ticket `expires_time` 到期后标记 `expired`；`processing` 状态超过 60 秒未完成的，在下一次访问时自动回退为 `issued`（崩溃恢复）；`completed/revoked/expired` 保留 24h 后分批清理；原 reset token 保留记录不删除。
- handoff 创建/撤销/过期/消费/失败均写审计事件，只记录 handoff ID、用户 ID、结果、错误码，不记录 ticket、reset token、newState、密钥、密文、完整 StateDto 内容。
- 测试矩阵：同用户成功、错误用户、过期、撤销、并发双消费、响应丢失重放、已完成后不同 newState、handoff expired 清理、processing 超时自动恢复、锁序死锁验证。


## 同步行为模型

**触发方式**：
- **解锁后首次同步**：`unlock()` 成功后 `coordinator` 必须立即执行一轮 sync（在现有 `start()` 后追加首次调度，或给 coordinator 加 `scheduleInitialSync()` 方法立即触发 drain，不依赖 debounce 定时器）。
- **本地变更自动同步**：`ConnectionStore.onChanged('user')` 经 250ms trailing debounce 触发（已有）；outbox 为空时本轮 reconcile 不生成 mutation 但仍执行 pull。
- **手动 Sync Now**：`dbclient.syncNow` 命令，重置退避计数立即执行一轮；不绕过 terminal/conflict/epoch 停止条件。
- **窗口聚焦触发**：订阅 `vscode.window.onDidChangeWindowState`，聚焦时若上次状态不是 idle/ok，调度一次 sync（用于网络恢复）。
- **不做定时轮询**：没有后台定时器持续拉取；远端变更只在下次触发点（本地变更、手动同步、窗口聚焦、重新 unlock）拉取。多设备并发依赖版本乐观锁发现冲突。

**每轮 sync 顺序（SyncEngine 已有但需修正 receipt 字段）**：
1. Epoch 对账：`GET /api/sync/state`，经 `validateSyncState` 校验；本地/远端 keyEpoch/stateVersion 比对，必要时更新本地 stateVersion。
2. Outbox 重放：逐条重放已签名 mutation；成功后先 confirm recordMap，再删 outbox 条目。
3. 分页 pull：固定 snapshotSequence，每页成功后持久化 cursor；逐条解密 applyRecord。
4. 错误分类（见错误表）停止本轮；成功则 applied 计数返回。

**错误退避（需新增 coordinator 级调度）**：
- HTTP 层重试已存在：`SyncClient.fetchWithRetry` 对 5xx/网络错误做单次请求的指数退避（1s/2s/4s，MAX_ATTEMPTS=3），401 单飞 refresh+重发。
- Coordinator 级退避（待新增）：`SyncCoordinator` 维护跨轮次指数退避定时器，1s → 2s → 4s → 8s → 16s（上限 30s），在一轮 sync 因 retryable 错误失败后自动调度下一轮；每轮成功后重置退避计数。
- 连续可重试失败 ≥5 次标记 `stalled`：该条 mutation 保留，停止自动重试，允许本轮继续入站 pull；等待用户手动 Sync Now 或新的本地变更重置计数。
- terminal/conflict/epoch：立即停止，标记状态，弹 UI；不自动重试。

**冲突策略**：以 record 为单位，不做字段级三路合并（见下一节）。

## 冲突模型（原子状态迁移）

### 冲突检测

- **出站冲突**：push mutation 返回 `SYNC_VERSION_CONFLICT`（附 `currentVersion`）。
- **入站冲突**：pull apply 时 `applyRecord` 抛 `RecordConflictError`：
  - `kind='version'`：本地 confirmed 记录 revision（updateTime）晚于 recordMap 中记录的 revision（远端同步期间用户又改了本地）。
  - `kind='pending'`：recordMap 中 status=pending 且本地连接存在（崩溃窗口内的中间状态）。

### 冲突条目持久化（新增）

`PendingMutationStore` 现有结构只有 `consecutiveFailureCount`，不支持冲突状态。**必须扩展** outbox 或新增单独的冲突存储（推荐扩展 outbox 条目增加可选 `conflict` 字段，保持单 record 至多一条 in-flight 语义）：

```
PendingMutation = PendingPutMutation | PendingDeleteMutation
  + conflict?: {
      kind: 'version' | 'pending';
      currentVersion: string;       // 远端当前版本
      remoteNonce?: string;         // 远端密文（仅 put 冲突时）
      remoteCiphertext?: string;
      remoteTag?: string;
      remoteRecordVersion: string;
    }
```

当检测到出站/入站冲突时：
- 出站 put 冲突：服务端响应 409 SYNC_VERSION_CONFLICT 携带 `currentVersion`（不含密文）。客户端需要**拉取该 record 的当前版本**才能让用户"使用远端"。API 不提供单 record 端点——因此出站 put 冲突时，停止本轮，cursor 不前进，标记 conflict；下一轮 pull 会把该 record 的远端版本拉下来（因为 after 是本地 changeSequence，而远端 changeSequence 更大）。applyRemote 时该 record 再次触发入站冲突，此时我们已有远端密文。为了避免"需要两轮"，扩展 SyncEngine：出站冲突时**立即 pull 到 snapshotSequence**，把该 record 的远端内容带入 apply，再进入冲突 UI。
- 入站冲突：`applyRemote` 已拿到 `nonce/ciphertext/tag/version`，可直接落入 conflict 字段。

更直接的方案：**扩展冲突条目**在 `SyncRunResult.conflicts` 中携带远端密文字段，UI 层展示冲突详情时可以解密远端版本（用户选 Use Remote 时直接 apply，不用再 pull）。需要在 SyncConflictEntry 中增加 `remoteNonce/remoteCiphertext/remoteTag/remoteVersion` 字段，applyRemote 捕获 RecordConflictError 时把这些信息带上。

### 用户操作的原子状态迁移

对每条冲突记录，用户有三个选择：

**Use Local（保留本地）**：
1. 读取本地当前连接内容（用户在冲突期间可能又编辑过）。
2. 用远端 `currentVersion` 作为 baseVersion，重新 sealRecord（recordVersion 为 `inc(currentVersion)`）+ sign，生成新 mutation。
3. 原子替换 outbox 中该 record 的旧 mutation（delete 旧条目 put 新条目，同一事务/写链完成）。
4. 清除该条目的 conflict 字段；`consecutiveFailureCount = 0`。
5. 立即调度一轮 sync。

**Use Remote（使用远端）**：
1. 用冲突条目中保存的 `remoteNonce/remoteCiphertext/remoteTag/remoteVersion` 解密远端 payload。
2. 回滚本地未同步修改：`ConnectionStore.save(remoteConn, 'sync')`，覆写本地连接内容，把 `updateTime` 设置为解密应用时刻（applyRecord 内部已处理）。
3. 更新 recordMap：`put(recordId, { connectionId, recordVersion: remoteVersion, revision: <新 updateTime>, status: 'confirmed' })`。
4. 删除 outbox 中该 record 的 mutation 条目。
5. 如果有其他冲突条目，继续处理；处理完所有冲突后刷新树并调度一轮 sync 验证收敛。

**Cancel（取消）**：
- 不修改 outbox 或 recordMap，状态保持 conflict。
- 状态栏显示"X 条冲突待处理"；自动同步停止，直到用户手动 Sync Now 或解决冲突。
- 下次触发同步时重新进入冲突面板（远端可能已变化，重新检测）。

"全部保留本地"/"全部使用远端"是对所有冲突项批量执行上述流程（按顺序原子替换，单条失败不影响其他条的替换，失败项继续保留 conflict）。

### 非冲突变更自动合并

两端修改不同 record 时自动双向收敛，无需用户介入。同一 record 一端只改本地、一端只改远端不重叠时（理论上不可能——record 是整包密文，任何修改都改 ciphertext），以版本乐观锁检测冲突，交由用户决定。

## 同步循环与状态栏

状态栏项 `dbclient.sync.status` 展示状态：

| 状态 | 展示 | 含义 |
|---|---|---|
| `idle` | $(sync) 最近成功时间 | 上一轮 sync 成功；无待处理 mutation |
| `syncing` | $(sync~spin) 同步中 | 一轮 sync 进行中 |
| `error` | $(error) 错误摘要 | 上一轮因 retryable 错误失败（不含秘密）；自动退避重试中 |
| `stalled` | $(warning) 某连接同步失败 | 连续失败≥5次，自动重试停止，等用户手动 |
| `conflict` | $(warning) N 条冲突 | 有未解决冲突，点击打开冲突面板 |
| `locked` | $(lock) 未解锁 | 已登录但同步未解锁，显示"点击设置/解锁" |

状态由 `SyncCoordinator.lastRun/lastError` 和 session 解锁状态驱动；状态栏点击打开同步面板（初始化/解锁/冲突/错误详情）。

## 错误码处置表

服务端错误码 → 客户端处置：

| Code | HTTP | 分类 | 处置 |
|---|---|---|---|
| `SYNC_NOT_INITIALIZED` | 400 | state | 停止，进入初始化引导 |

| `SYNC_EPOCH_STALE` | 409 | epoch | 停止，弹"同步状态已更新，请重新输入同步口令"引导重新解锁→cleanup |
| `SYNC_VERSION_CONFLICT` | 409 | conflict | 解析 currentVersion，拉远端内容，进入冲突 UI |
| `SYNC_NONCE_REUSED` | 409 | terminal | 停止，展示协议错误（可能是攻击或 bug） |
| `SYNC_QUOTA_EXCEEDED` | 409 | terminal | 停止，提示升级或删除连接 |
| `SYNC_SIGNATURE_INVALID` | 403 | terminal | 停止，签名无效（可能密钥损坏） |
| `SYNC_PROTOCOL_UNSUPPORTED` | 400 | terminal | 停止，客户端版本过旧 |
| `VALIDATION_FAILED` | 400 | terminal | 停止，请求格式错（bug） |
| `NOT_FOUND` (record) | 404 | terminal | 停止，record 状态不一致，需重新 init 或诊断 |

| 网络错误 | — | retryable | 指数退避重试 |

## 生命周期状态机

### 状态

客户端会话三态（`PersonalSyncSession` 已有框架）：
- **Logged Out**：无 token，不持有任何 sync 对象。
- **Logged In Locked**：有 token，有 StateStore 但无 DEK 在内存，不创建 engine/coordinator，不发起任何 sync API 请求（包括 GET state）。
- **Unlocked**：DEK 在内存，engine/mutator/coordinator 已构造并 start；coordinator 订阅本地变更。

### 状态发现（点击"设置同步"/"解锁同步"时触发）

1. 调用 `client.getState()` → `validateSyncState(raw)`。
2. 错误分流：
   - `SYNC_NOT_INITIALIZED`（400）→ 进入初始化流程。
   - 401 → 引导重新登录。
   - terminal/protocol/validation 错误 → fail-closed，展示错误（不含秘密）。
   - 网络/5xx → 提示重试。
3. 成功获取 state 但本地有 `pendingCleanup` → 进入 epoch cleanup 恢复流程。
4. 成功且无 pendingCleanup → 检查本地 snapshot：无 snapshot 或 keyEpoch 不匹配 → 进入解锁流程（首次在新设备解锁）。

### 初始化流程

1. 用户输入 SMP（两次确认，12-128 code points，禁止纯空）。
2. 调用 Argon2id Worker 生成初始材料：`createInitialMaterial(smp)` 返回 `{ dek, signSeed, recoverSignSeed, recoveryCode, smpKdf, recoveryKdf, envelopeSmp, envelopeRecovery, signPub, recoverSignPub, newState }`。
3. 恢复码和 DEK **暂存内存**，不写盘、不写日志。
4. 调用 `client.init(newState)`（`retry: false`）：
   - 201 成功：
     1. `dekStore.store(userId, 1n, dek)` 持久化 DEK 到 SecretStorage。
     2. `session.ensureStores('1')`。
     3. `stateStore.setSnapshot({ keyEpoch: '1', stateVersion: '1', changeSequence: '0' })`（持久化初始 snapshot——必须在 unlock 前完成）。
     4. `session.unlock('1', dek)`。
     5. 一次性展示恢复码，modal 要求用户确认"我已安全保存恢复码"。确认后清除内存中的恢复码明文。
   - 409 `SYNC_STATE_EXISTS`：服务端已有 state（响应丢失/并发 init）；不能再 init。转解锁流程，内存中的恢复码作废（警告说明）。
   - 网络/5xx：init 结果未知（服务端可能已提交也可能未提交），禁止自动重试；提示"初始化可能已提交，请尝试解锁"。

### 解锁流程

1. 用户输入 SMP。
2. 读取远端 state（`getState` + `validateSyncState`，若已在状态发现阶段读取则复用）。
3. 调用 `unlockDek(smp, state.smpKdf, state.envelopeSmp, userId, state.keyEpoch)`（Worker 派生 KEK → openEnvelope）：
   - GCM 验证失败 →"同步口令错误"，不清空本地状态，允许重试。
   - 成功 → 返回 DEK。
4. `session.ensureStores(state.keyEpoch)`。
5. 持久化 snapshot（若本地无 snapshot 或远端 stateVersion 更新）。
6. 检查本地 DEK：`dekStore.load(userId, BigInt(state.keyEpoch))`：
   - 无 → `dekStore.store()` 保存。
   - 有 → 比对与解封 DEK 字节一致；不一致 fail-closed（状态损坏，提示销毁重置）。
7. `session.unlock(state.keyEpoch, dek)`——这会创建 engine/mutator/coordinator 并 `start()`；start 后立即触发首次 sync。
8. 首次 sync 完成且 `stage === 'ok'` 后刷新 `DbTreeDataProvider`。

### Epoch cleanup 恢复流程

启动时（activate）若检测到 `session.pendingCleanup !== undefined`：
- 弹 modal："上次同步状态切换未完成，请输入同步口令以恢复"。
- 用户输入 SMP → 读取新 epoch state（`getState` + validate）→ unlockDek 解封新 DEK → `session.resumeEpochTransition(newSnapshot)` 幂等重放 cleanup（写新 snapshot → 清旧 recordMap/outbox → 删旧 DEK → 清 intent）→ unlock 新 epoch → 首次 sync。

### 解锁后的 SMP 更改（Change Password）

1. 用户从同步面板选"修改同步口令"。
2. 输入旧 SMP + 新 SMP（两次确认）。
3. 用旧 SMP 派生 KEK 解封当前 DEK（验证旧口令正确）。
4. 生成新 smpKdf（新 salt/参数），用新 SMP 派生新 KEK，seal 新 envelopeSmp（envelopeVersion+1）；envelopeRecovery 不变（不轮换恢复码），DEK 不变，signPub 不变。
5. 调用 `client.changeKey({ keyEpoch, mutationId, expectedStateVersion: local.stateVersion, smpKdf: newSmpKdf, envelopeSmp: newEnvelope })`，用 syncSign 签名。
6. 成功后（receipt 返回新 stateVersion）：
   - 更新本地 snapshot stateVersion。
   - 新 envelopeSmp 不需要本地持久化（它存在服务端 state 里；下次解锁从服务端拉）。
   - DEK 不变，无需更新 dekStore。
   - 显示"同步口令已修改"。
7. 失败保留旧 SMP 可用（不写任何本地变更）。

### 恢复码恢复（Recover）

1. 用户在未解锁状态下选"使用恢复码恢复"。
2. 输入恢复码（格式化分组输入）+ 新 SMP（两次确认）。
3. Worker：用恢复码派生 KEK_recovery，解封当前 envelopeRecovery 得到 DEK；生成新恢复码和新 recoverSign 密钥；用新 SMP 派生新 KEK，seal 新 envelopeSmp；用新恢复码派生新 KEK_recovery，seal 新 envelopeRecovery。
4. 调用 `client.recover(...)`，用**旧 recoverSign** 签名（证明持有恢复码）。
5. 成功后更新本地 snapshot（stateVersion 递增，recoverSignPub 轮换）、保存新 DEK、一次性展示新恢复码（旧恢复码作废）。
6. unlock 并触发 sync。

### 销毁（Destroy）

语义：清空服务端所有同步记录，从新的空 epoch 开始（仍用同一 SMP，但产生新 DEK/新密钥材料/新恢复码）。其他设备在下一次 sync 时会收到 SYNC_EPOCH_STALE，提示重新输入 SMP 以进入新 epoch（非 reset，SMP 仍有效）。

1. 用户在同步面板选"销毁同步数据"。
2. 二次确认 modal，要求输入当前 SMP。
3. Worker：用 SMP 解封当前 DEK（验证持有）；生成**全新**密钥材料：`createInitialMaterial(smp)`（新 DEK、新 signSeed、新 recoverSignSeed、新恢复码、新 smpKdf/recoveryKdf/envelopes/signPub/recoverSignPub/newState）。
4. 调用 `client.destroy({ keyEpoch, mutationId, expectedStateVersion, newState })`，用旧 syncSign 签名。
5. 服务端 tombstone 所有 active records，推进 keyEpoch+1，返回 `{ keyEpoch: newKeyEpoch, stateVersion: "1", changeSequence }`。
6. 客户端用返回的完整快照调用 `session.reconcileEpochTransition(oldKeyEpoch, newKeyEpoch, newSnapshot)`：写 cleanup intent → 持久化新 snapshot → 保存新 DEK → 清旧 recordMap/outbox → 删旧 DEK → 清 intent → resetRuntime → unlock 新 epoch → 首次 sync。
7. 一次性展示新恢复码（旧恢复码作废）。
8. 其他设备：下次 sync 得到 SYNC_EPOCH_STALE → 弹"同步数据已重置，请输入同步口令继续"→ 用户输入同一 SMP → Worker 用新 smpKdf 派生 KEK → 解封新 envelopeSmp 得到新 DEK → reconcileEpochTransition → unlock 新 epoch（无需 reset 邮件，无需重新 init）。

### 丢失 SMP 重置（Reset After Loss）

语义：用户遗忘 SMP 且丢失恢复码，通过邮箱挑战 token 建立全新 epoch（旧数据不可恢复）。这是灾难恢复，不是正常流程，UI 明确警告。

1. 用户在锁定/未初始化状态选"忘记同步口令"。
2. 输入邮箱（默认填登录邮箱）→ `client.resetChallenges()`（服务端发邮件，限流 user+IP 各每小时 3 次，token 24h 一次性）。扩展显示“请在邮件中打开安全链接，并登录同一账号后选择在 VS Code 中继续”。
3. 用户在浏览器完成 P3 邮件流认领和登录；浏览器创建 15 分钟单次 `handoffTicket`，通过 `vscode://dbclient.sync/reset-after-loss?handoffTicket=` 唤起扩展。扩展 URI handler 只将 ticket 保存在内存，立即打开 reset 面板；不得写入 Memento、SecretStorage、日志或错误上报。
4. 扩展要求当前 `aud=extension` 登录用户与 deep link 关联用户一致；不一致、未登录、ticket 过期或已消费时显示统一失败提示并要求用户重新申请邮件。
5. 用户输入新 SMP（两次确认）；Worker 生成全新密钥材料（`createInitialMaterial(newSmp)`），不依赖任何旧密钥。
6. 调用 `client.resetAfterLossWithHandoff(handoffTicket, newState)`。网络/5xx 使用同一 ticket 与相同 newState 自动重试最多 3 次；成功或终态 4xx 后立即从内存清除 ticket。
7. 服务端单事务（严格先锁 reset token 再锁 handoff）：消费 handoff ticket 与原 reset token → tombstone 旧 epoch records（若有）→ 创建新 epoch keyEpoch=1 或 keyEpoch+1 → 持久化完整 StateDto 到结果 receipt → 返回完整 `StateDto` 快照（包含新 epoch 所有 envelope/KDF/公钥字段）。
8. 客户端：
   - 若本地有旧 epoch snapshot：`reconcileEpochTransition(oldKeyEpoch, newKeyEpoch, newSnapshot)`（幂等）。
   - 若本地无 snapshot（新设备或已清理）：直接保存 DEK → `ensureStores(newKeyEpoch)` → `setSnapshot(newSnapshot)` → unlock。
   - 一次性展示新恢复码。
9. 其他设备：下次 sync 得到 SYNC_EPOCH_STALE，尝试用旧 SMP 解锁新 epoch 会失败（envelopeSmp 用新 SMP 密封，旧 SMP GCM 验证失败），提示"同步数据已被重置，请使用重置邮件恢复或销毁本地数据"；提供"销毁本地同步数据"入口清理本地状态后引导 init 或 reset-after-loss。

`SyncEngine.sync()` 返回 `stage==='ok'` 后，`SyncCoordinator` 触发 `DbTreeDataProvider.refresh()`。

**切片 1：协议修复（阻断）**
- 服务端：
  - `syncStateService.toDto()` 输出长名 `envelopeVersion`/`ciphertext`。
  - `StateDto.envelopeSmp/Recovery` 类型改为长名。
  - `syncStateService.destroy()`/`changeKey()`/`recover()` 返回完整快照（补 `changeSequence`）。
  - `syncResetService.resetAfterLoss()` 返回完整快照。
  - `recordReceipt()` 存 `resultChangeSequence`；checkReceipt 返回两个字段。
  - `syncRecordService.putRecord/deleteRecord` 返回 `{ version, changeSequence }`。
  - 路由层 decodeEnvelope 保持读 `envelopeVersion`/`ciphertext`（已实现）。
- 客户端：
  - `types.ts` 新增 `validateSyncState(raw)`，复用现有子 validator；rejectExtraKeys。
  - `types.ts` 新增 `StateDto` 类型（与服务端一致）。
  - `SyncEngine.parseState()` 改为调用 `validateSyncState`，返回完整 StateDto（engine 仍只需要 counters，但 validator 校验全部字段）。
  - `SyncEngine.parsePage()` 补 cipherSuite/formatVersion/base64url 长度校验。
  - `SyncEngine.confirmOutbound()` 从 receipt 读 version 和 changeSequence，commitCursor 用正确的 changeSequence。
  - `e2e/client.ts` 的方法返回类型补全；`putRecordSigned/deleteRecordSigned` 的 receipt 解析同步。
- 测试：
  - 服务端单测：toDto 字段名长名、destroy/reset 返回完整快照、receipt 存 changeSequence。
  - 客户端单测：validateSyncState 对畸形 state 拒绝、parsePage 对非法 cipherSuite/长度拒绝。
  - 跨包测试：服务端 toDto 输出通过客户端 validateSyncState。

**切片 2：Payload 收紧（按引擎区分）**
- `recordCodec.ts`：
  - `RECORD_PAYLOAD_FIELDS` 拆为 mysql/pg/sqlite 三组。
  - `encodeRecordPayload(conn)` 按 conn.dbType 选择白名单；SQLite 禁止 host/port/user/ssh/useSSL；非白名单字段若在源对象中为非空值则抛错（明确 fail-closed 而非静默丢弃）。
  - `decodeRecordPayload(p)` 返回类型按引擎区分；SQLite 解码后 host/port/user 等字段应为 undefined。
  - 白名单移除 `groupId`（v1 不同步分组）。
- `syncMutator.ts` 和 `applyRecords.ts`：适配新 payload 形状；`applyRecord` 创建 SQLite 连接时不要求 host/port。
- `ConnectionConfig`：增加 `rejectUnauthorized?: boolean`；MySQL/PG 驱动透传。
- 测试：SQLite payload 无 host/port、非白名单字段抛错、groupId 被拒绝。

**切片 3：字段覆盖存储与"需要配置"提示**
- 新增 `FieldOverrideStore`（或直接在 ConnectionStore 中支持）：读写 `dbclient.sync.fieldOverrides.<userId>.<connectionId>`，持久化本机路径类字段（dbPath/sshPrivateKeyPath/certPaths/sqliteCommand/connectionUrl）。
- ConnectionStore 在 materialize 时合并 fieldOverrides。
- DbTreeDataProvider 节点计算"needsConfig"状态：SQLite 无 dbPath、SSH 配置了 key auth 但 sshPrivateKeyPath 不存在、证书路径不存在。
- 树节点 contextValue 加 `needsConfig` 后缀；tooltip 显示缺什么字段；点击注册命令打开补齐对话框。
- 测试：缺路径连接不可建连，补齐后可建连。

**切片 4：Composition root（extension.ts 接线）**
- `extension.ts` 懒创建 PersonalSyncSession、注册命令、订阅 logout/window focus。
- 不注册 UI 面板（切片 5），只验证：
  - 未登录/未解锁状态不发任何 sync API 请求（可用 Sinon 拦截 fetch 验证）。
  - logout 后内存无 DEK。
  - 提供内部 API 供后续切片驱动 init/unlock。
- 测试：activation 不触发 sync 请求；session 懒创建；dispose 清理干净。

**切片 5：初始化与解锁 UI 最小闭环**
- 同步面板 Webview/QuickPick：输入 SMP → Worker → init/unlock 流程。
- init 201 后持久化 snapshot + DEK → unlock → 首次 sync 触发（coordinator.scheduleInitialSync）。
- init 网络错误提示"可能已提交，请解锁"。
- 解锁错误 SMP 提示、GCM 失败提示、状态损坏提示。
- 恢复码 modal 一次性展示+确认。
- 启动时 pendingCleanup modal 引导 SMP 恢复。
- 测试：初始化后重启可解锁；错误 SMP 不启动 session；恢复码只展示一次。

**切片 6：首次 pull + 树刷新 + coordinator 补全**
- `SyncCoordinator`：
  - 新增 `scheduleInitialSync()`：unlock 后立即执行一轮 drain（不经过 debounce）。
  - 新增 `scheduleNow()`：Sync Now 命令入口，重置退避计数立即 drain。
  - 新增退避定时器：retryable 错误后按指数退避调度下一次；stalled 阈值后停止自动重试；成功轮次或 Sync Now 重置计数。
  - 暴露 `schedule()` 给窗口聚焦事件调用。
- sync 成功后 DbTreeDataProvider.refresh()；needsConfig 标记生效。
- 状态栏项实现，订阅 coordinator/session 状态变更 setContext。
- 测试：首次 pull 刷新树；retry 退避逻辑；stalled 阈值；窗口聚焦触发。

**切片 7：冲突持久化与冲突 UI**
- 扩展 PendingMutationStore 的 outbox 条目支持 `conflict?` 字段；新增 `replaceMutation(mutationId, newMutation)` 原子替换（用于 Use Local）。
- SyncConflictEntry 增加 remoteNonce/ciphertext/tag/version 字段；applyRemote 捕获冲突时携带远端密文。
- SyncEngine.run()：出站冲突后立即 pull 当前 snapshot 再报冲突（或直接在 outbox 重试后让下轮 pull 带回）——采用后者简化：出站版本冲突只返回 conflict 条目（含 currentVersion），本轮停止；下一轮 pull 自然带回远端内容，入站 apply 时携带密文进入冲突 UI。
- 冲突面板：列出冲突项；三种操作按上文"原子状态迁移"实现。
- 测试：并发修改同一连接产生冲突；Use Local 生成新 mutation 推送成功；Use Remote 丢弃本地修改；Cancel 保持 conflict 状态。

**切片 8：换钥 / 恢复 / 销毁 / 重置 UI**
- 按上文"生命周期状态机"实现四个流程的 Webview/QuickPick。
- destroy/reset 成功后调用 `reconcileEpochTransition` 走 cleanup intent 幂等流程。
- 其他设备 epoch-stale 流程：SMP 解封新 DEK → reconcile 或提示 reset。
- 每个流程的失败回滚：失败不写本地状态变更。
- 测试：换钥后其他设备用新 SMP 解锁；恢复码轮换；destroy 后新 epoch 重建；reset token 一次性、限流。

**切片 9：双设备安装版验证**
- 用两个 VS Code 实例（两个 Profile）登录同一账号，按"验收矩阵"逐项验证。

## 验收（双设备矩阵）

两台安装版 VS Code（可本机不同 Profile）：

| 场景 | 预期 |
|---|---|
| 设备 A 初始化→解锁→首次同步；设备 B 登录解锁 | B 看到 A 创建的所有个人连接（敏感字段 password/sshPassword/sshPassphrase 同步） |
| A 新建 MySQL 连接 | B 自动同步看到 |
| A 编辑连接 | B 自动同步更新 |
| A 删除连接 | B 自动同步删除 |
| A 创建 SQLite 连接（填 dbPath） | B 看到连接标记"需要配置"；补齐 dbPath 后可连接；dbPath 不回传 A |
| A 用 SSH 私钥路径连接 | B 看到连接标记"需要配置"；补齐私钥路径后可连接 |
| 两端同时修改同一连接 | 冲突 UI 弹出；选 Use Local 则 A 胜出；选 Use Remote 则 B 胜出；Cancel 保留两边状态待后续 |
| 断网后本地修改→恢复网络（聚焦窗口或手动 Sync Now） | 变更自动同步到远端，无数据丢失 |
| 修改 SMP 口令 | 另一设备下次 sync 获 stateVersion 更新，弹"请输入新的同步口令"；新口令解锁成功，旧口令失败 |
| 恢复码恢复 | 旧恢复码失效，新恢复码一次性展示 |
| Destroy | A 销毁后 B 下次 sync 得 epoch-stale，输入 SMP 进入新空 epoch；旧数据不可恢复 |
| Reset-after-loss | token 一次性、限流生效；重置后新 epoch 从空开始；其他设备旧 SMP 无法解锁，提示需邮件重置 |
| 跨窗口 token 轮换 | 两个 VS Code 窗口同时操作不导致全员登出 |
| 组织连接、分组、保存查询 | 不出现在同步出站/入站；组织连接保持在本机 vault |

## 不验证项（明确排除）

- 分组同步、保存查询同步（后续 P2.x）。
- PostgreSQL 连接同步（依赖 P0 权益修复后纳入，v1 范围内 PG 连接 payload 按引擎白名单支持，但双设备验收以 MySQL/SQLite 为准）。
- 同步连接在同步前已存在的脏数据迁移（v1 假设初始化前无同步记录；首次 sync 时本地已有连接通过 mutator.reconcile 全量对账产生 put mutation 上传，是正常行为而非迁移）。
