## P0 — 功能性断裂（真实客户端路径已坏）

### 1. 连接元数据契约断裂：connections 节推送对真实客户端必 500
- 位置：客户端 `vscode-ext/src/connection/connectionStore.ts:354`（`getConnectionMeta`）；服务端 `server/src/repository/mysql/connectionMetaRepo.ts:41-55`、`server/src/service/syncService.ts:68-74`。
- 现状：客户端发 `{connUuid, createdAt, updatedAt, deleted}`，服务端读 `connId / clientCreatedAt / clientUpdatedAt`。`conn_id VARCHAR(64) NOT NULL` 收到 undefined → `ER_BAD_NULL_ERROR` → 500。服务端测试全部用服务端形状（`test/**` 均为 `connId`），测试绿、线上炸。
- 附加问题：墓碑语义相反——客户端把已删连接（`deleted:true`）也放进 meta；服务端把 meta 全部当活跃行 upsert、只墓碑「未上报」行。字段名对齐后，删除的连接会复活为 active；`projectedActive = meta.length`（syncService.ts:72）也把墓碑计入配额。
- 修复：
  1. 客户端改发 `connId / clientCreatedAt / clientUpdatedAt`，并保留 `deleted` 标志；
  2. 服务端 `replaceAll` 对 `deleted === true` 的条目直接置墓碑而非 upsert；
  3. `projectedActive` 只数非墓碑条目；
  4. 新增契约测试：用**客户端实际形状**的 payload 打 `PUT /api/sync`（含删除条目），断言活跃数与墓碑。
- 验证：新测试 + `pnpm -C packages/server test`。

### 2. 客户端 Plan 字段名为 v1 遗留，配额全部读成 undefined
- 位置：`vscode-ext/src/sync/syncClient.ts:69-89`（PlanInfo）、`sync/authService.ts:14-23`（CachedPlan）、`sync/features.ts:90,111`、`commands.ts:54-57`（状态栏）。
- 现状：客户端读 `maxDevices / maxConnections / maxOpenConnections / syncQuotaBytes`；服务端 Plan 实体是 `perSeatMaxDevices / perUserMaxPrivateConnections / perUserMaxOpenConnections / perUserPrivateSyncQuotaBytes`（entities.ts:47-57）。
- 后果：
  - `resolveMaxOpenConnections` → undefined → 不限。而服务端**完全不强制**并发打开数（planQuota 无此维度）→ free 的「2 并发打开」两端都不生效；
  - `resolveMaxConnections` → 本地不限，只在 push 时被服务端 403（割裂体验）;
  - 状态栏设备数/同步配额恒显 `∞`。
  - `features` 字段名恰好一致，功能门控未坏。
- 修复：客户端改用服务端字段名（含 CachedPlan 的 globalState 兼容迁移：读到旧形状缓存时作废重取）。
- 验证：客户端类型检查 + 手动核对状态栏与门控。

### 3. 推送基线丢失：服务端数据重建后永远 "No local changes to push"
- 位置：`vscode-ext/src/commands/sync.ts:143-146`（场景 A）、`sync/syncManager.ts:174-178`（`isLocalDirty`）。
- 现状：`isLocalDirty()` 在 `lastHash` 与本地哈希相等（或无基线）时返回 false；场景 A 只看 `dirty` 即 return，无视 `previewPush` 已算出的 `plan.hasLocalUnpushed`（syncManager.ts:186）。服务端库重建（Greenfield 迁移）或全新安装后，本地有数据也推不上去。
- 修复：场景 A 条件改为 `if (!dirty && !plan.hasLocalUnpushed)`；`!dirty && hasLocalUnpushed`（失基线）时走 `pushWithConflictFallback(mp)`（远端为空时 base=0 首次写入成立）。
- 验证：清服务端库后执行 Push 能入库；补对应用例（若该命令有测试文件则跟随其结构）。

## P1 — 安全与计费边界

### 4. 组织域路由整域无输入校验
- 位置：`server/src/route/organizations.ts` 全部 handler（`body(req)` 裸用）。
- 现状：`role` / `resourceType` / `accessScope` / `permission` 无枚举校验（任意字符串入库，对应列均为 VARCHAR）；org name（VARCHAR(100)）、resource name（VARCHAR(200)）无长度上限 → `ER_DATA_TOO_LONG` → 500；`addMember` 的 `Number(userId)` 可为 NaN → 500。
- 修复：为组织域补 schema（仿照现有 schemas.ts 片段；枚举对齐 `domain/enums.ts`；name 长度对齐列宽），service 层保留兜底校验。
- 验证：非法值 400、超长 400、NaN userId 400 的用例。

### 5. Team 试用可无限薅
- 位置：`server/src/service/organizationService.ts:75-91`（`createOrganization`）。
- 现状：每建一个 team org 送 14 天 team 配额 + 5 席位（trialing），无每用户数量限制；路由仅受 `default` 桶 1200 次/分/IP。循环建组织 = 永久免费 team。
- 修复（建议最小版）：同一用户同时最多持有 1 个 `trialing` 状态的 team 订阅（建前查询，超出抛 `ValidationError`）；如需「终身试用次数」限制另议。
- 验证：连续创建第 2 个 team org 返回 400 的用例。

### 6. addMember 治理缺口（配额流转灰产）
- 位置：`organizationService.ts:100-111`。
- 现状：① 拉人无需目标用户同意（任意 admin 可把任意注册用户拉进组织）；② `orgMaxMembers` 完全不校验；③ 用户无法自行退出组织（无 leave 接口）。与 #5 组合：试用组织互相拉人即可流转 team 配额。
- 修复（分期）：
  1. 立即：`addMember` 执行 `orgMaxMembers` 校验（0=无限，与 pickLimit 语义一致）；
  2. 立即：`POST /api/organizations/:organizationId/leave`（成员自退；owner 禁止自退）；
  3. 邀请同意机制（invitation 状态）列为产品决策项，先建 issue 不实现。
- 验证：超员 400、自退成功、owner 自退 400 的用例。

### 7. rollback 绕过设备门禁
- 位置：`server/src/route/sync.ts:88-97`、`server/src/service/syncService.ts:157-169`。
- 现状：push/pull 都走 `requireDeviceBound`，rollback 不读不传 deviceId → 超限未绑定设备仍可写数据。
- 修复：路由 `readDeviceId(req)` 传入，`rollback` 前置 `requireDeviceBound`。
- 验证：未绑定且配额满的用户回滚返回 403 的用例。

## P2 — 竞态与数据一致性

### 8. 设备绑定竞态（check-then-act）
- 位置：`authService.ts:203-210`（tryBindDevice）、`syncService.ts:119-127`（requireDeviceBound）。
- 现状：并发登录/同步可绑出超过 `perSeatMaxDevices` 的设备。
- 修复建议：`devices` 绑定走条件 INSERT（`INSERT ... WHERE NOT EXISTS` 或唯一键 + 捕获重复），绑定前计数改为事务内 `SELECT ... FOR UPDATE` 或接受「插入后超限即回滚并报错」。

### 9. addMember 席位竞态
- 位置：`organizationService.ts:100-111`。
- 现状：并发加成员可超席位。
- 修复建议：事务内 `SELECT ... FOR UPDATE` 锁席位行再比较，或唯一约束兜底。

### 10. webhook 幂等竞态
- 位置：`paymentService.ts:74-90`（seen → 处理 → record）。
- 现状：并发重复投递可双份生效（席位双加、订单双记）。
- 修复建议：先 `INSERT` 幂等行（`UNIQUE(provider, event_key)`）抢占，撞键即返回；处理失败再把幂等行标记可重试。

### 11. createOrganization 无事务
- 位置：`organizationService.ts:75-91`（org + membership + trialing 订阅 + 5 席位循环，逐条独立写入）。
- 修复：包进 `withTransaction`（参照 `registrationRepo.createAccount` 的写法，席位循环也在事务内）。

### 12. 长邮箱注册 500
- 位置：`registrationRepo.ts:32`（`orgName = email + "'s workspace"`）。
- 现状：schema 允许 email ≤190 字符，org name 超出 `organizations.name VARCHAR(100)` → 注册整体失败。
- 修复：orgName 截断到 100 字符（`…` 收尾）或改用「前缀 + 固定后缀」策略。

### 13. 版本历史在配额之外（存储放大）
- 位置：`syncRepo.sumBytes`（只算当前表）；`pruneVersions` 按 retention 保留。
- 现状：Pro/Team retention=30 × 5 节 × 单节最大 8MB ≈ 单用户 1.2GB 历史，配额与文档均未覆盖。
- 修复（产品决策项）：① 把 `sync_section_versions` 字节计入 `sync_bytes` 配额；或 ② 下调 retention 并在设计文档显式声明历史不计配额。建议 ① 的简化版：`sumBytes` 改为两表合计。

### 14. 重复注册并发 → 500
- 位置：`authService.ts:73-74` 预检查 + `registrationRepo.ts:18-19` 事务内检查抛 generic Error。
- 修复：映射 `ER_DUP_ENTRY` 与事务内重复检查为 `ConflictError`（409）。

## P3 — 语义、展示与文档债

### 15. 配额维度执行状态对齐（需逐项决策/文档化）
| 维度 | 服务端 | 客户端 | 结论 |
|---|---|---|---|
| perSeatMaxDevices | sync 硬卡（有 #7、#8 缺口） | 无 | 基本生效，修 #7/#8 |
| perUserMaxPrivateConnections | push 前置（依赖 #1 修复） | 坏（#2） | 修 #1/#2 后生效 |
| perUserMaxOpenConnections | **无** | 坏（#2） | 决策：服务端无法感知「打开」，明确为客户端限制并文档化；修 #2 后客户端恢复 |
| perUserPrivateSyncQuotaBytes | push/rollback 前置 | 无 | 生效（另见 #13） |
| perUserSyncVersionRetention | pruneVersions | 无 | 生效（0=无限需文档化） |
| perUserHistoryRetentionCount | 不可执行（history 节 E2E 加密） | 生效（字段名一致） | 文档化：客户端限制 |
| orgMaxSharedConnections / orgSharedSyncQuotaBytes | **无** | 无 | 决策：在 `createResource/updateResource` 加校验，或文档化未实现 |
| orgMaxMembers | **无** | 无 | 见 #6 |
| features | `hasFeature` 零调用 | `requireFeature`（生效） | 文档化：客户端门控；如需服务端强制另议 |

### 16. admin 自我续费无门禁（self-dealing）
- 位置：`server/src/route/admin.ts:111-124`。
- 现状：admin 可给任意组织（含自己所属组织）免费续费任意套餐，仅留审计。
- 修复（轻量）：目标组织的成员包含操作者时在审计 `detail` 标记 `selfBenefit: true`；是否禁止/二次确认由产品决策。

### 17. admin-ui 展示修正（UserDetailModal.vue 为主）
- Connections 页 `deleted` 徽章是死分支（服务端 `listByUser` 只返回 `delete_time IS NULL`）：要么服务端改返回墓碑行，要么删徽章分支；
- 同页「连接数对服务端不可见」提示与连接元数据页矛盾，改写；
- 会话吊销确认框补充「将同时撤销该设备绑定及其全部会话」；
- PlansView 编辑表单对 0 值显示「= 无限」提示（0=无限语义陷阱）；
- Traffic 页对「仅最近 60 分钟内存数据、routes 恒为 all、blockedTotal 为最近 200 条」加注释或按实际契约渲染。

### 18. 客户端残留清理（vscode-ext）
- `reportUsage` 打不存在的 `POST /api/usage`（syncClient.ts:228-231）：v2 无此端点，遥测发出即 404 且计数已清零。决策：删掉上报链路或补服务端端点；
- `changePassword` 注释「server 会 501」过期，删；
- `MeResponse.subscription.planCode` 在服务端不存在（服务端是 `planId`），类型改正；
- `X-Device-Os-Machine-Id` 头服务端不读（deviceHeaders.ts 无映射），删或补映射；
- `register` 响应带 `subscription` 而 `login` 不带：对齐（建议 login 也带，客户端登录后可直接展示订阅）。

### 19. 管理端可见性缺口
- 无「用户 → 所属组织/成员关系」视图：`getUserDetail` 增加 `memberships`（组织名 + 角色 + 状态），admin-ui 用户详情加一块展示；
